# 库存回滚实现

## 1. 功能定义

库存回滚要解决的问题是：

- 某笔订单之前占用或扣减的库存，在订单取消、支付失败、退款成功等场景下，如何安全地恢复回来

如果说库存扣减是“占资源”，那库存回滚就是“把资源还回去”。  
它和库存扣减一样重要，因为很多系统的库存问题并不是“扣错了”，而是“该还的时候没还”。

## 2. 哪些场景需要库存回滚

最常见的几种场景包括：

- 下单后未支付，订单取消
- 支付超时自动关闭
- 锁库存成功，但订单创建失败
- 支付成功后整单退款，恢复可售库存

不同场景的回滚方式可能不完全一样，关键取决于你之前采用的是哪种库存策略。

## 3. 回滚的前提：先分清你回滚的是什么

库存回滚并不总是同一种动作。

### 3.1 回滚锁定库存

适用于：

- 下单时先锁库存
- 最终没支付成功

此时通常是：

- `lockedStock - n`
- `availableStock + n`

### 3.2 回滚正式扣减库存

适用于：

- 已支付后已经正式扣减
- 后续整单退款或逆向业务需要恢复库存

此时通常是：

- `availableStock + n`

所以库存回滚实现前，必须先把库存生命周期设计清楚。

## 4. 典型流程

以“下单锁库存，取消订单回滚锁库存”为例，流程通常是：

1. 订单取消
2. 根据订单明细查出对应 SKU 和数量
3. 恢复可售库存
4. 减少锁定库存
5. 记录库存回滚流水

## 5. 核心设计

库存回滚实现时，至少要考虑：

1. 回滚动作必须幂等
2. 回滚要基于业务单据
3. 回滚要有流水
4. 回滚和订单状态要协同

其中“幂等”非常关键。  
因为取消订单、退款回调、补偿任务等场景，都可能触发重复回滚风险。

## 6. 核心代码

## 6.1 回滚锁库存核心实现

```java
@Service
public class InventoryServiceImpl implements InventoryService {

    private final InventoryMapper inventoryMapper;
    private final InventoryLogMapper inventoryLogMapper;

    public InventoryServiceImpl(
            InventoryMapper inventoryMapper,
            InventoryLogMapper inventoryLogMapper) {
        this.inventoryMapper = inventoryMapper;
        this.inventoryLogMapper = inventoryLogMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void rollbackReservedStock(Long orderId, List<OrderItemDTO> items) {
        for (OrderItemDTO item : items) {
            boolean alreadyRollback = inventoryLogMapper.existsByOrderIdAndSkuIdAndType(
                    orderId,
                    item.getSkuId(),
                    "ROLLBACK_RESERVED"
            );
            if (alreadyRollback) {
                continue;
            }

            int updated = inventoryMapper.rollbackReservedStock(item.getSkuId(), item.getQuantity());
            if (updated == 0) {
                throw new BizException("库存回滚失败, skuId=" + item.getSkuId());
            }

            InventoryLog log = new InventoryLog();
            log.setOrderId(orderId);
            log.setSkuId(item.getSkuId());
            log.setChangeType("ROLLBACK_RESERVED");
            log.setQuantity(item.getQuantity());
            log.setCreateTime(LocalDateTime.now());
            inventoryLogMapper.insert(log);
        }
    }
}
```

对应的 SQL 核心思路通常是：

```sql
update inventory
set available_stock = available_stock + #{quantity},
    locked_stock = locked_stock - #{quantity}
where sku_id = #{skuId}
  and locked_stock >= #{quantity}
```

这条 SQL 的意义是：

- 只允许在锁库存足够时回滚

## 7. 为什么库存回滚必须幂等

因为真实项目里，订单取消这件事可能来自多个触发源：

- 用户主动取消
- 超时自动关闭
- 人工补偿任务

如果回滚逻辑没有幂等控制，就可能出现：

- 库存被多次加回

这比少扣库存还危险，因为它会直接制造“虚假库存”。

所以常见做法包括：

1. 依赖订单状态控制
2. 依赖库存流水去重
3. 给库存回滚动作建立幂等唯一键

## 8. 正式扣减后的库存回补怎么理解

如果业务规则是：

- 支付成功才正式扣减库存

那么后续整单退款后，可能还要做“库存回补”。  
它和“锁库存回滚”很像，但业务语义不同。

这类场景建议在库存日志里区分类型，例如：

- `DEDUCT`
- `ROLLBACK_RESERVED`
- `RESTORE_AFTER_REFUND`

这样后续排查会清晰很多。

## 9. 常见坑点

### 9.1 库存回滚不做幂等

容易造成库存多次恢复。

### 9.2 没有库存流水

出问题后无法判断库存是怎么被加回去的。

### 9.3 回滚逻辑和库存策略不匹配

如果系统根本没有锁库存，却写了“回滚锁库存”逻辑，就会越做越乱。

## 10. 总结

库存回滚的核心，不是“加回去一个数字”，而是根据库存生命周期，把之前占用的资源按规则、按幂等方式恢复回来。

一个成熟的库存回滚实现至少应该做到：

- 明确回滚的是锁库存还是正式库存
- 按业务单据驱动回滚
- 回滚动作可幂等
- 库存流水可追溯

这才是库存体系真正完整的一半。
