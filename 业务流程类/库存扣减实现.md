# 库存扣减实现

## 1. 功能定义

库存扣减要解决的问题是：

- 当用户下单或支付成功后，系统如何把可售库存准确减少

它是订单系统里最典型、也最容易出并发问题的一环。  
因为库存天然是一个竞争资源：

- 多个用户可能同时买同一个商品
- 不能超卖
- 还要兼顾性能

所以库存扣减远不是一个普通的更新语句问题。

## 2. 常见库存模型

库存通常至少会区分两类：

1. 可售库存
2. 锁定库存

例如：

```json
{
  "skuId": 1001,
  "availableStock": 98,
  "lockedStock": 2
}
```

这两个字段分别表示：

- `availableStock`：还能卖多少
- `lockedStock`：已经被订单占住但还未最终完成多少

这是一种非常常见的库存设计。

## 3. 到底什么时候扣库存

这是库存系统里最核心的策略问题之一。  
常见有两种方案：

### 3.1 下单即扣减

优点：

- 逻辑直观

缺点：

- 大量未支付订单会占住库存

### 3.2 下单锁库存，支付后正式扣减

优点：

- 更适合支付型订单
- 逻辑更细化

缺点：

- 需要额外处理锁库存和回滚

正式电商或复杂业务里，更常见的是第二种。

## 4. 典型流程

如果采用“下单锁库存，支付后确认扣减”方案，流程通常如下：

1. 下单时锁定库存
2. 支付成功后确认扣减
3. 未支付取消时回滚锁定库存

所以严格来说，“库存扣减”和“库存锁定”往往不是同一件事。  
但如果你讨论的是支付成功后确认扣减，那重点就在于把锁定库存转成正式扣减结果。

## 5. 核心设计

库存扣减实现时，至少要解决：

1. 并发扣减不能超卖
2. 同一订单不能重复扣减
3. 库存操作要有业务流水
4. 扣减失败要能感知并补偿

## 6. 核心代码

## 6.1 扣减核心实现

下面给一个常见的“数据库乐观更新”思路。

```java
@Service
public class InventoryServiceImpl implements InventoryService {

    private final InventoryMapper inventoryMapper;
    private final InventoryLogMapper inventoryLogMapper;

    public InventoryServiceImpl(
            InventoryMapper inventoryMapper,
            InventoryLogMapper inventoryLogMapper) {
        this.inventoryMapper = inventoryMapper;
        this.inventoryLogMapper = inventoryLogMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void deductStock(Long orderId, List<OrderItemDTO> items) {
        for (OrderItemDTO item : items) {
            int updated = inventoryMapper.deductAvailableStock(item.getSkuId(), item.getQuantity());
            if (updated == 0) {
                throw new BizException("库存不足, skuId=" + item.getSkuId());
            }

            InventoryLog log = new InventoryLog();
            log.setOrderId(orderId);
            log.setSkuId(item.getSkuId());
            log.setChangeType("DEDUCT");
            log.setQuantity(item.getQuantity());
            log.setCreateTime(LocalDateTime.now());
            inventoryLogMapper.insert(log);
        }
    }
}
```

对应的更新 SQL 核心思路一般是：

```sql
update inventory
set available_stock = available_stock - #{quantity}
where sku_id = #{skuId}
  and available_stock >= #{quantity}
```

这条 SQL 的关键意义在于：

- 让“判断库存够不够”和“扣减库存”变成一个原子动作

## 7. 为什么不能先查库存再更新

很多初学者会写成：

1. 先 `select`
2. 判断库存够不够
3. 再 `update`

这种写法在并发下非常容易出问题。  
因为两个请求可能同时查到“库存还够”，然后一起更新，最终造成超卖。

所以更稳的方式一定是：

- 把判断和扣减合成一条有条件的更新 SQL

## 8. 库存流水为什么重要

库存流水可以帮助你解决很多后续问题：

- 这次库存为什么变少了
- 是哪笔订单扣的
- 是正式扣减还是回滚
- 某个 SKU 今天一共发生了多少库存变化

如果只有库存最终值，没有流水，排查问题会非常痛苦。

## 9. 常见坑点

### 9.1 先查再扣

这是超卖最经典的来源之一。

### 9.2 库存扣减没有业务流水

出问题后很难追踪。

### 9.3 支付回调重复触发时重复扣库存

所以库存扣减通常也要结合订单状态或库存日志做幂等保护。

## 10. 总结

库存扣减的核心，不是“减一个数字”，而是在高并发下安全地减少可售资源，并且确保每次变动都可追踪。

一个成熟的库存扣减实现至少应该做到：

- 条件更新防超卖
- 扣减动作事务化
- 库存流水留痕
- 重复回调可幂等

这才是库存系统真正能支撑订单流程的关键。
