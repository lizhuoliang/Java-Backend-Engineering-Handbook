# 任务分配实现

## 1. 功能定义

任务分配要解决的问题是：

- 某项工作应该由谁来处理，以及系统如何把这项工作准确地派给合适的人

常见场景包括：

- 工单分配
- 客服接单
- 线索分配
- 审批待办分派
- 运维告警派单

任务分配看起来像是“给某个人填个负责人”，但工程化项目里往往还要考虑：

- 分配规则是什么
- 是手动分配还是自动分配
- 已分配任务是否允许转派
- 分配动作是否留痕

## 2. 典型任务结构

```json
{
  "taskId": 7001,
  "taskType": "WORK_ORDER",
  "title": "处理服务器异常告警",
  "status": "WAIT_HANDLE",
  "assigneeUserId": 201
}
```

这里最核心的字段通常有：

- 任务类型
- 当前状态
- 当前负责人

## 3. 常见分配方式

任务分配大致有三种：

### 3.1 手动分配

由管理员、组长或系统操作员指定处理人。

### 3.2 自动分配

由系统根据规则自动挑选人，例如：

- 按部门
- 按岗位
- 按轮询
- 按空闲度

### 3.3 抢单模式

系统只把任务放到公共池里，由处理人自己领取。

本文先讲最典型、最常见的“手动分配 + 自动分配规则扩展”。

## 4. 核心设计

任务分配设计时，建议重点考虑：

1. 分配动作必须留痕
2. 分配要校验任务当前状态
3. 分配规则要和组织结构结合
4. 转派、改派、撤销规则要提前明确

## 5. 典型流程

1. 创建任务
2. 系统根据规则分配给处理人，或者由管理员手动分配
3. 任务进入待处理状态
4. 处理人开始处理
5. 后续可完成、退回、转派

## 6. 核心代码

## 6.1 手动分配核心实现

```java
@Service
public class TaskAssignServiceImpl implements TaskAssignService {

    private final TaskMapper taskMapper;
    private final TaskAssignLogMapper taskAssignLogMapper;

    public TaskAssignServiceImpl(
            TaskMapper taskMapper,
            TaskAssignLogMapper taskAssignLogMapper) {
        this.taskMapper = taskMapper;
        this.taskAssignLogMapper = taskAssignLogMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void assign(Long taskId, Long assigneeUserId, Long operatorUserId) {
        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            throw new BizException("任务不存在");
        }

        if ("DONE".equals(task.getStatus()) || "CANCELLED".equals(task.getStatus())) {
            throw new BizException("当前任务状态不允许分配");
        }

        Task update = new Task();
        update.setId(taskId);
        update.setAssigneeUserId(assigneeUserId);
        update.setStatus("WAIT_HANDLE");
        taskMapper.updateById(update);

        TaskAssignLog log = new TaskAssignLog();
        log.setTaskId(taskId);
        log.setBeforeAssigneeUserId(task.getAssigneeUserId());
        log.setAfterAssigneeUserId(assigneeUserId);
        log.setOperatorUserId(operatorUserId);
        log.setCreateTime(LocalDateTime.now());
        taskAssignLogMapper.insert(log);
    }
}
```

这段代码里非常关键的一点是：

- 分配动作单独记日志

因为后续很多问题都需要看：

- 任务最初给了谁
- 后来被谁改派过
- 是谁操作的

## 6.2 自动分配核心思路

自动分配最简单的一个版本可以是“轮询分配”：

```java
public interface TaskAutoAssignRule {

    Long selectAssignee(String taskType, Long deptId);
}
```

例如：

- 任务先按部门找候选人
- 再从候选人列表里选当前负载最低的人

或者：

- 直接按轮询顺序选一个人

这里的核心不是算法多复杂，而是要把“分配规则”抽出来，不要写死在业务方法里。

## 7. 为什么分配动作要和任务状态联动

因为并不是所有状态都允许重新分配。  
例如：

- 已完成任务通常不该再分配
- 已取消任务也不该再分配

所以分配操作必须是：

- 对任务生命周期有感知的动作

而不是随时想改就改。

## 8. 转派怎么理解

转派本质上也是一种分配，只不过触发者可能变成当前处理人。  
例如：

- 当前人不会处理
- 当前人请假
- 当前人工作量过大

工程上通常建议：

- 手动分配
- 转派
- 系统自动分配

三者共用一套“负责人变更 + 留痕”的底层能力。

## 9. 常见坑点

### 9.1 只改负责人字段，不记分配日志

后续无法追踪责任流转。

### 9.2 不校验任务状态

可能把已关闭任务又重新分给别人。

### 9.3 自动分配规则写死

后面一旦业务变复杂，维护成本会很高。

## 10. 总结

任务分配的核心，不是“填一个 assigneeUserId”，而是围绕任务状态、分配规则和责任留痕，建立一套可解释、可追踪、可扩展的派单机制。

这类能力在工单、审批、客服、运维等系统里都非常常见，也是业务流程类里很典型的一块能力。
