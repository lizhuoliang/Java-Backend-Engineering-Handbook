# 订单退款实现

## 1. 功能定义

订单退款要解决的问题是：

- 一笔已经支付的订单，在满足退款条件时，如何把资金按规则退回给用户，并同步更新订单与退款状态

退款是订单系统中非常敏感的一环，因为它同时涉及：

- 订单状态
- 资金状态
- 第三方支付渠道
- 库存和权益回收
- 退款单据追踪

所以退款绝对不能只理解成“调一下退款接口”。

## 2. 为什么退款需要单独的退款单

和支付类似，退款流程通常也需要独立的退款单。  
原因很简单：

- 一笔订单可能分多次退款
- 一次退款可能失败后重试
- 退款要记录渠道单号和状态变化

例如：

```json
{
  "refundNo": "REF202606020001",
  "orderId": 5001,
  "refundAmount": 99.00,
  "status": "WAIT_REFUND",
  "reason": "用户申请退款"
}
```

如果没有退款单，很多退款链路就很难追踪。

## 3. 典型退款流程

一个完整的退款流程通常如下：

1. 用户或客服发起退款申请
2. 系统查询订单并校验是否允许退款
3. 创建退款单
4. 调用第三方退款接口
5. 第三方异步返回退款结果
6. 更新退款单状态
7. 更新订单退款状态
8. 回收权益或恢复库存

## 4. 什么时候允许退款

这取决于业务场景，但一般至少会考虑：

- 订单是否已支付
- 是否已退款完成
- 是否超出退款时限
- 是否已经发货或已消费

退款流程最危险的地方之一，就是没有把“允许退款的状态范围”设计清楚。

## 5. 核心设计

我建议退款实现至少要明确：

1. 退款单独建表
2. 退款金额必须校验
3. 支持全额退款和部分退款
4. 退款结果不能只看同步接口返回
5. 退款后的订单状态要按规则更新

## 6. 核心代码

## 6.1 申请退款核心实现

```java
@Service
public class OrderRefundServiceImpl implements OrderRefundService {

    private final OrderMapper orderMapper;
    private final RefundOrderMapper refundOrderMapper;
    private final RefundNoGenerator refundNoGenerator;
    private final RefundChannelService refundChannelService;

    public OrderRefundServiceImpl(
            OrderMapper orderMapper,
            RefundOrderMapper refundOrderMapper,
            RefundNoGenerator refundNoGenerator,
            RefundChannelService refundChannelService) {
        this.orderMapper = orderMapper;
        this.refundOrderMapper = refundOrderMapper;
        this.refundNoGenerator = refundNoGenerator;
        this.refundChannelService = refundChannelService;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public RefundApplyVO apply(Long orderId, BigDecimal refundAmount, String reason) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException("订单不存在");
        }
        if (!"PAID".equals(order.getStatus()) && !"PART_REFUND".equals(order.getStatus())) {
            throw new BizException("当前订单状态不允许退款");
        }
        if (refundAmount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new BizException("退款金额必须大于0");
        }
        if (refundAmount.compareTo(order.getPayAmount()) > 0) {
            throw new BizException("退款金额不能大于实付金额");
        }

        String refundNo = refundNoGenerator.generate();

        RefundOrder refundOrder = new RefundOrder();
        refundOrder.setRefundNo(refundNo);
        refundOrder.setOrderId(orderId);
        refundOrder.setRefundAmount(refundAmount);
        refundOrder.setReason(reason);
        refundOrder.setStatus("WAIT_REFUND");
        refundOrder.setCreateTime(LocalDateTime.now());
        refundOrderMapper.insert(refundOrder);

        refundChannelService.refund(refundOrder);

        RefundApplyVO vo = new RefundApplyVO();
        vo.setRefundNo(refundNo);
        vo.setStatus("WAIT_REFUND");
        return vo;
    }
}
```

这里的重点不是“调了退款渠道”，而是：

- 退款资格校验
- 退款金额校验
- 退款单持久化

## 6.2 退款成功回调核心实现

```java
@Service
public class RefundCallbackServiceImpl implements RefundCallbackService {

    private final RefundOrderMapper refundOrderMapper;
    private final OrderMapper orderMapper;

    public RefundCallbackServiceImpl(
            RefundOrderMapper refundOrderMapper,
            OrderMapper orderMapper) {
        this.refundOrderMapper = refundOrderMapper;
        this.orderMapper = orderMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void handleRefundSuccess(RefundCallbackDTO callback) {
        RefundOrder refundOrder = refundOrderMapper.selectByRefundNo(callback.getRefundNo());
        if (refundOrder == null) {
            throw new BizException("退款单不存在");
        }

        if ("SUCCESS".equals(refundOrder.getStatus())) {
            return;
        }

        RefundOrder refundUpdate = new RefundOrder();
        refundUpdate.setId(refundOrder.getId());
        refundUpdate.setStatus("SUCCESS");
        refundUpdate.setRefundTime(callback.getRefundTime());
        refundUpdate.setThirdRefundNo(callback.getThirdRefundNo());
        refundOrderMapper.updateById(refundUpdate);

        Order order = orderMapper.selectById(refundOrder.getOrderId());
        if (order != null) {
            Order orderUpdate = new Order();
            orderUpdate.setId(order.getId());
            if (refundOrder.getRefundAmount().compareTo(order.getPayAmount()) == 0) {
                orderUpdate.setStatus("REFUNDED");
            } else {
                orderUpdate.setStatus("PART_REFUND");
            }
            orderMapper.updateById(orderUpdate);
        }
    }
}
```

这段代码里最重要的地方是：

- 回调幂等
- 退款单和订单状态联动
- 区分全额退款和部分退款

## 7. 为什么退款也要走回调思维

因为退款渠道的同步调用结果，未必就是最终结果。  
有些支付平台可能会返回：

- 退款受理中
- 退款处理中

真正最终是否退款成功，仍然要以异步通知或后续查询为准。

所以退款流程和支付流程非常像：

- 发起退款只是开始
- 最终状态以回调或查询结果为准

## 8. 退款后可能还要做什么

退款成功后，系统通常还要继续处理：

- 恢复库存
- 回收权益
- 回退积分
- 关闭履约流程
- 发送退款通知

这类动作如果很多，也更适合用异步事件方式分发。

## 9. 常见坑点

### 9.1 不建退款单，直接调退款接口

后续状态追踪和问题排查会很困难。

### 9.2 退款金额不校验

容易导致超额退款。

### 9.3 退款回调不做幂等

可能导致重复业务补偿。

### 9.4 退款后订单状态不更新

会导致订单资金状态和业务状态不一致。

## 10. 总结

订单退款的核心，不是“把钱退回去”这么简单，而是围绕退款资格、退款单、渠道回调和状态联动，建立一条完整的逆向资金流程。

一个成熟的退款实现至少应该做到：

- 单独建退款单
- 金额和状态严格校验
- 以回调结果为准
- 支持全额和部分退款

这才是可追踪、可审计、可运维的退款体系。
