# 订单支付实现

## 1. 功能定义

订单支付要解决的问题是：

- 用户为一笔待支付订单完成付款后，系统如何安全地把订单状态从“待支付”推进到“已支付”

支付看上去像一个简单的“改状态”，但它在业务流程里往往是最敏感的环节之一。  
真正的支付实现通常会同时涉及：

- 支付单创建
- 第三方支付渠道调用
- 支付回调验签
- 幂等处理
- 订单状态流转
- 库存确认
- 发货或权益发放

所以支付不是一个单接口问题，而是一套典型的状态驱动流程。

## 2. 支付和下单的边界

下单的目标是：

- 生成一笔合法订单

支付的目标是：

- 让一笔合法订单完成资金确认

这两个动作通常要拆开，因为：

- 下单不代表付款
- 付款成功也不应该只由前端一句“支付完成”决定

真正可靠的支付确认，一般都依赖支付回调。

## 3. 典型流程

一个常见的支付流程如下：

1. 用户发起支付
2. 后端校验订单状态是否允许支付
3. 创建支付单
4. 调用第三方支付接口，返回支付参数
5. 用户在支付平台完成付款
6. 支付平台回调后端
7. 后端验签并校验金额
8. 更新支付单状态
9. 更新订单状态为 `PAID`
10. 触发后续履约逻辑

## 4. 为什么支付回调比前端结果更可信

因为前端结果可以被伪造。  
如果你只依据前端“支付成功”的通知来改订单状态，风险会非常大。

更稳的支付确认方式一般是：

1. 前端只负责发起支付
2. 后端以第三方支付回调为准确认结果

所以支付实现里最关键的一段逻辑，通常不是“拉起支付”，而是“支付回调处理”。

## 5. 典型数据结构

支付系统里通常会至少有：

1. 订单表
2. 支付单表

例如：

```json
{
  "payOrder": {
    "payNo": "PAY202606020001",
    "orderId": 5001,
    "payAmount": 159.00,
    "status": "WAIT_PAY",
    "channel": "ALIPAY"
  }
}
```

为什么还要单独做支付单？

因为一笔订单后面可能涉及：

- 多次支付尝试
- 不同支付渠道
- 支付失败重试

如果所有信息都挤在订单表里，后期会很难维护。

## 6. 核心设计

订单支付设计时，建议至少明确这些点：

1. 订单和支付单分离
2. 支付结果以回调为准
3. 回调必须做验签和幂等
4. 更新订单状态时要校验原状态
5. 支付成功后的后续动作尽量异步

## 7. 核心代码

## 7.1 发起支付核心实现

```java
@Service
public class OrderPayServiceImpl implements OrderPayService {

    private final OrderMapper orderMapper;
    private final PayOrderMapper payOrderMapper;
    private final PayNoGenerator payNoGenerator;
    private final PayChannelService payChannelService;

    public OrderPayServiceImpl(
            OrderMapper orderMapper,
            PayOrderMapper payOrderMapper,
            PayNoGenerator payNoGenerator,
            PayChannelService payChannelService) {
        this.orderMapper = orderMapper;
        this.payOrderMapper = payOrderMapper;
        this.payNoGenerator = payNoGenerator;
        this.payChannelService = payChannelService;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public PayCreateVO createPayOrder(Long orderId, String channel) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException("订单不存在");
        }
        if (!"WAIT_PAY".equals(order.getStatus())) {
            throw new BizException("当前订单状态不允许支付");
        }

        String payNo = payNoGenerator.generate();

        PayOrder payOrder = new PayOrder();
        payOrder.setPayNo(payNo);
        payOrder.setOrderId(orderId);
        payOrder.setPayAmount(order.getPayAmount());
        payOrder.setStatus("WAIT_PAY");
        payOrder.setChannel(channel);
        payOrder.setCreateTime(LocalDateTime.now());
        payOrderMapper.insert(payOrder);

        return payChannelService.createPay(payOrder);
    }
}
```

这段代码里最重要的是：

- 支付前必须校验订单状态
- 支付参数从后端订单数据生成
- 支付单单独落库

## 7.2 支付回调核心实现

```java
@Service
public class PayCallbackServiceImpl implements PayCallbackService {

    private final PayOrderMapper payOrderMapper;
    private final OrderMapper orderMapper;

    public PayCallbackServiceImpl(PayOrderMapper payOrderMapper, OrderMapper orderMapper) {
        this.payOrderMapper = payOrderMapper;
        this.orderMapper = orderMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void handlePaySuccess(PayCallbackDTO callback) {
        if (!callback.isSignatureValid()) {
            throw new BizException("回调验签失败");
        }

        PayOrder payOrder = payOrderMapper.selectByPayNo(callback.getPayNo());
        if (payOrder == null) {
            throw new BizException("支付单不存在");
        }

        if ("SUCCESS".equals(payOrder.getStatus())) {
            return;
        }

        if (payOrder.getPayAmount().compareTo(callback.getPayAmount()) != 0) {
            throw new BizException("支付金额不一致");
        }

        PayOrder payUpdate = new PayOrder();
        payUpdate.setId(payOrder.getId());
        payUpdate.setStatus("SUCCESS");
        payUpdate.setThirdTradeNo(callback.getThirdTradeNo());
        payUpdate.setPayTime(callback.getPayTime());
        payOrderMapper.updateById(payUpdate);

        Order order = orderMapper.selectById(payOrder.getOrderId());
        if (order != null && "WAIT_PAY".equals(order.getStatus())) {
            Order orderUpdate = new Order();
            orderUpdate.setId(order.getId());
            orderUpdate.setStatus("PAID");
            orderUpdate.setPayTime(callback.getPayTime());
            orderMapper.updateById(orderUpdate);
        }
    }
}
```

这段代码是支付实现里最关键的部分。  
它至少做了 5 件大事：

- 验签
- 查支付单
- 做幂等处理
- 校验金额
- 更新支付单和订单状态

## 8. 为什么支付回调必须幂等

因为第三方支付平台的回调不一定只来一次。  
常见情况包括：

- 网络波动导致平台重复通知
- 你的系统响应超时，平台认为没成功
- 人工补单或平台重发

如果回调处理没有幂等，就可能出现：

- 重复改状态
- 重复发货
- 重复发积分

所以支付回调里通常至少要做：

- 如果支付单已经成功，直接返回

## 9. 为什么金额必须校验

因为支付单和第三方回调金额不一致时，说明存在严重风险：

- 数据被篡改
- 回调错单
- 支付配置错误

所以回调时不能只看到“成功”就盲目把订单改成已支付。

## 10. 支付成功后还能触发什么

支付成功只是一个关键节点，它后面通常还会触发很多流程，例如：

- 库存正式扣减
- 优惠券核销
- 积分发放
- 站内信通知
- 发货任务创建

正式项目里，这些动作通常不建议都在回调事务里同步执行，而更适合：

- 回调里先完成核心状态更新
- 后续动作用 MQ 异步分发

## 11. 常见坑点

### 11.1 只相信前端支付成功通知

这是最典型的支付设计错误之一。

### 11.2 回调不做幂等

会导致重复业务执行。

### 11.3 不校验订单原状态

可能把一笔已取消、已关闭订单错误地改成已支付。

### 11.4 回调里做太多重逻辑

容易造成回调处理过慢，甚至再次被支付平台重试。

## 12. 总结

订单支付的核心，不是“调起支付页面”，而是围绕支付单、回调确认、幂等处理和状态流转，建立一条可靠的资金确认链路。

一个更成熟的实现至少应该做到：

- 订单和支付单分离
- 支付结果以回调为准
- 回调验签、验金额、做幂等
- 订单状态按规则推进

这才是支付系统真正可靠的基础。
