# 审批流实现

## 1. 功能定义

审批流要解决的问题是：

- 某个业务申请从发起到通过、驳回、撤回之间，如何按照组织规则逐步流转

最常见的审批场景包括：

- 请假审批
- 报销审批
- 用印审批
- 合同审批
- 采购审批

审批流的核心不是“有个通过按钮”，而是：

- 谁能审批
- 审到哪一步
- 驳回后怎么处理
- 最终状态如何确定

## 2. 审批流和工作流的区别

这两个概念经常被混用，但可以先这样理解：

- 审批流：更强调“逐级审批决策”
- 工作流：更强调“整个业务节点编排”

也就是说，审批流通常可以看作工作流中的一个重要子类型。  
如果先学工程化，审批流是一个非常好的切入口，因为它的核心结构更明确。

## 3. 一个审批流通常包含什么

最常见的审批流最少会包含三类数据：

1. 申请单
2. 审批实例
3. 审批节点记录

例如：

```json
{
  "applyNo": "LEAVE202606020001",
  "applicantUserId": 101,
  "status": "APPROVING",
  "currentNode": "部门经理审批",
  "records": [
    {
      "nodeName": "部门经理审批",
      "approverUserId": 201,
      "status": "WAIT_APPROVE"
    }
  ]
}
```

## 4. 典型流程

一个最基础的审批流程通常如下：

1. 用户发起申请
2. 系统创建审批实例
3. 生成第一个待审批节点
4. 审批人处理节点
5. 如果通过，则推进到下一个节点
6. 如果驳回，则结束流程
7. 所有节点通过后，申请单状态变为已通过

## 5. 核心设计

审批流设计时，建议至少明确：

1. 申请单和审批记录分开
2. 当前节点是谁要审批要明确
3. 节点状态变化要留痕
4. 驳回、撤回、转交规则要提前定
5. 审批动作必须做状态校验

## 6. 核心代码

## 6.1 发起审批核心实现

```java
@Service
public class LeaveApproveServiceImpl implements LeaveApproveService {

    private final LeaveApplyMapper leaveApplyMapper;
    private final ApproveNodeMapper approveNodeMapper;
    private final ApproverResolver approverResolver;

    public LeaveApproveServiceImpl(
            LeaveApplyMapper leaveApplyMapper,
            ApproveNodeMapper approveNodeMapper,
            ApproverResolver approverResolver) {
        this.leaveApplyMapper = leaveApplyMapper;
        this.approveNodeMapper = approveNodeMapper;
        this.approverResolver = approverResolver;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void submit(LeaveApplyRequest request) {
        LeaveApply apply = new LeaveApply();
        apply.setApplicantUserId(request.getApplicantUserId());
        apply.setReason(request.getReason());
        apply.setStatus("APPROVING");
        apply.setCreateTime(LocalDateTime.now());
        leaveApplyMapper.insert(apply);

        Long approverUserId = approverResolver.resolveDeptManager(request.getApplicantUserId());

        ApproveNode node = new ApproveNode();
        node.setApplyId(apply.getId());
        node.setNodeNo(1);
        node.setNodeName("部门经理审批");
        node.setApproverUserId(approverUserId);
        node.setStatus("WAIT_APPROVE");
        approveNodeMapper.insert(node);
    }
}
```

这段代码里最核心的思想是：

- 发起申请不等于审批结束
- 发起后要生成一个明确的待审批节点

## 6.2 审批通过核心实现

```java
@Service
public class ApproveActionServiceImpl implements ApproveActionService {

    private final ApproveNodeMapper approveNodeMapper;
    private final LeaveApplyMapper leaveApplyMapper;

    public ApproveActionServiceImpl(
            ApproveNodeMapper approveNodeMapper,
            LeaveApplyMapper leaveApplyMapper) {
        this.approveNodeMapper = approveNodeMapper;
        this.leaveApplyMapper = leaveApplyMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void approve(Long nodeId, Long approverUserId, String remark) {
        ApproveNode node = approveNodeMapper.selectById(nodeId);
        if (node == null) {
            throw new BizException("审批节点不存在");
        }
        if (!Objects.equals(node.getApproverUserId(), approverUserId)) {
            throw new BizException("无权审批当前节点");
        }
        if (!"WAIT_APPROVE".equals(node.getStatus())) {
            throw new BizException("当前节点已处理");
        }

        ApproveNode updateNode = new ApproveNode();
        updateNode.setId(nodeId);
        updateNode.setStatus("APPROVED");
        updateNode.setRemark(remark);
        updateNode.setApproveTime(LocalDateTime.now());
        approveNodeMapper.updateById(updateNode);

        LeaveApply updateApply = new LeaveApply();
        updateApply.setId(node.getApplyId());
        updateApply.setStatus("APPROVED");
        leaveApplyMapper.updateById(updateApply);
    }
}
```

这里先给的是最简一层审批版本。  
如果是多级审批，核心差异只是：

- 审完一个节点后，不是直接结束
- 而是继续创建下一个节点

## 7. 为什么审批记录必须留痕

审批是一种强审计业务。  
很多时候系统最重要的不是“现在是什么状态”，而是：

- 谁审批过
- 什么时候审批的
- 审批意见是什么

所以审批节点记录表几乎是审批流里最不能省的一张表。

## 8. 多级审批怎么扩展

例如一个更复杂的审批链可能是：

1. 部门经理审批
2. 人事审批
3. 总监审批

这种情况下，工程实现通常会多出一个“流程定义”层，用来描述：

- 第几步是谁审批
- 下一步是什么

但无论流程定义多复杂，运行时核心都还是：

- 当前待审批节点
- 节点处理结果
- 流程实例状态

## 9. 常见坑点

### 9.1 审批动作不校验当前节点状态

容易导致重复审批或越级审批。

### 9.2 申请单状态和审批节点状态不同步

会让前端展示和后端规则出现冲突。

### 9.3 只在申请单上改状态，不留审批记录

后续无法审计。

## 10. 总结

审批流的核心，不是“有通过和驳回按钮”，而是围绕申请单、审批节点和状态流转，建立一套可追踪、可审计、可扩展的处理链路。

一个成熟的审批流实现至少应该做到：

- 申请单和审批记录分离
- 当前审批人明确
- 节点状态可校验
- 审批过程全留痕

这样后面扩展多级审批、抄送、转交、撤回才会更稳。
