# 活动系统实现

## 1. 功能定义

活动系统要解决的问题是：

- 在一定时间、规则和对象范围内，通过营销玩法影响用户行为和订单转化

常见活动包括：

- 限时秒杀
- 满减活动
- 拼团活动
- 新人专享
- 节日促销

从工程视角看，活动系统的重点不是页面样式，而是：

- 活动规则怎么定义
- 活动生效范围怎么判断
- 活动和订单价格如何联动
- 活动并发下如何保证正确性

## 2. 活动系统和优惠券的关系

这两个概念经常一起出现，但它们不完全一样。

- 优惠券更偏“凭证型优惠”
- 活动更偏“场景型规则”

例如：

- 满 200 减 30 的券，需要先领券
- 限时满 200 减 30 的活动，可能所有用户自动生效

所以活动系统更像一个“营销规则引擎入口”。

## 3. 一个活动通常包含什么

一个基础活动通常至少有：

```json
{
  "activityId": 3001,
  "activityName": "618满减活动",
  "activityType": "FULL_REDUCTION",
  "startTime": "2026-06-10 00:00:00",
  "endTime": "2026-06-18 23:59:59",
  "status": "ENABLED"
}
```

如果再展开，通常还会有：

- 规则明细
- 适用商品范围
- 适用用户范围

## 4. 典型流程

一个典型活动参与流程通常如下：

1. 系统配置活动
2. 用户下单时系统匹配活动
3. 校验活动是否在有效期内
4. 校验订单商品是否命中活动范围
5. 按规则计算优惠
6. 订单支付成功后记活动参与结果

## 5. 核心设计

活动系统实现时，我建议重点考虑：

1. 活动定义和活动规则分离
2. 活动计算要可扩展
3. 活动是否叠加要有明确规则
4. 活动适用范围要可配置
5. 秒杀等高并发活动要单独处理

## 6. 核心代码

## 6.1 活动匹配和优惠计算核心实现

```java
@Service
public class ActivityServiceImpl implements ActivityService {

    private final ActivityMapper activityMapper;
    private final ActivityRuleMapper activityRuleMapper;

    public ActivityServiceImpl(
            ActivityMapper activityMapper,
            ActivityRuleMapper activityRuleMapper) {
        this.activityMapper = activityMapper;
        this.activityRuleMapper = activityRuleMapper;
    }

    @Override
    public BigDecimal calculateActivityDiscount(OrderCreateRequest request, BigDecimal totalAmount) {
        List<Activity> activities = activityMapper.selectActiveActivities(LocalDateTime.now());
        if (activities == null || activities.isEmpty()) {
            return BigDecimal.ZERO;
        }

        BigDecimal bestDiscount = BigDecimal.ZERO;
        for (Activity activity : activities) {
            ActivityRule rule = activityRuleMapper.selectByActivityId(activity.getId());
            BigDecimal discount = calculateByRule(rule, totalAmount);
            if (discount.compareTo(bestDiscount) > 0) {
                bestDiscount = discount;
            }
        }

        return bestDiscount;
    }

    private BigDecimal calculateByRule(ActivityRule rule, BigDecimal totalAmount) {
        if (rule == null) {
            return BigDecimal.ZERO;
        }
        if ("FULL_REDUCTION".equals(rule.getRuleType())
                && totalAmount.compareTo(rule.getThresholdAmount()) >= 0) {
            return rule.getDiscountAmount();
        }
        return BigDecimal.ZERO;
    }
}
```

这段代码先用一个最简单的“满减活动”说明问题。  
真正复杂的活动系统可以继续扩展：

- 多规则阶梯满减
- 商品级活动
- 用户等级活动
- 是否叠加计算

## 7. 活动和订单价格计算怎么衔接

工程上比较常见的顺序是：

1. 计算商品总价
2. 计算活动优惠
3. 再计算优惠券优惠
4. 得出最终实付金额

但活动和优惠券是否叠加，顺序是否固定，一定要提前定义业务规则。  
否则后面活动越多，价格计算越容易混乱。

## 8. 为什么活动系统容易越做越复杂

因为营销玩法天然很容易扩张。  
最开始可能只有：

- 满减

后面很快会演变成：

- 满减 + 优惠券
- 限时秒杀
- 新人专享
- 会员价
- 多活动互斥

所以工程上，一开始就应该尽量把活动“定义层”和“计算层”拆开，而不是把所有规则都写死在下单代码里。

## 9. 常见坑点

### 9.1 活动规则直接写在订单服务里

活动一多就会把订单代码拖垮。

### 9.2 多活动叠加规则不明确

最终实付金额会非常混乱。

### 9.3 只按时间判断活动，不判断适用范围

可能把本不该参与的商品也算进优惠。

## 10. 总结

活动系统的核心，不是“做一个促销页面”，而是把营销规则变成可配置、可匹配、可计算的业务能力。

一个成熟的活动系统至少应该做到：

- 活动定义和规则分离
- 订单价格计算可接入活动引擎
- 叠加和互斥规则明确
- 高并发玩法可进一步专项优化

这才是活动系统能长期演进的基础。
