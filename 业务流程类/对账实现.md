# 对账实现

## 1. 功能定义

对账要解决的问题是：

- 系统内部记录和外部渠道记录是否一致，如果不一致，差异在哪里

它通常出现在：

- 支付对账
- 退款对账
- 结算对账
- 渠道资金对账

对账是典型的“系统运营与财务可靠性”能力。  
很多业务平时看起来都正常，真正暴露问题往往是在对账阶段。

## 2. 为什么一定要对账

因为你的系统并不是唯一真相来源。  
很多关键资金和业务结果，还会存在于外部系统里，例如：

- 支付平台
- 银行
- 商家系统
- 结算渠道

如果双方记录不一致，就会带来严重问题：

- 用户已支付但订单未改成功
- 系统显示退款成功但渠道实际失败
- 平台账和渠道账对不上

所以对账本质上是“发现问题和补救问题”的核心机制。

## 3. 常见对账方式

### 3.1 支付对账

拿支付平台账单和本地支付单对比。

### 3.2 退款对账

拿退款平台账单和本地退款单对比。

### 3.3 结算对账

拿平台内部结算单和商家确认结果对比。

在 Java 后端实战里，最典型的就是“下载支付渠道账单后做差异比对”。

## 4. 典型流程

一个支付对账流程通常如下：

1. 定时下载第三方账单
2. 解析账单数据
3. 根据订单号或支付单号匹配本地记录
4. 比较金额、状态、时间等关键字段
5. 生成差异记录
6. 后续人工或系统补偿处理

## 5. 核心设计

对账实现时，建议至少明确：

1. 对账粒度是什么  
按订单、支付单、退款单还是结算单。

2. 对账关键字段有哪些  
通常是单号、金额、状态、时间。

3. 差异如何分类
4. 差异发现后如何处理

其中“差异分类”非常重要，不然对账做完也只是得到一堆看不懂的数据。

## 6. 常见差异类型

对账差异常见有几类：

1. 本地有，渠道无
2. 渠道有，本地无
3. 双方都有，但金额不一致
4. 双方都有，但状态不一致

例如：

```json
{
  "payNo": "PAY202606020001",
  "localStatus": "WAIT_PAY",
  "channelStatus": "SUCCESS",
  "diffType": "STATUS_DIFF"
}
```

## 7. 核心代码

## 7.1 对账核心实现

```java
@Service
public class PayReconcileServiceImpl implements PayReconcileService {

    private final PayOrderMapper payOrderMapper;
    private final ReconcileDiffMapper reconcileDiffMapper;

    public PayReconcileServiceImpl(
            PayOrderMapper payOrderMapper,
            ReconcileDiffMapper reconcileDiffMapper) {
        this.payOrderMapper = payOrderMapper;
        this.reconcileDiffMapper = reconcileDiffMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void reconcile(List<ChannelPayBillDTO> channelBills) {
        for (ChannelPayBillDTO bill : channelBills) {
            PayOrder payOrder = payOrderMapper.selectByPayNo(bill.getPayNo());

            if (payOrder == null) {
                saveDiff(bill.getPayNo(), "CHANNEL_HAS_LOCAL_NOT", null, bill.getStatus(), null, bill.getAmount());
                continue;
            }

            if (payOrder.getPayAmount().compareTo(bill.getAmount()) != 0) {
                saveDiff(
                        bill.getPayNo(),
                        "AMOUNT_DIFF",
                        payOrder.getStatus(),
                        bill.getStatus(),
                        payOrder.getPayAmount(),
                        bill.getAmount()
                );
                continue;
            }

            if (!Objects.equals(payOrder.getStatus(), bill.getStatus())) {
                saveDiff(
                        bill.getPayNo(),
                        "STATUS_DIFF",
                        payOrder.getStatus(),
                        bill.getStatus(),
                        payOrder.getPayAmount(),
                        bill.getAmount()
                );
            }
        }
    }

    private void saveDiff(
            String payNo,
            String diffType,
            String localStatus,
            String channelStatus,
            BigDecimal localAmount,
            BigDecimal channelAmount) {
        ReconcileDiff diff = new ReconcileDiff();
        diff.setBizNo(payNo);
        diff.setDiffType(diffType);
        diff.setLocalStatus(localStatus);
        diff.setChannelStatus(channelStatus);
        diff.setLocalAmount(localAmount);
        diff.setChannelAmount(channelAmount);
        diff.setCreateTime(LocalDateTime.now());
        reconcileDiffMapper.insert(diff);
    }
}
```

这段代码体现了对账实现里最关键的思路：

- 不一致不急着直接修
- 先把差异记录下来

## 8. 为什么对账不应该直接“边对边改”

因为差异的原因可能很复杂。  
例如一条状态不一致，可能是：

- 回调延迟
- 本地处理失败
- 渠道账单延迟生成

如果发现差异后立刻直接改本地数据，很可能会把问题掩盖得更深。

更稳的做法通常是：

1. 先记录差异
2. 再分类处理
3. 必要时人工复核

## 9. 对账后的补偿怎么理解

对账的目标不是“找出错账就结束”，而是后续还能做补偿。  
例如：

- 渠道成功、本地失败  
需要补单或补状态。

- 渠道失败、本地成功  
需要回滚本地状态或发起人工检查。

所以对账实际上常常和：

- 补单任务
- 差异工单
- 财务人工处理

一起出现。

## 10. 常见坑点

### 10.1 不做对账

系统短期看能跑，长期资金风险会越来越大。

### 10.2 对账只比单号，不比金额和状态

这样很多问题根本发现不了。

### 10.3 发现差异后直接改数据

容易把问题处理得更乱。

## 11. 总结

对账的核心，不是“比一比数据”，而是建立一套发现差异、分类差异、记录差异并为后续补偿提供依据的机制。

一个成熟的对账实现至少应该做到：

- 外部账单可导入或可拉取
- 本地数据可匹配
- 差异类型可分类
- 差异记录可追踪

这类能力在支付、退款、结算等资金相关流程里非常重要，也是业务流程类里最偏“稳态治理”的一项关键能力。
