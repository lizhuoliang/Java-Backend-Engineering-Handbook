# 结算实现

## 1. 功能定义

结算要解决的问题是：

- 一笔或一批业务完成后，系统如何把应收、应付、分账、佣金或收益结果计算并确认下来

结算常见于：

- 电商平台商家结算
- 外卖或服务平台分账
- 分销佣金结算
- 财务费用结转

它的重点不是“收款”，而是“把业务金额如何归属”算清楚。

## 2. 结算和支付的区别

这两个概念很容易混淆。

- 支付：用户把钱付进来
- 结算：系统把这笔钱如何分给谁算出来

例如一笔 100 元的订单：

- 用户付了 100 元，这是支付
- 平台抽成 10 元，商家结算 90 元，这是结算

所以结算更偏“账务归属”。

## 3. 典型数据结构

一个结算单通常至少包括：

```json
{
  "settlementNo": "SET202606020001",
  "bizType": "ORDER",
  "bizId": 90001,
  "merchantId": 3001,
  "orderAmount": 100.00,
  "platformFee": 10.00,
  "settlementAmount": 90.00,
  "status": "WAIT_SETTLE"
}
```

有些系统还会拆：

- 结算主单
- 结算明细单

尤其在批量结算场景中非常常见。

## 4. 典型流程

一个常见的结算流程如下：

1. 订单完成或满足结算条件
2. 系统根据规则计算结算金额
3. 创建结算单
4. 结算审核或自动确认
5. 更新为已结算
6. 后续进入打款或财务处理流程

## 5. 核心设计

结算实现时，建议至少明确：

1. 结算时机是什么
2. 结算规则如何计算
3. 结算单据是否需要独立建表
4. 一笔业务是否允许重复结算
5. 结算和打款是否分开

其中第 4 点尤其重要。  
很多结算问题本质上不是不会算，而是“重复结算了”。

## 6. 核心代码

## 6.1 创建结算单核心实现

```java
@Service
public class SettlementServiceImpl implements SettlementService {

    private final OrderMapper orderMapper;
    private final SettlementMapper settlementMapper;
    private final SettlementNoGenerator settlementNoGenerator;

    public SettlementServiceImpl(
            OrderMapper orderMapper,
            SettlementMapper settlementMapper,
            SettlementNoGenerator settlementNoGenerator) {
        this.orderMapper = orderMapper;
        this.settlementMapper = settlementMapper;
        this.settlementNoGenerator = settlementNoGenerator;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void createByOrder(Long orderId) {
        boolean exists = settlementMapper.existsByBiz("ORDER", orderId);
        if (exists) {
            return;
        }

        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException("订单不存在");
        }
        if (!"FINISHED".equals(order.getStatus())) {
            throw new BizException("订单未完成，不能结算");
        }

        BigDecimal orderAmount = order.getPayAmount();
        BigDecimal platformFee = orderAmount.multiply(new BigDecimal("0.10")).setScale(2, RoundingMode.HALF_UP);
        BigDecimal settlementAmount = orderAmount.subtract(platformFee);

        Settlement settlement = new Settlement();
        settlement.setSettlementNo(settlementNoGenerator.generate());
        settlement.setBizType("ORDER");
        settlement.setBizId(orderId);
        settlement.setMerchantId(order.getMerchantId());
        settlement.setOrderAmount(orderAmount);
        settlement.setPlatformFee(platformFee);
        settlement.setSettlementAmount(settlementAmount);
        settlement.setStatus("WAIT_SETTLE");
        settlement.setCreateTime(LocalDateTime.now());
        settlementMapper.insert(settlement);
    }
}
```

这段代码里最核心的思想是：

- 结算不是实时收款，而是后置账务计算
- 结算必须防重复

## 7. 为什么结算单要独立存在

因为很多后续动作都依赖它：

- 财务审核
- 商家对账
- 打款处理
- 结算报表统计

如果没有结算单，很多账务追踪都只能直接从订单表硬算，既不稳定也不方便审计。

## 8. 结算和打款为什么通常要分开

因为“算清楚该给谁多少钱”和“真的把钱打出去”并不是同一件事。  
现实里往往会经历：

1. 结算生成
2. 财务确认
3. 打款执行
4. 打款成功回执

所以很多正式系统里：

- `WAIT_SETTLE`
- `SETTLED`
- `PAYING`
- `PAID_OUT`

会是不同的状态阶段。

## 9. 常见坑点

### 9.1 直接拿订单金额当结算金额

忽略了平台服务费、佣金、退款等因素。

### 9.2 不做重复结算校验

会导致一笔业务被多次结算。

### 9.3 结算和打款混成一个动作

不利于账务治理和审批控制。

## 10. 总结

结算的核心，不是“改个状态说钱算完了”，而是围绕业务归属、费用规则和账务单据，把一笔业务最终该结给谁多少钱算清楚、记清楚。

一个成熟的结算实现至少应该做到：

- 独立结算单
- 明确结算时机
- 规则化金额计算
- 重复结算可防控

这样后面的财务处理和对账才有稳定基础。
