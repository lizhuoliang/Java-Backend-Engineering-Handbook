# 订单取消实现

## 1. 功能定义

订单取消要解决的问题是：

- 一笔尚未完成履约的订单，在满足取消条件时，如何安全地终止后续流程

很多系统里，“取消订单”看上去只是把状态改成 `CANCELLED`，但真实业务里通常还要同时考虑：

- 当前订单是否允许取消
- 谁发起取消
- 是否已经支付
- 是否需要释放库存
- 是否需要关闭支付单
- 是否需要记录取消原因

所以订单取消本质上是一个“带前置校验和补偿动作的状态终止流程”。

## 2. 哪些订单通常可以取消

这取决于业务规则，但最常见的可取消状态通常包括：

- `WAIT_PAY`
- `WAIT_CONFIRM`
- 某些待处理状态

而下面这些状态通常不允许直接取消：

- 已完成
- 已退款结束
- 已关闭
- 已发货且不支持取消

所以订单取消最核心的第一步不是改状态，而是“状态校验”。

## 3. 典型流程

一个典型的取消流程通常如下：

1. 用户或系统发起取消请求
2. 查询订单
3. 校验当前订单状态是否允许取消
4. 记录取消原因和取消人
5. 更新订单状态为 `CANCELLED`
6. 如果有预占库存，执行库存回滚
7. 如果有未支付支付单，执行支付关闭
8. 发送取消通知

## 4. 核心设计

订单取消设计时，我建议至少明确：

1. 取消动作不是删除订单
2. 取消原因要保留
3. 状态流转要严格校验
4. 和库存、支付等下游动作要联动
5. 尽量支持系统自动取消和用户主动取消两类来源

## 5.2 订单取消核心实现

```java
@Service
public class OrderCancelServiceImpl implements OrderCancelService {

    private final OrderMapper orderMapper;
    private final InventoryService inventoryService;
    private final PayOrderService payOrderService;

    public OrderCancelServiceImpl(
            OrderMapper orderMapper,
            InventoryService inventoryService,
            PayOrderService payOrderService) {
        this.orderMapper = orderMapper;
        this.inventoryService = inventoryService;
        this.payOrderService = payOrderService;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void cancel(Long orderId, String cancelReason, Long operatorId) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException("订单不存在");
        }

        if (!"WAIT_PAY".equals(order.getStatus()) && !"WAIT_CONFIRM".equals(order.getStatus())) {
            throw new BizException("当前订单状态不允许取消");
        }

        Order update = new Order();
        update.setId(orderId);
        update.setStatus("CANCELLED");
        update.setCancelReason(cancelReason);
        update.setCancelUserId(operatorId);
        update.setCancelTime(LocalDateTime.now());
        orderMapper.updateById(update);

        inventoryService.rollbackReservedStock(orderId);
        payOrderService.closeUnpaidPayOrder(orderId);
    }
}
```

这段代码表达的重点是：

- 先做状态校验
- 再改订单状态
- 最后联动库存和支付系统

## 6. 为什么取消订单不是删除订单

因为订单是一条非常重要的业务痕迹。  
哪怕最终没支付、没成交，它也往往仍然具备分析和追踪价值。

例如：

- 用户为什么取消
- 取消率是多少
- 哪些商品容易被取消

所以工程里几乎不会把“取消订单”做成物理删除，而是：

- 保留订单
- 改终止状态
- 记录取消原因

## 7. 自动取消订单怎么理解

很多系统都有“超时未支付自动取消”逻辑。  
例如：

- 下单 30 分钟未支付，自动关闭订单

这类动作通常不会由用户主动触发，而是由：

- 延迟消息
- 定时任务

来执行。

它和手动取消的主流程大体一致，但额外要注意：

- 执行时订单状态可能已经变化
- 所以一定要再次校验状态

## 8. 常见坑点

### 8.1 不校验状态直接取消

可能把已支付订单错误取消。

### 8.2 取消订单后不回滚库存

会导致库存长期被占住。

### 8.3 取消原因不记录

后续很难分析取消行为。

### 8.4 用户和系统取消逻辑完全写两套

容易出现规则不一致。

## 9. 总结

订单取消的核心，不是“把状态改掉”，而是围绕取消资格、状态流转、库存补偿和支付关闭，建立一个可终止、可追踪、可补偿的流程。

一个成熟的订单取消实现，至少应该做到：

- 严格校验可取消状态
- 记录取消来源和原因
- 联动库存与支付补偿
- 支持系统自动取消

这才是真正完整的取消逻辑。
