# 订单创建实现

## 1. 功能定义

订单创建要解决的问题是：

- 用户在选择商品、提交数量、确认价格后，系统如何生成一笔可追踪、可支付、可后续流转的业务订单

在很多系统里，订单创建看上去像是“往订单表插一条数据”，但真实项目里通常远不止如此。  
一次完整的订单创建，往往还会同时涉及：

- 商品信息校验
- 价格快照
- 库存预检查
- 优惠信息计算
- 运费计算
- 订单号生成
- 订单明细落库
- 初始状态设置

所以从工程角度看，订单创建本质上是一个“带规则计算和事务写入的业务聚合流程”。

## 2. 典型场景

订单创建并不只存在于电商系统里，很多业务都能抽象成订单：

- 电商下单
- 课程购买
- 会员开通
- 预约服务
- 采购申请

虽然业务细节不同，但核心骨架通常相似：

1. 确认买什么
2. 确认多少钱
3. 确认给谁
4. 生成一笔后续可支付或可处理的订单

## 3. 一笔订单通常包含什么

最小化理解，一笔订单通常至少有两层结构：

1. 订单主表
2. 订单明细表

例如：

```json
{
  "order": {
    "orderNo": "ORD202606020001",
    "userId": 101,
    "totalAmount": 199.00,
    "payAmount": 159.00,
    "status": "WAIT_PAY"
  },
  "items": [
    {
      "skuId": 1001,
      "skuName": "Java课程会员",
      "price": 199.00,
      "quantity": 1
    }
  ]
}
```

这里的重点是：

- 主表描述“这是一笔什么订单”
- 明细表描述“这笔订单里买了哪些东西”

## 4. 订单创建的典型流程

一个比较完整的下单流程通常如下：

1. 前端提交下单请求
2. 后端校验用户和商品信息
3. 查询商品最新价格和状态
4. 计算订单原价、优惠金额、应付金额
5. 生成订单号
6. 写订单主表
7. 写订单明细表
8. 设置订单初始状态为 `WAIT_PAY`
9. 返回订单号和应付金额

如果项目更完整，订单创建后还可能继续触发：

- 预占库存
- 发送待支付通知
- 创建支付单

## 5. 核心设计

订单创建实现时，建议先明确这些设计点：

1. 价格不能完全信任前端
2. 商品快照要落库
3. 订单号要全局唯一
4. 主表和明细表必须放同一事务
5. 初始状态要明确

其中第 1 点和第 2 点最容易被低估。

前端传来的价格只能作为参考，真正下单价格必须以后端实时查询的商品数据为准。  
同时，下单时的商品标题、价格、规格信息最好做快照落库，避免后续商品改名或改价后影响历史订单展示。

## 7.2 订单创建核心实现

```java
@Service
public class OrderServiceImpl implements OrderService {

    private final OrderMapper orderMapper;
    private final OrderItemMapper orderItemMapper;
    private final SkuService skuService;
    private final CouponService couponService;
    private final OrderNoGenerator orderNoGenerator;

    public OrderServiceImpl(
            OrderMapper orderMapper,
            OrderItemMapper orderItemMapper,
            SkuService skuService,
            CouponService couponService,
            OrderNoGenerator orderNoGenerator) {
        this.orderMapper = orderMapper;
        this.orderItemMapper = orderItemMapper;
        this.skuService = skuService;
        this.couponService = couponService;
        this.orderNoGenerator = orderNoGenerator;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public OrderCreateVO create(OrderCreateRequest request) {
        if (request.getItems() == null || request.getItems().isEmpty()) {
            throw new BizException("订单明细不能为空");
        }

        List<SkuSnapshot> skuSnapshots = skuService.loadOrderSkus(request.getItems());

        BigDecimal totalAmount = skuSnapshots.stream()
                .map(item -> item.getPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        BigDecimal discountAmount = couponService.calculateDiscount(
                request.getCouponId(),
                request.getUserId(),
                totalAmount
        );

        BigDecimal payAmount = totalAmount.subtract(discountAmount);
        if (payAmount.compareTo(BigDecimal.ZERO) < 0) {
            payAmount = BigDecimal.ZERO;
        }

        String orderNo = orderNoGenerator.generate();

        Order order = new Order();
        order.setOrderNo(orderNo);
        order.setUserId(request.getUserId());
        order.setTotalAmount(totalAmount);
        order.setDiscountAmount(discountAmount);
        order.setPayAmount(payAmount);
        order.setStatus("WAIT_PAY");
        order.setCreateTime(LocalDateTime.now());
        orderMapper.insert(order);

        for (SkuSnapshot snapshot : skuSnapshots) {
            OrderItem item = new OrderItem();
            item.setOrderId(order.getId());
            item.setSkuId(snapshot.getSkuId());
            item.setSkuName(snapshot.getSkuName());
            item.setPrice(snapshot.getPrice());
            item.setQuantity(snapshot.getQuantity());
            item.setAmount(snapshot.getPrice().multiply(BigDecimal.valueOf(snapshot.getQuantity())));
            orderItemMapper.insert(item);
        }

        OrderCreateVO vo = new OrderCreateVO();
        vo.setOrderId(order.getId());
        vo.setOrderNo(orderNo);
        vo.setPayAmount(payAmount);
        return vo;
    }
}
```

这段代码里的关键点有：

- 商品信息以后端查询为准
- 优惠金额由后端计算
- 订单主表和明细表在同一个事务里落库
- 初始状态明确为 `WAIT_PAY`

## 8. 为什么价格不能信任前端

因为前端传来的价格可以被篡改。  
如果直接使用前端价格创建订单，就会带来严重风险：

- 0 元下单
- 恶意改价
- 历史商品价格混乱

所以更稳的做法一定是：

1. 前端只传商品 ID 和数量
2. 后端实时查询商品价格
3. 后端统一计算订单金额

## 9. 为什么订单明细要做快照

因为商品数据会变化。

例如：

- 商品名称会改
- 商品价格会变
- 商品图片会更新

如果订单明细只存 `skuId`，不做快照，那么后续用户查看历史订单时，看到的就不一定是下单当时的真实内容。

所以订单明细通常会至少保留：

- 商品名称快照
- 购买价格快照
- 购买数量

## 10. 订单号怎么设计

订单号生成的目标通常有两个：

1. 全局唯一
2. 便于查询和展示

常见做法包括：

- 时间戳 + 随机数
- 日期前缀 + 序列号
- 雪花算法

如果系统规模较大，通常会倾向：

- 用雪花 ID 生成内部主键
- 用业务规则生成可展示订单号

## 11. 常见坑点

### 11.1 使用前端传入的金额下单

这是订单系统里最危险的错误之一。

### 11.2 主表和明细表不在同一事务里

可能出现主表有了，明细没了，或者反过来。

### 11.3 不校验商品状态

商品已下架、已禁售、库存不足时仍然创建订单，会导致后续流程异常。

### 11.4 订单创建时直接扣减真实库存

在很多系统里，下单时未必立刻扣真实库存，而可能先预占库存，支付后再确认扣减。

## 12. 总结

订单创建的核心，不是“生成一条订单记录”，而是围绕商品、价格、优惠、明细和状态，建立一笔可持续流转的业务订单。

一个更像正式项目的订单创建实现，至少应该做到：

- 金额后端计算
- 明细快照落库
- 主明细事务一致
- 状态初始化明确

这才是后面支付、取消、退款、对账等流程能够顺利衔接的基础。
