# 状态流转实现

## 1. 功能定义

状态流转要解决的问题是：

- 一个业务对象在生命周期里，允许从什么状态变成什么状态，以及这个变化应该由谁、在什么条件下触发

这是几乎所有业务流程类系统都会遇到的核心问题。  
例如：

- 订单：待支付 -> 已支付 -> 已完成
- 工单：待处理 -> 处理中 -> 已解决 -> 已关闭
- 审批单：待审批 -> 已通过 / 已驳回

所以“状态流转”其实是很多复杂业务流程的底层骨架。

## 2. 为什么状态流转不能随便改

如果系统里一个状态字段可以被任何地方随便更新，就很容易出现：

- 已取消订单又变成已支付
- 已完成工单又回到待处理
- 已驳回审批又被改成通过

这些问题本质上都来自：

- 没有清晰的状态机约束

所以工程上，状态流转一定要从“随便 update 一个字段”，提升到“按规则推进状态”。

## 3. 常见状态流转模型

最常见的一种建模方式是：

- 定义允许的状态集合
- 定义每个状态可流向哪些下一个状态

例如订单：

```json
{
  "WAIT_PAY": ["PAID", "CANCELLED"],
  "PAID": ["DELIVERED", "REFUNDING"],
  "DELIVERED": ["FINISHED"],
  "REFUNDING": ["REFUNDED"]
}
```

这本质上就是一个简化版状态机。

## 4. 核心设计

状态流转实现时，建议重点考虑：

1. 状态集合要固定
2. 流转规则要集中管理
3. 更新状态前必须校验当前状态
4. 状态变化最好记录日志

## 5. 核心代码

## 5.1 状态规则定义

```java
public class OrderStatusFlowRule {

    private static final Map<String, Set<String>> FLOW_MAP = Map.of(
            "WAIT_PAY", Set.of("PAID", "CANCELLED"),
            "PAID", Set.of("DELIVERED", "REFUNDING"),
            "DELIVERED", Set.of("FINISHED"),
            "REFUNDING", Set.of("REFUNDED")
    );

    public static boolean canTransfer(String from, String to) {
        return FLOW_MAP.getOrDefault(from, Collections.emptySet()).contains(to);
    }
}
```

## 5.2 状态流转核心实现

```java
@Service
public class OrderStatusServiceImpl implements OrderStatusService {

    private final OrderMapper orderMapper;
    private final OrderStatusLogMapper orderStatusLogMapper;

    public OrderStatusServiceImpl(
            OrderMapper orderMapper,
            OrderStatusLogMapper orderStatusLogMapper) {
        this.orderMapper = orderMapper;
        this.orderStatusLogMapper = orderStatusLogMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void transfer(Long orderId, String targetStatus, Long operatorUserId, String remark) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException("订单不存在");
        }

        String currentStatus = order.getStatus();
        if (!OrderStatusFlowRule.canTransfer(currentStatus, targetStatus)) {
            throw new BizException("不允许从 " + currentStatus + " 流转到 " + targetStatus);
        }

        Order update = new Order();
        update.setId(orderId);
        update.setStatus(targetStatus);
        orderMapper.updateById(update);

        OrderStatusLog log = new OrderStatusLog();
        log.setOrderId(orderId);
        log.setFromStatus(currentStatus);
        log.setToStatus(targetStatus);
        log.setOperatorUserId(operatorUserId);
        log.setRemark(remark);
        log.setCreateTime(LocalDateTime.now());
        orderStatusLogMapper.insert(log);
    }
}
```

这段代码体现了状态流转里最重要的 3 个动作：

- 查询当前状态
- 校验是否允许流转
- 留状态变更日志

## 6. 为什么状态流转要集中管理

如果你把状态判断逻辑散落在各个业务方法里，后期会出现几个问题：

1. 同一个业务对象不同地方规则不一致
2. 新增状态时改动范围很难控
3. 很难整体看清流程边界

所以更好的做法是：

- 把状态规则集中成一份显式配置或代码规则

哪怕是最简单的 `Map`，也比到处写 `if else` 更容易维护。

## 7. 为什么状态日志很重要

很多业务问题最终都要追问：

- 这个订单什么时候从待支付变成已支付的
- 是谁手工关闭的
- 为什么进入退款中状态

这些问题如果没有状态日志，就很难还原。

所以流程类系统里，状态日志往往和主表一样重要。

## 8. 常见坑点

### 8.1 状态直接随便改

这是流程系统最常见的失控来源。

### 8.2 流转时不校验当前状态

会导致非法跳转。

### 8.3 没有状态日志

后续排查和审计都很困难。

## 9. 总结

状态流转的核心，不是“改个字段”，而是把业务对象的生命周期显式化、规则化、可追踪化。

任何流程类系统，一旦把状态流转这一层设计清楚，后面的订单、审批、工单、任务系统都会稳很多。
