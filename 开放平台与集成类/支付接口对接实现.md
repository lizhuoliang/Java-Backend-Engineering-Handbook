# 支付接口对接实现

## 1. 功能定义

支付接口对接要解决的问题是：

- 你的系统如何和第三方支付平台协作，完成支付发起、支付确认、退款、账单与回调处理

和前面“订单支付实现”那篇不同，这一篇更偏：

- 开放平台与第三方支付渠道的集成层

也就是说，前面那篇讲的是：

- 订单系统内部怎么推进支付流程

这一篇讲的是：

- 系统怎么和微信支付、支付宝等外部平台打通

## 2. 为什么支付对接是高风险集成

因为支付不是普通的外部 API 调用。  
它的特殊性在于：

1. 涉及真实资金
2. 回调结果不能丢
3. 参数签名和验签要求严格
4. 一旦处理错，影响非常大

所以支付对接从来都不只是“发个 HTTP 请求”，而是一条：

- 参数构造
- 签名
- 调用
- 回调验签
- 幂等更新

的完整资金通道链路。

## 3. 支付接口对接通常包含哪些能力

最常见的能力包括：

1. 统一下单
2. 查询支付状态
3. 关闭支付单
4. 退款申请
5. 支付回调处理
6. 退款回调处理
7. 账单下载 / 对账

一个成熟的支付渠道接入层，通常会把这些能力封装成统一的 `PayChannelService`。

## 4. 核心设计

支付接口对接时，建议重点考虑：

1. 渠道参数如何封装
2. 签名如何统一处理
3. 回调如何验签
4. 回调如何做幂等
5. 渠道切换是否要抽象统一接口

这里最关键的一点是：

- 业务层不应该直接堆满支付渠道细节

否则以后换支付平台、接第二个支付平台、升级 SDK，成本都会很高。

## 5. 典型支付对接流程

以“统一下单”场景为例，通常流程如下：

1. 业务系统创建本地支付单
2. 构造第三方支付请求参数
3. 计算签名
4. 调用支付平台统一下单接口
5. 返回前端拉起支付需要的参数
6. 等待第三方回调
7. 回调验签并更新本地支付单状态

## 6. 核心代码

## 6.1 统一支付渠道接口

```java
public interface PayChannelService {

    PayCreateVO createPay(PayOrder payOrder);

    void handlePayCallback(Map<String, String> callbackParams);

    void refund(RefundOrder refundOrder);
}
```

这个接口的价值在于：

- 把支付平台细节和业务层分开

## 6.2 支付发起核心实现示例

下面用一个简化版“支付宝下单”思路举例。

```java
@Service
public class AlipayChannelServiceImpl implements PayChannelService {

    private final AlipayClient alipayClient;

    public AlipayChannelServiceImpl(AlipayClient alipayClient) {
        this.alipayClient = alipayClient;
    }

    @Override
    public PayCreateVO createPay(PayOrder payOrder) {
        AlipayTradePagePayRequest request = new AlipayTradePagePayRequest();
        request.setReturnUrl("https://example.com/pay/return");
        request.setNotifyUrl("https://example.com/pay/callback");

        JSONObject biz = new JSONObject();
        biz.put("out_trade_no", payOrder.getPayNo());
        biz.put("total_amount", payOrder.getPayAmount());
        biz.put("subject", "订单支付");
        biz.put("product_code", "FAST_INSTANT_TRADE_PAY");
        request.setBizContent(biz.toJSONString());

        try {
            String form = alipayClient.pageExecute(request).getBody();
            PayCreateVO vo = new PayCreateVO();
            vo.setPayNo(payOrder.getPayNo());
            vo.setPayForm(form);
            return vo;
        } catch (Exception ex) {
            throw new BizException("支付下单失败");
        }
    }

    @Override
    public void handlePayCallback(Map<String, String> callbackParams) {
        // 见下文
    }

    @Override
    public void refund(RefundOrder refundOrder) {
        // 见退款部分
    }
}
```

这段代码里最重要的不是 SDK 细节，而是：

- 本地支付单存在
- 支付参数由后端构造
- 回调地址由后端掌控

## 6.3 回调验签与处理示例

```java
@Override
public void handlePayCallback(Map<String, String> callbackParams) {
    try {
        boolean verify = AlipaySignature.rsaCheckV1(
                callbackParams,
                alipayPublicKey,
                "UTF-8",
                "RSA2"
        );
        if (!verify) {
            throw new BizException("支付回调验签失败");
        }

        String payNo = callbackParams.get("out_trade_no");
        String tradeStatus = callbackParams.get("trade_status");
        String totalAmount = callbackParams.get("total_amount");

        if (!"TRADE_SUCCESS".equals(tradeStatus)) {
            return;
        }

        // 后续交给本地支付回调服务：
        // 1. 查支付单
        // 2. 金额校验
        // 3. 幂等更新
        // 4. 推进订单状态
    } catch (Exception ex) {
        throw new BizException("回调处理失败");
    }
}
```

这段代码体现了支付回调处理最关键的第一步：

- 先验签，再谈业务

## 7. 为什么支付回调一定要先验签

因为回调接口暴露在公网，任何人理论上都能访问它。  
如果你不验签，就无法确认：

- 这份回调是不是支付平台真的发来的

那就可能出现非常严重的问题，例如：

- 攻击者伪造支付成功回调

所以支付回调里第一优先级永远是：

- 验签

## 8. 为什么支付渠道对接层要和业务层分开

因为它们关注点不同。

### 渠道层关注

- 参数构造
- 签名
- 调 SDK
- 渠道返回值解析

### 业务层关注

- 支付单状态推进
- 订单状态推进
- 库存、积分、通知等后续动作

如果把两者堆在一起，后面：

- 切换渠道
- 增加第二支付渠道
- 处理回调问题

都会非常麻烦。

## 9. 支付对接最常见的几个坑

### 9.1 只看同步下单返回，不重视回调

支付最终结果通常要以回调为准。

### 9.2 回调不验签

这是高风险错误。

### 9.3 本地支付单和渠道单不分离

后续对账和问题追踪会很困难。

### 9.4 业务层直接写渠道 SDK 代码

后面扩展和维护成本会很高。

## 10. 总结

支付接口对接的核心，不是“调用了某个支付 SDK”，而是围绕：

- 本地支付单
- 渠道请求参数
- 签名与验签
- 回调幂等处理
- 渠道能力抽象

建立一套稳定、可审计、可扩展的支付集成层。

一个成熟的支付接口对接实现至少应该做到：

- 支付渠道统一封装
- 下单和回调分层处理
- 回调先验签、再校验、再推进业务
- 本地单据与渠道单据清晰分离

这才是真正适合生产环境的支付集成架构。
