# 地图服务对接实现

## 1. 功能定义

地图服务对接要解决的问题是：

- 系统如何借助第三方地图平台完成定位、地理编码、距离计算、路线规划、逆地理解析等能力

最常见的地图平台包括：

- 高德地图
- 百度地图
- 腾讯地图
- Google Maps

从工程角度看，地图服务对接并不是“在前端嵌一个地图组件”那么简单。  
后端通常也需要处理很多地图能力，例如：

- 根据地址换经纬度
- 根据经纬度反查地址
- 计算两点距离
- 计算配送范围

## 2. 地图服务最常见的业务场景

常见场景包括：

1. 地址解析  
把用户填写的地址解析成经纬度。

2. 附近门店查询
3. 配送距离计算
4. 区域围栏判断
5. 路线规划

所以地图服务通常既会出现在：

- 前端交互层

也会出现在：

- 后端业务决策层

## 3. 核心设计

地图服务对接时，建议重点考虑：

1. 哪些能力放前端，哪些放后端
2. 第三方 key 如何管理
3. 是否需要缓存结果
4. 调用失败如何降级
5. 地址和坐标是否要落本地数据库

这里最关键的一点通常是：

- 不是每次业务都实时调用第三方地图接口

很多结果完全可以：

- 解析一次后入库
- 后续优先复用

## 4. 典型流程

以“地址转经纬度”举例，一个典型流程如下：

1. 用户提交地址
2. 后端调用地图平台地理编码接口
3. 拿到经纬度
4. 存入本地业务表
5. 后续配送、门店范围判断优先用本地坐标

## 5. 核心代码

## 5.1 地图服务统一接口

```java
public interface MapService {

    GeoPoint geocode(String address);

    String reverseGeocode(Double lng, Double lat);

    Integer distanceMeter(Double fromLng, Double fromLat, Double toLng, Double toLat);
}
```

这个接口的价值在于：

- 地图平台细节被统一封装

## 5.2 地理编码核心实现

下面用高德风格接口举例。

```java
@Service
public class AmapServiceImpl implements MapService {

    private final RestTemplate restTemplate;

    @Value("${map.amap.key}")
    private String amapKey;

    public AmapServiceImpl(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @Override
    public GeoPoint geocode(String address) {
        String url = "https://restapi.amap.com/v3/geocode/geo?address={address}&key={key}";
        Map response = restTemplate.getForObject(url, Map.class, address, amapKey);

        if (response == null || !"1".equals(String.valueOf(response.get("status")))) {
            throw new BizException("地理编码失败");
        }

        List<Map<String, Object>> geocodes = (List<Map<String, Object>>) response.get("geocodes");
        if (geocodes == null || geocodes.isEmpty()) {
            throw new BizException("地址解析不到坐标");
        }

        String location = String.valueOf(geocodes.get(0).get("location"));
        String[] arr = location.split(",");
        GeoPoint point = new GeoPoint();
        point.setLng(Double.valueOf(arr[0]));
        point.setLat(Double.valueOf(arr[1]));
        return point;
    }

    @Override
    public String reverseGeocode(Double lng, Double lat) {
        return null;
    }

    @Override
    public Integer distanceMeter(Double fromLng, Double fromLat, Double toLng, Double toLat) {
        return null;
    }
}
```

这段代码里最重要的点不是某个地图平台 URL，而是：

- 外部响应不能直接信任
- 需要做状态校验和空结果校验

## 6. 为什么地图结果最好尽量落本地

因为第三方地图调用通常有这些特点：

1. 有调用成本或限额
2. 网络不稳定
3. 地址相同结果往往可复用

所以很多场景更合理的做法是：

1. 第一次解析调用第三方
2. 结果存本地
3. 后续直接复用

例如用户收货地址一旦解析过，通常不需要每次下单都重新调地图接口。

## 7. 距离计算为什么常常是后端逻辑

因为很多业务规则依赖它，例如：

- 超过 5 公里不配送
- 最近门店优先匹配
- 运费按距离分段计费

这些都属于业务决策，而不只是地图展示。  
所以“距离计算”不应该只停留在前端页面。

## 8. 常见坑点

### 8.1 所有请求都实时调第三方地图接口

会带来成本和稳定性问题。

### 8.2 地址解析结果不做容错

地址格式不规范时很容易失败。

### 8.3 地图 key 硬编码到代码里

后期管理和安全都很差。

### 8.4 前端和后端各算一套距离规则

容易出现不一致。

## 9. 总结

地图服务对接的核心，不是“能调通某个地图 API”，而是把地图平台能力稳定地封装成：

- 可调用
- 可缓存
- 可复用
- 可参与业务决策

的系统能力。

一个成熟的地图服务对接实现至少应该做到：

- 地图平台统一封装
- 关键结果尽量本地沉淀
- 调用失败可感知
- 地图能力和业务规则清晰衔接

这才是真正有工程价值的地图集成方式。
