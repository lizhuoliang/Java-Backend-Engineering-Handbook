# 短信平台对接实现

## 1. 功能定义

短信平台对接要解决的问题是：

- 系统如何调用第三方短信服务，把验证码或通知短信稳定地发送给用户

这一篇和前面“消息与通知类”里的“短信发送实现”不同。  
前面那篇更偏：

- 你的业务系统怎么组织短信能力

这一篇更偏：

- 你的系统怎么和阿里云短信、腾讯云短信等外部平台打通

也就是说，前面讲的是业务通知层，这一篇讲的是外部通道集成层。

## 2. 为什么短信平台对接不是简单的 HTTP 调用

因为短信平台通常会涉及：

1. 平台鉴权
2. 模板管理
3. 签名管理
4. 发送状态追踪
5. 调用限流与成本控制

所以真正的短信平台对接，核心不只是：

- 调通接口

而是：

- 把通道能力稳定封装成系统内部可复用的能力

## 3. 一个成熟的短信平台集成通常包括什么

最常见的能力包括：

1. 单条短信发送
2. 模板参数发送
3. 状态回执查询
4. 发送日志记录
5. 通道切换或扩展能力

如果系统规模更大，往往还会继续做：

6. 多供应商通道
7. 失败自动切换
8. 成本和成功率监控

## 4. 核心设计

短信平台对接时，建议重点考虑：

1. 平台 SDK 是否统一封装
2. 模板 code 和业务场景是否映射清晰
3. 通道失败后怎么处理
4. 日志是否记录完整
5. 平台密钥如何安全管理

最重要的一点通常是：

- 业务层不要直接依赖具体短信平台 SDK

否则后面换平台、增加备用通道会非常难受。

## 5. 典型流程

一个典型的短信平台发送流程如下：

1. 业务系统生成短信发送请求
2. 组装模板参数
3. 调用短信通道服务
4. 短信通道服务调用平台 SDK / API
5. 平台返回发送结果
6. 本地记录发送日志

## 6. 核心代码

## 6.1 短信平台统一发送接口

```java
public interface SmsPlatformClient {

    SmsSendResult send(String phone, String templateCode, Map<String, String> params);
}
```

这层非常关键，因为它决定了：

- 平台实现和业务逻辑是否解耦

## 6.2 平台调用核心实现示例

下面用一个简化版阿里云风格示意。

```java
@Service
public class AliyunSmsPlatformClientImpl implements SmsPlatformClient {

    private final IAcsClient acsClient;

    @Value("${sms.aliyun.sign-name}")
    private String signName;

    public AliyunSmsPlatformClientImpl(IAcsClient acsClient) {
        this.acsClient = acsClient;
    }

    @Override
    public SmsSendResult send(String phone, String templateCode, Map<String, String> params) {
        CommonRequest request = new CommonRequest();
        request.setSysMethod(MethodType.POST);
        request.setSysDomain("dysmsapi.aliyuncs.com");
        request.setSysVersion("2017-05-25");
        request.setSysAction("SendSms");
        request.putQueryParameter("PhoneNumbers", phone);
        request.putQueryParameter("SignName", signName);
        request.putQueryParameter("TemplateCode", templateCode);
        request.putQueryParameter("TemplateParam", JSON.toJSONString(params));

        try {
            CommonResponse response = acsClient.getCommonResponse(request);
            SmsSendResult result = new SmsSendResult();
            result.setSuccess(response.getHttpStatus() == 200);
            result.setRawResponse(response.getData());
            return result;
        } catch (Exception ex) {
            throw new BizException("短信平台调用失败");
        }
    }
}
```

这段代码里最重要的不是具体 SDK 类名，而是：

- 业务参数被统一翻译成平台模板参数
- 平台结果再被统一翻译回本地结果对象

## 7. 为什么短信模板和业务场景最好解耦

很多系统一开始会直接在业务里写：

- `"SMS_123456"`

这很快就会带来维护问题。  
更稳的做法通常是：

- 业务场景 code -> 平台模板 code

例如：

```json
{
  "LOGIN_CODE": "SMS_123456",
  "RESET_PASSWORD": "SMS_654321"
}
```

这样以后模板迁移、平台切换、模板升级时，业务代码不需要跟着大改。

## 8. 平台失败了怎么办

短信平台调用失败很常见，例如：

- 超时
- 平台限流
- 模板审核异常
- 账户余额不足

所以一个成熟的对接层通常至少要做：

1. 失败日志记录
2. 错误码映射
3. 重试或补偿策略
4. 必要时备用通道切换

## 9. 常见坑点

### 9.1 业务代码直接调平台 SDK

后期平台切换成本很高。

### 9.2 模板 code 散落在业务代码里

非常难统一治理。

### 9.3 平台调用结果不落日志

发送失败后很难排查。

### 9.4 accessKey / secret 明文硬编码

存在明显安全风险。

## 10. 总结

短信平台对接的核心，不是“某个平台短信发通了”，而是把第三方短信能力封装成：

- 可复用
- 可替换
- 可追踪
- 可治理

的系统通道层。

一个成熟的短信平台对接实现至少应该做到：

- 平台 SDK 统一封装
- 模板和业务场景解耦
- 发送结果可记录
- 密钥和配置可安全管理

这才是真正适合长期演进的短信平台集成方式。
