# 死信队列处理实现

## 1. 功能定义

死信队列处理要解决的问题是：

- 某条消息多次消费失败后，不能无限重试，也不能悄悄丢掉，那应该放到哪里

答案通常就是：

- 放到死信队列，等待后续排查或人工处理

所以死信队列本质上是“失败消息的最终缓冲区”。

## 2. 什么是死信

在消息系统里，一条消息之所以会成为死信，常见有几种原因：

1. 被消费者拒绝且不重新入队
2. 超过最大重试次数
3. 超过生存时间仍未被消费

对于通知系统来说，最常见的死信场景通常是：

- 消费失败次数过多
- 数据本身有问题导致始终无法成功

## 3. 为什么要有死信队列

因为“失败消息”不能简单粗暴地处理成两种极端：

1. 无限重试  
会不断浪费资源。

2. 直接丢弃  
会悄悄丢业务通知，风险很大。

死信队列提供的是第三种思路：

- 先从主消费链路里摘出去
- 保留问题现场
- 后续再分析或人工补偿

## 4. 典型流程

1. 正常消息进入业务队列
2. 消费失败
3. 达到最大重试次数
4. 消息进入死信队列
5. 运维或系统后台查看死信消息
6. 决定重新投递、人工处理或废弃

## 5. 典型死信数据示例

```json
{
  "messageType": "MAIL_NOTIFY",
  "bizId": 90001,
  "payload": "{...}",
  "retryCount": 5,
  "status": "DEAD",
  "failReason": "SMTP server timeout"
}
```

## 6. 核心设计

死信队列处理设计时，最关键的点有：

1. 死信必须可追踪
2. 死信不能只存 MQ 里没人看
3. 要能重新投递
4. 要能区分技术故障和业务脏数据

这意味着死信处理通常不只是 MQ 配置，还应该配套：

- 死信记录查询
- 死信人工处理后台
- 死信重投能力

## 7. 核心代码

## 7.1 消息超过最大重试次数后转死信

下面延续上一篇“失败表重试”的思路。

```java
@Service
public class MessageRetryJob {

    private final MessageRetryMapper messageRetryMapper;
    private final DeadLetterMessageMapper deadLetterMessageMapper;
    private final SmsSender smsSender;

    public MessageRetryJob(
            MessageRetryMapper messageRetryMapper,
            DeadLetterMessageMapper deadLetterMessageMapper,
            SmsSender smsSender) {
        this.messageRetryMapper = messageRetryMapper;
        this.deadLetterMessageMapper = deadLetterMessageMapper;
        this.smsSender = smsSender;
    }

    @Scheduled(fixedDelay = 60000)
    public void retry() {
        List<MessageRetry> list = messageRetryMapper.selectWaitRetryList(LocalDateTime.now());
        for (MessageRetry item : list) {
            try {
                SmsNotifyEvent event = JSON.parseObject(item.getPayload(), SmsNotifyEvent.class);
                smsSender.send(event.getPhone(), event.getTemplateCode(), event.getParams());

                MessageRetry update = new MessageRetry();
                update.setId(item.getId());
                update.setStatus("SUCCESS");
                update.setRetryCount(item.getRetryCount() + 1);
                messageRetryMapper.updateById(update);
            } catch (Exception ex) {
                int retryCount = item.getRetryCount() + 1;
                if (retryCount >= item.getMaxRetryCount()) {
                    moveToDeadLetter(item, retryCount, ex.getMessage());
                } else {
                    MessageRetry update = new MessageRetry();
                    update.setId(item.getId());
                    update.setRetryCount(retryCount);
                    update.setStatus("WAIT_RETRY");
                    update.setFailReason(ex.getMessage());
                    update.setNextRetryTime(LocalDateTime.now().plusMinutes(5));
                    messageRetryMapper.updateById(update);
                }
            }
        }
    }

    private void moveToDeadLetter(MessageRetry item, int retryCount, String failReason) {
        DeadLetterMessage dead = new DeadLetterMessage();
        dead.setMessageType(item.getMessageType());
        dead.setBizId(item.getBizId());
        dead.setPayload(item.getPayload());
        dead.setRetryCount(retryCount);
        dead.setFailReason(failReason);
        dead.setCreateTime(LocalDateTime.now());
        deadLetterMessageMapper.insert(dead);

        MessageRetry update = new MessageRetry();
        update.setId(item.getId());
        update.setStatus("DEAD");
        update.setRetryCount(retryCount);
        update.setFailReason(failReason);
        messageRetryMapper.updateById(update);
    }
}
```

这段代码的重点是：

- 到了最大重试次数，不再继续尝试
- 把失败消息转移到死信表

## 7.2 死信重投核心实现

```java
@Service
public class DeadLetterServiceImpl implements DeadLetterService {

    private final DeadLetterMessageMapper deadLetterMessageMapper;
    private final NotifyEventPublisher notifyEventPublisher;

    public DeadLetterServiceImpl(
            DeadLetterMessageMapper deadLetterMessageMapper,
            NotifyEventPublisher notifyEventPublisher) {
        this.deadLetterMessageMapper = deadLetterMessageMapper;
        this.notifyEventPublisher = notifyEventPublisher;
    }

    @Override
    public void requeue(Long deadLetterId) {
        DeadLetterMessage message = deadLetterMessageMapper.selectById(deadLetterId);
        if (message == null) {
            throw new BizException("死信记录不存在");
        }

        if (!"ORDER_PAY_SUCCESS".equals(message.getMessageType())) {
            throw new BizException("当前消息类型暂不支持重投");
        }

        OrderPaySuccessNotifyEvent event = JSON.parseObject(
                message.getPayload(),
                OrderPaySuccessNotifyEvent.class
        );

        notifyEventPublisher.publishOrderPaySuccess(event);
    }
}
```

死信重投并不意味着“盲目重新丢回去”，而是应该在确认问题已修复后再执行。

## 8. 为什么死信最好能人工介入

因为很多死信并不是纯技术问题，而是业务数据问题，例如：

- 手机号本身非法
- 邮件地址失效
- 模板参数缺失

这类问题就算再重试十次，也不会成功。  
所以死信处理通常需要：

1. 查看失败原因
2. 定位业务数据问题
3. 修复后再选择是否重投

## 9. 和 MQ 自带死信队列的关系

很多消息中间件本身就支持死信队列，这很好。  
但从工程治理角度看，还建议在应用层补一层“可查询、可审计、可重投”的死信记录能力。

因为只依赖 MQ 自带死信能力时，业务方通常不容易直接排查。

所以比较完整的做法是：

- MQ 层负责路由和存放死信
- 应用层负责死信管理和业务修复流程

## 10. 常见坑点

### 10.1 最大重试后直接丢弃

会造成消息静默丢失。

### 10.2 死信没有记录失败原因

后续几乎无法排查。

### 10.3 死信可以被任何人随意重投

这会带来较大业务风险，通常应该限制权限。

## 11. 总结

死信队列处理的核心，不是“把失败消息换个地方放”，而是给多次失败的消息提供一个可追踪、可分析、可重投的最终落点。

它是消息可靠性体系里的最后一道防线，也是通知系统从“能跑”走向“可治理”的关键一步。
