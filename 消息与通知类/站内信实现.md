# 站内信实现

## 1. 功能定义

站内信要解决的问题是：

- 系统内部给用户发送一条可查看、可追踪、可管理的消息

它通常不像短信、邮件那样依赖外部渠道，而是系统自身提供一套消息投递和查看能力。

常见场景包括：

- 审批结果通知
- 系统公告通知
- 工单处理提醒
- 订单状态变化提醒
- 安全告警提醒

如果从工程角度看，站内信本质上是一套“消息生产、消息存储、消息消费展示”的内部通知系统。

## 2. 站内信和其他通知方式的区别

站内信最大的特点是：

- 消息内容完全由系统自己掌控
- 不依赖第三方通道
- 可持久化
- 可查询历史
- 可做已读未读管理

相比之下：

- 短信更适合强触达
- 邮件更适合正式通知和长内容
- 推送更适合移动端实时提醒

所以站内信通常是通知体系里的基础层。

## 3. 典型数据结构

一个最基础的站内信模型，通常至少包含这些字段：

```json
{
  "id": 1,
  "title": "审批通过通知",
  "content": "你的请假申请已通过审批",
  "receiverUserId": 101,
  "status": 0,
  "bizType": "leave_apply",
  "bizId": 9001,
  "sendTime": "2026-06-02 10:00:00"
}
```

这里通常约定：

- `status = 0` 表示未读
- `status = 1` 表示已读

如果系统更复杂，还会加上：

- 发送人
- 跳转链接
- 消息模板编号
- 优先级

## 4. 典型流程

一个完整的站内信流程通常如下：

1. 业务事件发生  
例如审批通过、订单支付成功、任务分配完成。

2. 系统组装消息内容
3. 写入站内信表
4. 用户进入消息中心查看
5. 用户点击后更新为已读

如果做得更工程化，通常不会在业务主流程里直接写消息表，而是通过事件或消息队列异步投递。

## 5. 核心设计

我建议站内信至少按下面几个点来设计：

1. 消息和业务解耦  
业务系统只负责“发通知请求”，不直接关心消息表结构。

2. 支持未读/已读状态
3. 支持按用户维度查询
4. 支持与业务对象关联  
例如点击消息可以跳到订单详情、审批详情。

5. 内容生成和发送存储分层  
消息模板、消息内容、消息投递尽量分开。

    private String title;

        return bizId;

## 6.2 站内信发送核心实现

```java
@Service
public class InboxMessageServiceImpl implements InboxMessageService {

    private final InboxMessageMapper inboxMessageMapper;

    public InboxMessageServiceImpl(InboxMessageMapper inboxMessageMapper) {
        this.inboxMessageMapper = inboxMessageMapper;
    }

    @Override
    public void send(InboxMessageSendRequest request) {
        if (request.getReceiverUserId() == null) {
            throw new BizException("接收用户不能为空");
        }

        InboxMessage message = new InboxMessage();
        message.setReceiverUserId(request.getReceiverUserId());
        message.setTitle(request.getTitle());
        message.setContent(request.getContent());
        message.setBizType(request.getBizType());
        message.setBizId(request.getBizId());
        message.setStatus(0);
        message.setSendTime(LocalDateTime.now());
        inboxMessageMapper.insert(message);
    }
}
```

这段代码不复杂，但它表达了一个很重要的工程思想：

- 业务方只需要调用 `send`
- 站内信系统自己负责落表

## 6.3 查询当前用户站内信列表

```java
@RestController
@RequestMapping("/inbox")
public class InboxMessageController {

    private final InboxMessageQueryService inboxMessageQueryService;

    public InboxMessageController(InboxMessageQueryService inboxMessageQueryService) {
        this.inboxMessageQueryService = inboxMessageQueryService;
    }

    @GetMapping("/page")
    public Result<PageResult<InboxMessageVO>> page(PageRequest request) {
        Long userId = UserContext.get().getUserId();
        return Result.success(inboxMessageQueryService.pageByUserId(userId, request));
    }
}
```

## 6.4 标记已读核心实现

```java
@Service
public class InboxMessageReadServiceImpl implements InboxMessageReadService {

    private final InboxMessageMapper inboxMessageMapper;

    public InboxMessageReadServiceImpl(InboxMessageMapper inboxMessageMapper) {
        this.inboxMessageMapper = inboxMessageMapper;
    }

    @Override
    public void read(Long userId, Long messageId) {
        InboxMessage message = inboxMessageMapper.selectById(messageId);
        if (message == null || !Objects.equals(message.getReceiverUserId(), userId)) {
            throw new BizException("消息不存在");
        }

        if (message.getStatus() == 1) {
            return;
        }

        InboxMessage update = new InboxMessage();
        update.setId(messageId);
        update.setStatus(1);
        update.setReadTime(LocalDateTime.now());
        inboxMessageMapper.updateById(update);
    }
}
```

这里把“已读”做成幂等处理是很合理的：

- 已经读过了，再点一次也不用报错

## 7. 为什么站内信适合做成独立模块

因为很多业务都会发通知：

- 审批系统
- 订单系统
- 工单系统
- 风控系统

如果每个业务都自己建一张“通知表”，最后会非常混乱。

所以更成熟的做法是：

- 建统一站内信模块
- 各业务只负责发消息请求

## 8. 站内信和消息模板的关系

很多系统里的站内信不是完全手写内容，而是走模板，例如：

```json
{
  "templateCode": "approve_pass",
  "params": {
    "userName": "张三",
    "orderNo": "ORD20260602001"
  }
}
```

然后由模板系统渲染出最终标题和正文。  
这样后续维护文案会方便很多。

## 9. 常见坑点

### 9.1 业务里直接硬编码站内信落表

这样消息能力很难复用，也不利于统一治理。

### 9.2 不做已读状态

用户无法区分哪些消息处理过，体验会很差。

### 9.3 没有和业务对象建立关联

用户看到消息后，无法跳转到对应详情页。

## 10. 总结

站内信实现的核心，是建立一套统一的系统内通知能力：  
业务侧发消息请求，消息中心完成存储、查询、已读未读管理，并且能和业务对象关联。

这套能力虽然看起来简单，但在工程化系统里非常基础，而且经常是后续短信、邮件、推送等统一通知平台的第一步。
