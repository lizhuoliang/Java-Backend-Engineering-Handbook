# 消息重试实现

## 1. 功能定义

消息重试要解决的问题是：

- 某条消息第一次消费失败后，系统如何再次尝试处理

这在消息通知体系里非常常见，因为很多失败都是“暂时性的”：

- 短信平台短时异常
- 邮件服务器超时
- 下游接口网络波动
- 数据库瞬时锁冲突

如果一失败就直接丢掉，系统通知可靠性会很差。  
所以工程里通常都要设计消息重试机制。

## 2. 重试的本质

重试并不是“无脑再来一次”，而是：

- 在可控次数内，对临时失败进行补偿尝试

所以重试设计最关键的不是循环，而是：

1. 哪些异常值得重试
2. 最多重试几次
3. 每次间隔多久
4. 超过次数后怎么办

## 3. 常见重试方式

### 3.1 消费者内部立即重试

适合非常轻量的场景，但不适合复杂通知系统。

### 3.2 借助 MQ 自带重投

例如消费失败后重新入队。

### 3.3 落失败表 + 定时补偿任务

很多正式项目很喜欢这种方式，因为更可控，也更容易追踪。

本文重点讲第三种，因为它更适合工程化思维。

## 4. 典型数据结构

失败重试表通常最少要有这些字段：

```json
{
  "id": 1,
  "messageType": "SMS_NOTIFY",
  "bizId": 90001,
  "payload": "{...}",
  "retryCount": 1,
  "maxRetryCount": 5,
  "status": "WAIT_RETRY",
  "nextRetryTime": "2026-06-02 12:10:00"
}
```

这些字段很关键，因为它们决定了：

- 要重试什么
- 已经试过几次
- 下一次什么时候再试

## 5. 核心代码

## 5.1 消费失败时写入重试记录

```java
@Service
public class SmsNotifyConsumer {

    private final SmsSender smsSender;
    private final MessageRetryMapper messageRetryMapper;

    public SmsNotifyConsumer(SmsSender smsSender, MessageRetryMapper messageRetryMapper) {
        this.smsSender = smsSender;
        this.messageRetryMapper = messageRetryMapper;
    }

    public void consume(SmsNotifyEvent event) {
        try {
            smsSender.send(event.getPhone(), event.getTemplateCode(), event.getParams());
        } catch (Exception ex) {
            MessageRetry record = new MessageRetry();
            record.setMessageType("SMS_NOTIFY");
            record.setBizId(event.getBizId());
            record.setPayload(JSON.toJSONString(event));
            record.setRetryCount(0);
            record.setMaxRetryCount(5);
            record.setStatus("WAIT_RETRY");
            record.setNextRetryTime(LocalDateTime.now().plusMinutes(5));
            record.setFailReason(ex.getMessage());
            messageRetryMapper.insert(record);
            throw ex;
        }
    }
}
```

这段代码的重点不是“插一张表”，而是给失败消息留下后续补偿入口。

## 5.2 定时重试任务核心实现

```java
@Service
public class MessageRetryJob {

    private final MessageRetryMapper messageRetryMapper;
    private final SmsSender smsSender;

    public MessageRetryJob(MessageRetryMapper messageRetryMapper, SmsSender smsSender) {
        this.messageRetryMapper = messageRetryMapper;
        this.smsSender = smsSender;
    }

    @Scheduled(fixedDelay = 60000)
    public void retry() {
        List<MessageRetry> list = messageRetryMapper.selectWaitRetryList(LocalDateTime.now());
        for (MessageRetry item : list) {
            try {
                SmsNotifyEvent event = JSON.parseObject(item.getPayload(), SmsNotifyEvent.class);
                smsSender.send(event.getPhone(), event.getTemplateCode(), event.getParams());

                MessageRetry update = new MessageRetry();
                update.setId(item.getId());
                update.setStatus("SUCCESS");
                update.setRetryCount(item.getRetryCount() + 1);
                messageRetryMapper.updateById(update);
            } catch (Exception ex) {
                int retryCount = item.getRetryCount() + 1;
                MessageRetry update = new MessageRetry();
                update.setId(item.getId());
                update.setRetryCount(retryCount);
                update.setFailReason(ex.getMessage());

                if (retryCount >= item.getMaxRetryCount()) {
                    update.setStatus("FAIL");
                } else {
                    update.setStatus("WAIT_RETRY");
                    update.setNextRetryTime(LocalDateTime.now().plusMinutes(5));
                }

                messageRetryMapper.updateById(update);
            }
        }
    }
}
```

这段代码表达了重试机制里最核心的三件事：

- 找到待重试消息
- 再执行一次
- 成功则结束，失败则更新重试次数和下次时间

## 6. 为什么重试机制不能无限重试

因为无限重试会带来几个严重问题：

1. 无法恢复的错误会永远占资源
2. 大量失败消息会不断积压
3. 运维人员很难判断哪些是真正异常

所以工程里通常都会设：

- 最大重试次数
- 失败终态

超过阈值后，就该进入人工关注或死信处理，而不是无限重试。

## 7. 什么时候适合重试

适合重试的通常是“暂时性失败”：

- 网络超时
- 下游短时不可用
- 限流后稍后可恢复

不适合重试的通常是“确定性错误”：

- 手机号格式错误
- 模板参数缺失
- 业务数据本身错误

所以正式项目里，最好对异常做分类，不要所有异常都重试。

## 8. 常见坑点

### 8.1 失败后直接丢弃

通知可靠性会明显不够。

### 8.2 不区分临时错误和永久错误

会产生很多无意义重试。

### 8.3 重试次数和状态不落库

后续根本无法运营和排查。

## 9. 总结

消息重试的核心，是把“第一次失败”当成一次可补偿的暂时异常，而不是最终结果。

一个成熟的实现通常会做到：

- 失败消息可记录
- 重试次数可追踪
- 重试时机可控制
- 超过次数后进入最终失败状态

这对提高通知系统的可靠性非常关键。
