# 消息队列异步通知实现

## 1. 功能定义

消息队列异步通知要解决的问题是：

- 业务事件发生后，不在主流程里直接发送通知，而是把通知任务异步化

它的核心价值是：

- 解耦
- 削峰
- 提升主流程响应速度

例如一个订单支付成功后，系统可能要同时做很多事情：

- 发站内信
- 发短信
- 发邮件
- 发积分
- 发优惠券

如果这些动作全都同步做，主流程会非常重。  
这时就适合用消息队列异步通知。

## 2. 核心设计

消息队列通知实现时，最重要的不是“会不会发 MQ”，而是：

1. 哪些事件值得异步
2. 消息体怎么设计
3. 消费失败怎么办
4. 如何避免重复消费

所以它本质上是一套“事件驱动通知架构”。

## 3. 典型流程

1. 业务主流程完成  
例如订单支付成功。

2. 发送一个通知事件消息到 MQ
3. 通知消费者监听这个消息
4. 消费者根据消息内容发送站内信、短信或邮件
5. 记录发送结果

## 4. 典型消息结构

```json
{
  "eventType": "ORDER_PAY_SUCCESS",
  "bizId": 90001,
  "receiverUserId": 101,
  "params": {
    "orderNo": "ORD20260602001",
    "amount": "99.00"
  }
}
```

这个结构的关键点是：

- 描述一个通知事件
- 不直接和某个具体渠道强绑定

## 5. 核心代码

## 5.1 消息生产者

下面用 `RabbitMQ` 风格举例。

```java
@Service
public class NotifyEventPublisher {

    private final RabbitTemplate rabbitTemplate;

    public NotifyEventPublisher(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    public void publishOrderPaySuccess(OrderPaySuccessNotifyEvent event) {
        rabbitTemplate.convertAndSend(
                "notify.exchange",
                "notify.order.pay.success",
                event
        );
    }
}
```

生产者本身很轻，它的意义是：

- 主流程只负责发事件
- 不直接做通知细节

## 5.2 消息消费者

```java
@Component
public class NotifyEventConsumer {

    private final InboxMessageService inboxMessageService;
    private final SmsNotifyService smsNotifyService;

    public NotifyEventConsumer(
            InboxMessageService inboxMessageService,
            SmsNotifyService smsNotifyService) {
        this.inboxMessageService = inboxMessageService;
        this.smsNotifyService = smsNotifyService;
    }

    @RabbitListener(queues = "notify.order.queue")
    public void consumeOrderPaySuccess(OrderPaySuccessNotifyEvent event) {
        inboxMessageService.send(buildInboxRequest(event));
        smsNotifyService.sendOrderPaySuccess(event.getReceiverUserId(), event.getParams());
    }

    private InboxMessageSendRequest buildInboxRequest(OrderPaySuccessNotifyEvent event) {
        InboxMessageSendRequest request = new InboxMessageSendRequest();
        request.setReceiverUserId(event.getReceiverUserId());
        request.setTitle("支付成功通知");
        request.setContent("订单 " + event.getParams().get("orderNo") + " 支付成功");
        request.setBizType("order");
        request.setBizId(event.getBizId());
        return request;
    }
}
```

这段代码体现的核心思想是：

- 消费者负责真正的通知动作
- 一个事件可以触发多个通知渠道

## 6. 为什么 MQ 适合通知场景

因为通知通常具有这些特点：

- 不一定要求和主流程强一致
- 允许稍有延迟
- 渠道调用可能不稳定

所以非常适合从主业务链路中拆出去，交给异步消费者处理。

如果同步发通知，问题会比较明显：

- 主流程响应变慢
- 某个通知渠道异常会拖累主业务

## 7. 如何避免重复消费

消息队列场景里，重复消费是很常见的问题。  
所以通知消费者通常要做幂等控制。

常见做法包括：

1. 消息里带唯一业务 ID
2. 消费前查是否已处理
3. 已处理则直接返回

例如：

```json
{
  "eventId": "notify_20260602_001",
  "bizId": 90001
}
```

## 8. 常见坑点

### 8.1 主流程和通知逻辑完全耦合

一旦通知渠道有问题，主业务就容易被拖慢。

### 8.2 MQ 消费失败没有重试策略

消息很容易悄悄丢掉。

### 8.3 不做消费幂等

同一个用户可能收到重复短信、重复邮件、重复站内信。

## 9. 总结

消息队列异步通知的核心，是把“业务事件”和“通知执行”拆开。

主流程只负责发事件，消费者再去执行站内信、短信、邮件等具体动作。  
这样能明显提升系统解耦能力、主流程性能和通知体系可扩展性。
