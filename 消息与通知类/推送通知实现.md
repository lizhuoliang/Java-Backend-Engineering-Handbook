# 推送通知实现

## 1. 功能定义

推送通知要解决的问题是：

- 系统如何把实时提醒送到用户设备或客户端上

常见场景包括：

- App 消息推送
- Web 实时提醒
- 订单状态变化提醒
- 聊天消息提醒
- 风控告警提醒

如果说站内信更偏“用户主动去看”，那么推送通知更偏“系统主动把提醒送过去”。

## 2. 常见推送类型

推送通知大致分为三类：

### 2.1 App Push

例如：

- Android 推送
- iOS 推送

### 2.2 Web 实时推送

例如：

- WebSocket
- SSE

### 2.3 第三方即时通知渠道

例如企业微信、钉钉、飞书机器人等。

在 Java 后端里，最常见的基础能力通常是：

- 站内信落库
- WebSocket 做实时提醒

## 3. 核心设计

推送通知设计时最关键的是：

1. 通知内容和推送渠道解耦
2. 用户和连接关系要管理起来
3. 推送失败要有兜底策略
4. 推送不等于最终送达  
很多场景里只能保证“尝试推送”

## 4. 典型流程

1. 业务事件发生
2. 系统生成通知内容
3. 查询目标用户在线状态
4. 在线则实时推送
5. 不在线则只保留站内信或待补发记录

## 5. 核心代码

## 5.1 WebSocket 会话管理

```java
@Component
public class WebSocketSessionManager {

    private final Map<Long, WebSocketSession> sessionMap = new ConcurrentHashMap<>();

    public void bind(Long userId, WebSocketSession session) {
        sessionMap.put(userId, session);
    }

    public void remove(Long userId) {
        sessionMap.remove(userId);
    }

    public WebSocketSession get(Long userId) {
        return sessionMap.get(userId);
    }
}
```

这层的意义很直接：

- 当前哪个用户在线
- 当前用户对应哪个连接

## 5.2 推送核心实现

```java
@Service
public class PushNotifyServiceImpl implements PushNotifyService {

    private final WebSocketSessionManager webSocketSessionManager;
    private final InboxMessageService inboxMessageService;

    public PushNotifyServiceImpl(
            WebSocketSessionManager webSocketSessionManager,
            InboxMessageService inboxMessageService) {
        this.webSocketSessionManager = webSocketSessionManager;
        this.inboxMessageService = inboxMessageService;
    }

    @Override
    public void pushToUser(Long userId, String title, String content) {
        inboxMessageService.send(buildInboxRequest(userId, title, content));

        WebSocketSession session = webSocketSessionManager.get(userId);
        if (session == null || !session.isOpen()) {
            return;
        }

        try {
            String payload = JSON.toJSONString(Map.of(
                    "title", title,
                    "content", content
            ));
            session.sendMessage(new TextMessage(payload));
        } catch (IOException ex) {
            // 实时推送失败时，不影响站内信持久化
        }
    }

    private InboxMessageSendRequest buildInboxRequest(Long userId, String title, String content) {
        InboxMessageSendRequest request = new InboxMessageSendRequest();
        request.setReceiverUserId(userId);
        request.setTitle(title);
        request.setContent(content);
        return request;
    }
}
```

这段代码里最关键的设计点是：

- 先落站内信
- 再尝试实时推送

这样即使实时推送失败，用户后面仍然能在消息中心看到这条通知。

## 6. 为什么推送通知通常要和站内信配合

因为推送本身并不天然可靠：

- 用户可能不在线
- WebSocket 可能断开
- App 可能被系统限制

如果系统只做推送，不做持久化消息，就会出现：

- 当时没收到
- 后面也查不到

所以在工程上，比较稳的做法往往是：

1. 先存站内信
2. 再做实时推送

这其实是“可追溯”和“实时性”的组合。

## 7. 常见扩展

### 7.1 用户离线补发

用户下次上线时，把未读消息一次性推过去。

### 7.2 多端推送

同一个用户可能同时在线：

- Web
- App
- 小程序

这时就不一定是一个 `userId -> 一个连接`，而是一个用户可能绑定多个连接。

### 7.3 推送回执

如果业务要求更高，可能还会追踪：

- 是否送达
- 是否点击

## 8. 常见坑点

### 8.1 只做实时推送，不做持久化

离线用户就收不到了。

### 8.2 业务线程里强依赖推送成功

推送失败不应该拖垮主业务。

### 8.3 会话映射不清晰

用户断线后不及时清理，会导致大量失效连接残留。

## 9. 总结

推送通知的核心，不是“把一条消息发出去”，而是同时平衡实时性和可靠性。

更稳妥的工程实现通常是：

- 先存站内信
- 再做实时推送
- 推送失败不影响主流程

这样通知体系才既能“即时提醒”，又不会“提醒丢失”。
