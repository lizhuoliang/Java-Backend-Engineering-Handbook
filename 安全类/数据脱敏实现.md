# 数据脱敏实现

## 1. 功能定义

数据脱敏要解决的问题是：

- 在展示、导出、日志记录或共享数据时，如何避免把敏感信息完整暴露出去

最常见的敏感数据包括：

- 手机号
- 身份证号
- 邮箱
- 银行卡号
- 住址
- 姓名

很多系统的数据泄露，并不是数据库被黑了，而是：

- 管理后台看得太全
- 日志打得太多
- 导出文件没处理

所以数据脱敏本质上是在做：

- 数据可用性和数据暴露风险之间的平衡

## 2. 数据脱敏通常出现在哪些位置

数据脱敏最常见的几个位置包括：

1. 页面展示脱敏  
例如用户列表里显示 `138****0000`。

2. 接口返回脱敏  
对某些角色只返回部分可见信息。

3. 日志脱敏  
避免在日志里输出完整手机号、证件号。

4. 导出脱敏  
导出给非高权限人员的数据不应是全量明文。

## 3. 核心设计

数据脱敏实现时，建议重点考虑：

1. 哪些字段是敏感字段
2. 哪些场景必须脱敏
3. 哪些角色可以看明文
4. 脱敏是展示层做还是返回层做

这类问题如果不提前定规则，后面系统里就会出现：

- 有的页面脱了
- 有的页面没脱
- 有的导出是明文
- 有的日志全打出来

非常混乱。

## 4. 常见脱敏方式

最常见的脱敏方式包括：

1. 掩码脱敏  
例如中间打星号。

2. 截断脱敏  
只展示前几位或后几位。

3. 按权限控制是否脱敏

在大多数业务系统里，最常见也最实用的是：

- 掩码脱敏 + 权限控制

## 5. 典型示例

```json
{
  "phone": "138****0000",
  "idCard": "3701**********1234",
  "email": "zh***@example.com"
}
```

## 6. 核心代码

## 6.1 脱敏工具类

```java
public class MaskUtil {

    public static String maskPhone(String phone) {
        if (!StringUtils.hasText(phone) || phone.length() < 7) {
            return phone;
        }
        return phone.substring(0, 3) + "****" + phone.substring(phone.length() - 4);
    }

    public static String maskIdCard(String idCard) {
        if (!StringUtils.hasText(idCard) || idCard.length() < 8) {
            return idCard;
        }
        return idCard.substring(0, 4) + "**********" + idCard.substring(idCard.length() - 4);
    }

    public static String maskEmail(String email) {
        if (!StringUtils.hasText(email) || !email.contains("@")) {
            return email;
        }
        int index = email.indexOf("@");
        if (index <= 2) {
            return "***" + email.substring(index);
        }
        return email.substring(0, 2) + "***" + email.substring(index);
    }
}
```

## 6.2 查询返回时按权限脱敏

```java
@Service
public class UserQueryServiceImpl implements UserQueryService {

    private final UserMapper userMapper;
    private final PermissionService permissionService;

    public UserQueryServiceImpl(UserMapper userMapper, PermissionService permissionService) {
        this.userMapper = userMapper;
        this.permissionService = permissionService;
    }

    @Override
    public UserVO detail(Long queryUserId, Long currentUserId) {
        User user = userMapper.selectById(queryUserId);
        if (user == null) {
            throw new BizException("用户不存在");
        }

        boolean canViewFull = permissionService.hasPermission(currentUserId, "user:sensitive:view");

        UserVO vo = new UserVO();
        vo.setUserId(user.getId());
        vo.setNickname(user.getNickname());
        vo.setPhone(canViewFull ? user.getPhone() : MaskUtil.maskPhone(user.getPhone()));
        vo.setEmail(canViewFull ? user.getEmail() : MaskUtil.maskEmail(user.getEmail()));
        vo.setIdCard(canViewFull ? user.getIdCard() : MaskUtil.maskIdCard(user.getIdCard()));
        return vo;
    }
}
```

这里体现的一个很重要的设计思想是：

- 脱敏不一定是全员统一规则
- 它往往和权限直接相关

## 7. 为什么数据脱敏不只是前端问题

很多团队会想：

- 前端自己把字符串打星号就行了

这其实很危险。  
因为如果后端已经把明文返回给前端，那么：

- 抓包里就是明文
- 前端日志里可能是明文
- 其他调用方也能拿到明文

所以真正的脱敏，关键场景下一定要从：

- 后端返回层

就开始控制。

## 8. 日志脱敏为什么特别重要

很多系统真正的数据泄露，不一定是在页面，而是在日志。  
例如：

- 登录请求参数全量打印
- 回调报文全量打印
- 异常堆栈里带明文字段

所以日志脱敏往往和页面脱敏同等重要。  
正式项目里，常见做法包括：

1. 打日志前手动脱敏
2. 统一日志切面处理
3. 敏感字段黑名单过滤

## 9. 导出数据为什么更要谨慎

页面展示通常还有权限和操作门槛，但导出数据一旦形成文件，就更容易扩散。  
所以导出场景下通常要额外明确：

- 谁可以导出明文
- 谁只能导出脱敏数据

这往往不能只靠技术默认处理，还要结合业务权限设计。

## 10. 常见坑点

### 10.1 只在前端脱敏

后端明文已经泄露给调用方了。

### 10.2 页面脱敏了，日志没脱

这在真实项目里非常常见。

### 10.3 所有角色一刀切脱敏

可能影响正常业务操作。

### 10.4 敏感字段清单不统一

系统不同模块脱敏标准会越来越混乱。

## 11. 总结

数据脱敏的核心，不是“给字符串打星号”，而是围绕敏感字段识别、权限控制、返回展示、日志记录和导出共享，建立一套统一的数据暴露控制策略。

一个成熟的数据脱敏实现至少应该做到：

- 敏感字段清单明确
- 后端返回层可控脱敏
- 日志和导出一并纳入治理
- 明文查看权限可控

这才是真正可落地的数据安全能力。
