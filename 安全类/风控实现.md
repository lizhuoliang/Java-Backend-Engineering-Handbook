# 风控实现

## 1. 功能定义

风控要解决的问题是：

- 系统如何在业务过程中识别高风险行为，并根据风险等级采取不同控制措施

和普通安全防护不同，风控更偏：

- 行为判断
- 风险评分
- 决策控制

它不只是回答：

- 请求是否合法

而更关注：

- 请求是否可疑
- 用户行为是否异常
- 当前业务是否值得进一步拦截或验证

## 2. 风控和传统安全控制的区别

可以简单理解为：

- 传统安全控制更偏固定规则  
例如密码错误、权限不足、参数非法。

- 风控更偏动态判断  
例如这个用户虽然密码正确，但行为模式看起来很异常。

所以风控的特点通常是：

- 更贴近业务
- 更依赖上下文
- 更强调分级处理

## 3. 典型风控场景

最常见的风控场景包括：

1. 登录风控  
异地登录、异常设备登录、撞库行为。

2. 注册风控  
批量注册、薅羊毛注册。

3. 支付风控  
异常金额、异常支付频次、异常设备。

4. 营销风控  
优惠券滥用、活动作弊、刷积分。

所以风控几乎从来都不是一个孤立模块，它通常是多个业务场景的安全控制层。

## 4. 风控最核心的思想

风控不是简单地把所有“看起来不正常”的请求全部拦掉。  
更合理的做法通常是：

1. 先识别风险特征
2. 计算或判断风险等级
3. 按风险等级采取不同动作

例如：

- 低风险：放行
- 中风险：要求验证码或二次验证
- 高风险：直接拒绝

这才是更符合真实业务的风控模式。

## 5. 核心设计

风控实现时，建议重点考虑：

1. 风险特征有哪些
2. 风险规则由谁维护
3. 风险命中后做什么动作
4. 风险结果是否记录
5. 风险策略是否可动态调整

风控系统最怕的不是“规则不够多”，而是：

- 规则太死
- 误伤正常用户
- 结果不可解释

## 6. 常见风险因子

最常见的风控因子包括：

1. IP 风险  
异常国家、代理 IP、黑名单 IP。

2. 设备风险  
异常设备、短时间频繁切设备。

3. 账号行为风险  
短时间高频操作、异地登录、异常时间段操作。

4. 业务行为风险  
同设备批量领券、同账号短时间多次支付失败。

## 7. 核心代码

## 7.1 一个简化的登录风控示例

```java
@Service
public class LoginRiskControlServiceImpl implements LoginRiskControlService {

    private final StringRedisTemplate stringRedisTemplate;

    public LoginRiskControlServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public RiskDecision check(String username, String ip, String deviceId) {
        int score = 0;

        Long ipCount = getCount("risk:login:ip:" + ip, Duration.ofMinutes(10));
        if (ipCount != null && ipCount > 20) {
            score += 40;
        }

        Long userCount = getCount("risk:login:user:" + username, Duration.ofMinutes(10));
        if (userCount != null && userCount > 10) {
            score += 30;
        }

        Long deviceCount = getCount("risk:login:device:" + deviceId, Duration.ofMinutes(10));
        if (deviceCount != null && deviceCount > 15) {
            score += 30;
        }

        if (score >= 70) {
            return new RiskDecision("REJECT", "高风险登录，拒绝访问");
        }
        if (score >= 40) {
            return new RiskDecision("VERIFY", "需要图形验证码或二次验证");
        }
        return new RiskDecision("PASS", "通过");
    }

    private Long getCount(String key, Duration duration) {
        Long count = stringRedisTemplate.opsForValue().increment(key);
        if (count != null && count == 1L) {
            stringRedisTemplate.expire(key, duration);
        }
        return count;
    }
}
```

这段代码展示的是一个非常简化的风控雏形：

- 按多个维度累积风险分
- 再根据分值给出决策

## 8. 风控结果为什么最好不是“只返回 true/false”

因为风控不是只有：

- 通过
- 拒绝

很多时候更合理的结果是：

- 放行
- 二次验证
- 人工审核
- 暂时冻结

所以风控系统的输出更适合是：

- 风险决策

而不是简单布尔值。

## 9. 风控和审计的关系

这两个能力经常一起出现。

- 风控负责“事中判断”
- 审计负责“事后留痕”

例如登录风控命中高风险后，不只是要拒绝，还应该记录：

- 用户
- IP
- 风险原因
- 命中规则

这样后续才能分析：

- 是误判还是攻击

## 10. 为什么风控规则要能动态调整

因为风控是非常业务化的。  
不同阶段、不同活动、不同业务场景，风险阈值很可能不一样。

例如：

- 活动大促期间阈值可能更严格
- 内部管理系统和开放平台注册阈值也不同

如果所有规则都硬编码在 Java 代码里，后期维护会非常困难。  
所以更成熟的风控系统往往会继续演进到：

- 规则配置化
- 风险分级配置化

## 11. 常见坑点

### 11.1 只有一刀切拦截，没有中间态

会误伤大量正常用户。

### 11.2 风控命中不留痕

后续很难做策略优化。

### 11.3 规则完全写死

业务一变就得改代码上线。

### 11.4 风控和业务链路强耦合

后续复用会很差。

## 12. 总结

风控的核心，不是“拦请求”，而是围绕风险特征识别、风险等级判断和差异化控制动作，建立一套对业务行为进行动态安全治理的能力。

一个成熟的风控实现至少应该做到：

- 多维风险因子
- 风险结果分级
- 风险决策可留痕
- 风险规则可逐步配置化

这才是真正有业务价值的风控体系。
