# 接口签名实现

## 1. 功能定义

接口签名要解决的问题是：

- 请求在到达服务端时，系统如何确认这份请求参数没有被篡改、确实来自合法调用方、并且不是旧请求重放

它最常见于：

- 开放平台 API
- 第三方回调校验
- 服务间调用安全
- App 请求防篡改

如果说登录安全解决的是“用户身份可信”，那接口签名更偏解决：

- 请求内容可信
- 请求来源可信

## 2. 为什么要做接口签名

因为很多系统并不只面对浏览器前端，还要面对：

- 移动端
- 第三方商户
- 外部系统
- 支付平台回调

这些请求如果没有额外校验，只靠普通参数传递，很容易出现：

1. 参数被篡改  
金额、状态、业务 ID 被改。

2. 请求被伪造  
别人仿照接口格式直接发请求。

3. 请求被重放  
旧请求被重复提交多次。

所以接口签名本质上是一套：

- 完整性验证
- 来源校验
- 重放防护

机制。

## 3. 一个典型的签名机制通常包含什么

最常见的签名方案通常会包含这些字段：

```json
{
  "appId": "merchant_1001",
  "timestamp": 1717300000,
  "nonce": "a8c91d",
  "sign": "签名字符串"
}
```

它们的作用分别是：

- `appId`：标识调用方是谁
- `timestamp`：防止请求长期有效
- `nonce`：防止同一时间戳下重复请求
- `sign`：对请求内容做签名摘要

## 4. 典型签名流程

一个常见的签名校验流程通常如下：

1. 调用方准备请求参数
2. 按约定顺序拼接参数串
3. 使用 `secret` 生成签名
4. 服务端收到请求
5. 根据 `appId` 查到对应 `secret`
6. 服务端重新计算签名
7. 对比签名是否一致
8. 校验时间戳和 nonce 是否有效

## 5. 核心设计

接口签名实现时，建议重点考虑：

1. 哪些字段参与签名
2. 参数拼接规则是否唯一确定
3. 时间戳容忍窗口多大
4. nonce 怎么防重放
5. secret 如何安全管理

其中最容易出问题的一点是：

- 签名规则不统一

如果客户端和服务端对“参与签名的参数顺序、空值处理、编码方式”理解不一致，签名系统会非常难用。

## 6. 核心代码

## 6.1 签名生成核心实现

```java
@Component
public class SignService {

    public String sign(Map<String, String> params, String secret) {
        String source = params.entrySet().stream()
                .filter(e -> !"sign".equals(e.getKey()) && StringUtils.hasText(e.getValue()))
                .sorted(Map.Entry.comparingByKey())
                .map(e -> e.getKey() + "=" + e.getValue())
                .collect(Collectors.joining("&"));

        String signSource = source + "&secret=" + secret;
        return DigestUtils.md5DigestAsHex(signSource.getBytes(StandardCharsets.UTF_8)).toUpperCase();
    }
}
```

这段代码表达的是最经典的一类签名思路：

- 参数按 key 排序
- 拼成统一字符串
- 再加 secret 做摘要

## 6.2 服务端签名校验示例

```java
@Service
public class SignVerifyServiceImpl implements SignVerifyService {

    private final SignService signService;
    private final StringRedisTemplate stringRedisTemplate;
    private final AppSecretMapper appSecretMapper;

    public SignVerifyServiceImpl(
            SignService signService,
            StringRedisTemplate stringRedisTemplate,
            AppSecretMapper appSecretMapper) {
        this.signService = signService;
        this.stringRedisTemplate = stringRedisTemplate;
        this.appSecretMapper = appSecretMapper;
    }

    @Override
    public void verify(Map<String, String> params) {
        String appId = params.get("appId");
        String sign = params.get("sign");
        String timestamp = params.get("timestamp");
        String nonce = params.get("nonce");

        if (!StringUtils.hasText(appId) || !StringUtils.hasText(sign)
                || !StringUtils.hasText(timestamp) || !StringUtils.hasText(nonce)) {
            throw new BizException("签名参数缺失");
        }

        long requestTs = Long.parseLong(timestamp);
        long now = Instant.now().getEpochSecond();
        if (Math.abs(now - requestTs) > 300) {
            throw new BizException("请求已过期");
        }

        String nonceKey = "sign:nonce:" + appId + ":" + nonce;
        Boolean first = stringRedisTemplate.opsForValue().setIfAbsent(nonceKey, "1", Duration.ofMinutes(5));
        if (Boolean.FALSE.equals(first)) {
            throw new BizException("请求重复提交");
        }

        String secret = appSecretMapper.selectSecretByAppId(appId);
        if (!StringUtils.hasText(secret)) {
            throw new BizException("非法调用方");
        }

        String calculated = signService.sign(params, secret);
        if (!Objects.equals(calculated, sign)) {
            throw new BizException("签名校验失败");
        }
    }
}
```

这段代码里最关键的三层保护分别是：

1. 时间戳校验
2. nonce 防重放
3. sign 参数防篡改

## 7. 为什么光有 sign 还不够

如果只有签名，没有时间戳和 nonce，会出现一个问题：

- 攻击者拿到一份合法请求后，可以重复重放

因为签名本身只保证：

- 参数没变

但不能保证：

- 这是不是一份旧请求

所以真正完整的签名机制，几乎一定要配：

- `timestamp`
- `nonce`

## 8. 接口签名最适合什么场景

接口签名最适合：

1. 开放平台接口  
外部合作方调用你的系统。

2. 支付回调和第三方回调  
确认回调确实来自可信平台。

3. 服务间高安全调用  
尤其是跨网络边界的调用。

而对于普通浏览器登录用户访问的业务接口，通常更多依赖：

- token
- session
- CSRF 保护

而不是把所有前端接口都做成复杂签名机制。

## 9. 常见坑点

### 9.1 客户端和服务端参数拼接规则不一致

这是签名系统最常见的接入问题。

### 9.2 签名里不带时间戳和 nonce

容易被重放攻击。

### 9.3 secret 硬编码在代码里随意传播

会造成更大的安全风险。

### 9.4 签名只校验通过与否，不记录异常请求

后续很难做风险分析和排查。

## 10. 总结

接口签名的核心，不是“多传一个 sign 参数”，而是围绕：

- 参数完整性
- 调用方合法性
- 请求时效性
- 重放防护

建立一套可被客户端和服务端共同遵守的安全调用规则。

一个成熟的接口签名实现至少应该做到：

- 统一的参数签名规则
- appId 对应 secret 管理
- 时间戳校验
- nonce 防重放
- 签名失败可追踪

这才是接口签名真正的工程价值。
