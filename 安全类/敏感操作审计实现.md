# 敏感操作审计实现

## 1. 功能定义

敏感操作审计要解决的问题是：

- 系统中那些高风险、可造成重大影响的操作，如何被完整记录下来，便于事后追踪、问责和复盘

最常见的敏感操作包括：

- 删除核心数据
- 修改权限角色
- 调整支付金额
- 审核关键单据
- 导出大量敏感数据
- 重置用户密码

这类操作的共性是：

- 一旦出错或被滥用，影响很大

所以系统不能只做“执行成功”，还要做：

- 谁在什么时候做了什么

## 2. 为什么审计和普通操作日志不同

很多系统都有“操作日志”，但敏感操作审计比普通操作日志更强调：

1. 风险级别更高
2. 记录粒度更细
3. 更强调不可抵赖性
4. 更适合事后调查和安全追踪

换句话说：

- 普通日志偏运营可见
- 审计日志偏安全和合规可追责

## 3. 典型审计内容

一个比较完整的敏感操作审计记录，通常至少包括：

```json
{
  "operatorUserId": 101,
  "operatorName": "admin",
  "operationType": "DELETE_USER",
  "bizId": 2001,
  "beforeData": "{...}",
  "afterData": "{...}",
  "clientIp": "10.0.0.1",
  "operationTime": "2026-06-02 16:00:00"
}
```

这里几个非常关键的字段是：

- 谁操作的
- 操作了哪个对象
- 操作前后数据是什么
- 什么时候操作的

## 4. 核心设计

敏感操作审计实现时，建议重点考虑：

1. 哪些操作属于敏感操作
2. 审计日志是否单独落表
3. 是否记录操作前后快照
4. 是否记录请求来源和 IP
5. 审计日志是否允许随意删除

尤其是最后一点：

- 审计日志本身应该比普通业务日志更严肃

## 5. 典型流程

1. 用户触发敏感操作
2. 系统执行权限校验
3. 操作前获取关键信息快照
4. 执行业务动作
5. 写入审计日志

如果更严格，还可以做到：

- 审计日志异步落库 + 失败告警

## 6. 核心代码

## 6.1 审计日志对象示例

```java
public class AuditLog {

    private Long operatorUserId;
    private String operationType;
    private String bizType;
    private Long bizId;
    private String beforeData;
    private String afterData;
    private String clientIp;
    private LocalDateTime operationTime;
}
```

## 6.2 业务中手动记录审计日志

以“删除用户”为例：

```java
@Service
public class UserAdminServiceImpl implements UserAdminService {

    private final UserMapper userMapper;
    private final AuditLogMapper auditLogMapper;

    public UserAdminServiceImpl(UserMapper userMapper, AuditLogMapper auditLogMapper) {
        this.userMapper = userMapper;
        this.auditLogMapper = auditLogMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void deleteUser(Long userId, Long operatorUserId, String clientIp) {
        User user = userMapper.selectById(userId);
        if (user == null) {
            throw new BizException("用户不存在");
        }

        String beforeData = JSON.toJSONString(user);
        userMapper.deleteById(userId);

        AuditLog log = new AuditLog();
        log.setOperatorUserId(operatorUserId);
        log.setOperationType("DELETE_USER");
        log.setBizType("USER");
        log.setBizId(userId);
        log.setBeforeData(beforeData);
        log.setAfterData(null);
        log.setClientIp(clientIp);
        log.setOperationTime(LocalDateTime.now());
        auditLogMapper.insert(log);
    }
}
```

这段代码最关键的不是删用户，而是：

- 删除前保留了快照
- 删除后保留了审计记录

## 7. 为什么操作前后快照很有价值

因为很多敏感操作不是简单的“有没有发生”，而是：

- 改了什么
- 改之前是什么
- 改之后是什么

例如：

- 某个用户原来是普通角色，被改成了管理员
- 某个订单金额原来是 100，被改成了 1

这类问题如果没有前后快照，很难完整还原现场。

## 8. 为什么审计不适合只靠普通接口日志

普通接口日志通常只知道：

- 谁调了什么接口

但审计更关心：

- 真正影响了哪条业务数据
- 变更前后是什么

所以敏感操作审计更适合和具体业务动作绑定，而不只是记录 HTTP 访问。

## 9. 审计日志和权限系统的关系

一个成熟的安全体系里：

- 权限系统负责“谁能做”
- 审计系统负责“谁做了什么”

也就是说：

- 权限控制是事前防护
- 审计记录是事后追踪

这两者结合起来，系统的安全闭环才算比较完整。

## 10. 常见坑点

### 10.1 只做权限校验，不做审计

事后出了问题很难追踪。

### 10.2 审计日志只记“操作成功”

却不记录操作对象和变更内容，价值会很有限。

### 10.3 审计日志可以随意被删除

会削弱审计的可信度。

### 10.4 所有操作都写成审计级别

会让审计数据噪音过大，失去重点。

## 11. 总结

敏感操作审计的核心，不是“多打一条日志”，而是围绕高风险业务动作，建立一套可还原、可追踪、可追责的操作留痕机制。

一个成熟的审计实现至少应该做到：

- 敏感操作范围明确
- 审计日志独立记录
- 操作人、对象、时间、前后快照可追踪
- 审计记录不轻易被篡改

这才是真正有安全价值的审计体系。
