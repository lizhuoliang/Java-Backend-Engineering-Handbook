# 异常行为识别实现

## 1. 功能定义

异常行为识别要解决的问题是：

- 系统如何从一连串用户行为、设备行为或业务操作中，识别出“看起来不正常”的模式

它和前一篇的风控关系很近，但可以这样理解：

- 风控更偏“规则决策”
- 异常行为识别更偏“发现异常模式”

也就是说：

- 风控负责决定拦不拦
- 异常行为识别负责告诉你“哪里不对劲”

## 2. 为什么需要异常行为识别

因为很多风险并不是一次请求就能看出来，而是要结合行为序列。  
例如：

- 某账号 10 分钟内连续登录失败 30 次
- 某设备半小时切换了 20 个账号
- 某用户凌晨连续导出大量数据
- 某 IP 在极短时间内扫描大量接口

单次请求看起来可能都“合法”，但连续行为组合起来就很异常。

## 3. 典型识别场景

最常见的异常行为识别场景包括：

1. 登录异常  
异地登录、失败爆发、设备切换异常。

2. 操作异常  
短时间连续删除、连续审批、大量导出。

3. 营销异常  
短时间批量领券、重复薅活动。

4. 数据访问异常  
夜间异常查阅敏感数据、大规模批量访问。

## 4. 核心设计

异常行为识别实现时，建议重点考虑：

1. 识别对象是谁  
用户、IP、设备、商户。

2. 观察窗口多长  
1 分钟、10 分钟、24 小时。

3. 什么模式算异常
4. 识别结果如何处理  
只是告警，还是直接拦截。

这里最关键的一点是：

- 异常行为识别更像一层“感知系统”

它不一定直接阻断业务，但会为风控、审计和运营提供重要输入。

## 5. 常见识别方式

最基础的识别方式通常是：

1. 频率阈值识别
2. 时间窗口识别
3. 多维组合识别

例如：

- 同一用户 5 分钟内导出超过 10 次
- 同一设备 10 分钟内切换超过 5 个账号
- 同一 IP 1 分钟内访问超过 100 次登录接口

这些都是非常典型的异常行为规则。

## 6. 核心代码

## 6.1 导出行为异常识别示例

```java
@Service
public class AbnormalBehaviorServiceImpl implements AbnormalBehaviorService {

    private final StringRedisTemplate stringRedisTemplate;
    private final AbnormalEventMapper abnormalEventMapper;

    public AbnormalBehaviorServiceImpl(
            StringRedisTemplate stringRedisTemplate,
            AbnormalEventMapper abnormalEventMapper) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.abnormalEventMapper = abnormalEventMapper;
    }

    @Override
    public void detectExportBehavior(Long userId, String clientIp) {
        String userKey = "abnormal:export:user:" + userId;
        Long count = stringRedisTemplate.opsForValue().increment(userKey);
        if (count != null && count == 1L) {
            stringRedisTemplate.expire(userKey, Duration.ofMinutes(10));
        }

        if (count != null && count > 10) {
            AbnormalEvent event = new AbnormalEvent();
            event.setUserId(userId);
            event.setClientIp(clientIp);
            event.setEventType("EXPORT_OVER_FREQUENCY");
            event.setDescription("10分钟内导出次数超过阈值");
            event.setCreateTime(LocalDateTime.now());
            abnormalEventMapper.insert(event);
        }
    }
}
```

这段代码体现的是最基础的一种异常行为识别方式：

- 行为计数
- 阈值判断
- 命中后记录异常事件

## 7. 为什么异常行为识别最好和“事件记录”结合

因为异常识别很多时候不是为了立刻拒绝，而是为了：

- 后续分析
- 风控联动
- 人工排查

所以识别结果最好不要只是：

- `return true`

更有价值的做法是：

- 把异常事件记下来

例如：

```json
{
  "eventType": "LOGIN_FAIL_BURST",
  "userId": 101,
  "ip": "1.2.3.4",
  "description": "10分钟内登录失败超过20次"
}
```

## 8. 异常识别和风控如何衔接

一个很常见的工程模式是：

1. 异常行为识别模块负责产出“风险信号”
2. 风控模块根据这些信号做决策

例如：

- 异常识别发现“同设备频繁换账号”
- 风控模块据此决定“要求二次验证”

这样设计的好处是：

- 感知和决策分层
- 后续规则更容易扩展

## 9. 为什么异常行为识别不能只看单次请求

因为很多风险只有放到行为序列里才有意义。  
例如：

- 一次导出没问题
- 一次登录失败没问题

但如果：

- 10 分钟内导出 50 次
- 5 分钟内切换 20 个账号

那就明显不正常了。

所以异常行为识别的重点往往在于：

- 时间窗口
- 行为累计
- 多维组合

## 10. 常见坑点

### 10.1 只识别，不记录

后续无法分析趋势和误报。

### 10.2 所有异常一律直接封禁

会误伤正常用户。

### 10.3 规则只看单一维度

很容易被绕过。

### 10.4 没有时间窗口概念

很多行为异常其实依赖频率和时序。

## 11. 总结

异常行为识别的核心，不是“找几个奇怪请求”，而是围绕用户、设备、IP 和业务行为，在时间窗口内识别不符合正常模式的访问和操作轨迹。

一个成熟的异常行为识别实现至少应该做到：

- 识别对象明确
- 时间窗口明确
- 异常模式可定义
- 识别结果可记录可联动

这样它才能真正成为风控和安全治理体系的前哨层。
