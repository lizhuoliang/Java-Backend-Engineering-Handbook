# 定时任务实现

## 1. 功能定义

定时任务要解决的问题是：

- 某段业务逻辑不是由用户请求实时触发，而是由系统按照预先约定的时间规则自动执行

这是后端系统里非常基础但也非常容易被低估的一类能力。  
因为很多业务并不是“用户点一下就执行”，而是天然带有时间驱动属性，例如：

- 每天凌晨跑日报
- 每小时同步外部数据
- 每 5 分钟清理过期缓存
- 每天定时做对账
- 每晚批量统计订单数据

所以从工程角度看，定时任务本质上是在系统内部建立一套：

- 能按时间触发
- 能自动执行
- 能失败可追踪
- 能集群可治理

的后台执行机制。

## 2. 为什么业务系统离不开定时任务

很多业务如果没有定时任务，只能靠人工或者临时脚本来弥补。  
这会带来几个明显问题：

1. 不稳定  
人工执行容易忘、容易晚、容易漏。

2. 不可追踪  
出了问题后，很难回答：
这次任务到底跑没跑、跑到哪、失败在哪。

3. 不可规模化  
任务一多，人工维护成本会迅速上升。

所以只要系统里存在“基于时间触发的后台逻辑”，就绕不开任务调度体系。

## 3. 定时任务和其他任务类型的区别

为了后面把第八类整体串起来，先把几个概念分开：

### 3.1 定时任务

强调：

- 按固定时间规则触发

例如：

- 每天 2 点执行
- 每 5 分钟执行

### 3.2 延迟任务

强调：

- 某个具体业务对象，在未来某个时间点执行一次

例如：

- 订单 30 分钟未支付自动关闭

### 3.3 批处理任务

强调：

- 一次处理大量数据

例如：

- 每天批量生成订单统计

也就是说：

- “定时”是触发方式
- “批处理”是任务形态

一个任务完全可能既是定时任务，又是批处理任务。

## 4. 常见定时任务类型

定时任务大致可以分为两类。

### 4.1 固定频率任务

例如：

- 每 1 分钟执行一次
- 每 5 分钟执行一次
- 每小时执行一次

这类任务更适合：

- 轮询检查
- 轻量同步
- 周期性扫描

### 4.2 固定时刻任务

例如：

- 每天凌晨 1 点执行
- 每月 1 号执行
- 每周一早上 8 点执行

这类任务更适合：

- 日报
- 月结
- 定时归档

## 5. 典型应用场景

最常见的定时任务场景包括：

1. 周期清理类  
例如清理过期会话、清理临时文件、归档历史数据。

2. 周期同步类  
例如同步第三方商品、同步组织架构、同步外部汇率。

3. 周期统计类  
例如日报、周报、月报。

4. 周期修正类  
例如扫描异常订单、扫描待补偿数据。

如果你把这些场景看透，就会发现定时任务并不是一个“技术装饰”，而是很多系统业务运转的基础设施。

## 6. 核心设计

定时任务实现时，我建议至少先把下面这些问题想清楚：

1. 任务由什么规则触发  
固定频率还是 cron 表达式。

2. 任务允许重复执行吗  
单机可以重复，集群可能不行。

3. 任务失败怎么办  
失败后重试、补偿还是直接记录告警。

4. 任务执行时间可能多长  
如果任务执行 10 分钟，但调度周期是 5 分钟，就要考虑重叠执行问题。

5. 任务是否要记录执行日志  
这决定后续能否排查和运营。

这几个问题如果一开始没想清楚，任务一多就会越来越乱。

## 7. 最基础的实现方式

在 Spring Boot 项目里，最基础的定时任务通常用：

- `@Scheduled`

例如：

```java
@Component
public class DailyReportJob {

    @Scheduled(cron = "0 0 2 * * ?")
    public void execute() {
        // 每天凌晨 2 点执行日报生成逻辑
    }
}
```

这适合：

- 单体项目
- 单机部署
- 任务量不大
- 学习和基础工程阶段

但要强调：

- `@Scheduled` 只是调度入口，不等于完整的任务治理体系

## 8. 一个更接近真实项目的任务写法

真实项目里，定时任务不能只写一句执行逻辑，通常还要把这些信息记录下来：

- 任务开始时间
- 任务结束时间
- 耗时
- 成功处理数量
- 失败异常

例如：

```java
@Component
public class OrderCloseJob {

    private final OrderTimeoutService orderTimeoutService;

    public OrderCloseJob(OrderTimeoutService orderTimeoutService) {
        this.orderTimeoutService = orderTimeoutService;
    }

    @Scheduled(fixedDelay = 60000)
    public void execute() {
        long start = System.currentTimeMillis();
        try {
            int count = orderTimeoutService.closeTimeoutOrders();
            System.out.println("定时关闭订单成功，处理数量=" + count);
        } catch (Exception ex) {
            System.err.println("定时关闭订单失败: " + ex.getMessage());
        } finally {
            long cost = System.currentTimeMillis() - start;
            System.out.println("任务耗时(ms)=" + cost);
        }
    }
}
```

这段代码的价值不是输出日志本身，而是体现一个很重要的工程意识：

- 定时任务很多时候没有前端用户盯着
- 所以日志和监控几乎就是它的唯一“可见性”

## 9. 集群环境下最大的问题：重复执行

这是定时任务最经典、也是最常见的坑。

假设你有 3 台应用实例，都部署了这个任务，那么默认情况下：

- 这 3 台都会执行一次

有些任务允许这样，例如：

- 本地缓存刷新

但很多任务绝对不能这样，例如：

- 每日结算
- 批量关单
- 月度统计入库

所以一旦进入集群环境，你就必须明确：

- 这个任务是允许多节点执行，还是只允许一个节点执行

## 10. 集群下的基础防重思路

最常见的轻量做法是：

- 给任务加分布式锁

例如：

```java
@Component
public class SettlementJob {

    private final RedisDistributedLockService lockService;

    public SettlementJob(RedisDistributedLockService lockService) {
        this.lockService = lockService;
    }

    @Scheduled(cron = "0 0 1 * * ?")
    public void execute() {
        String requestId = lockService.tryLock("job:settlement", Duration.ofMinutes(10));
        if (requestId == null) {
            return;
        }

        try {
            // 执行结算逻辑
        } finally {
            lockService.unlock("job:settlement", requestId);
        }
    }
}
```

它背后的思想很直接：

- 多节点都能尝试触发
- 但最终只有抢到锁的节点真正执行

## 11. 为什么光有锁还不够

因为锁只能解决：

- 谁来执行

但解决不了下面这些问题：

- 执行成功没有
- 执行了多久
- 失败了多少次
- 是否支持暂停恢复
- 是否支持手工补跑

所以任务一旦变多，仅靠 `@Scheduled + 分布式锁` 往往不够用。

## 12. 更完整的工程化方案

当任务规模上来后，正式项目里经常会使用：

- Quartz
- XXL-Job
- 自研调度中心

这些调度平台真正的价值不是“支持 cron 表达式”，而是：

1. 任务集中管理
2. 执行日志统一查看
3. 失败告警统一处理
4. 动态启停和手工触发
5. 集群调度治理

所以当你发现项目里的任务已经越来越多时，真正该升级的不是注解写法，而是任务治理方式。

## 13. 定时任务和业务逻辑应该怎么分层

一个很好的实践是：

- Job 只负责触发
- Service 负责真正业务处理

也就是说：

- Job 是调度层
- Service 是业务层

这样做有几个好处：

1. 业务逻辑可复用  
同一个逻辑既能被定时任务触发，也能被人工补偿触发。

2. 测试更容易  
你可以直接测 Service，不依赖调度环境。

3. 任务职责更清晰  
Job 不会变成一个超大业务类。

## 14. 执行时间长的任务要注意什么

如果一个任务执行很慢，比如 20 分钟，而调度周期只有 5 分钟，就会出现：

- 上一个还没跑完，下一个又触发了

这会带来：

- 重叠执行
- 资源竞争
- 结果混乱

常见应对方式包括：

1. 调整调度周期
2. 任务加锁防重入
3. 拆分成更细的批处理
4. 使用调度平台控制并发执行策略

## 15. 常见坑点

### 15.1 任务异常直接抛出没人管

结果通常是：

- 日志里报一次错
- 但没人知道业务其实已经漏执行了

### 15.2 集群多节点重复执行

这是定时任务最典型的线上问题。

### 15.3 没有任务执行日志

出了问题后很难回答：

- 今天任务到底跑没跑

### 15.4 任务逻辑写得过重

把非常大的业务逻辑全塞进 Job 里，后期维护很困难。

## 16. 总结

定时任务的核心，不是“按时跑一段代码”，而是为系统建立一套可按时间自动触发、可观测、可治理、可在集群环境中稳定执行的后台任务机制。

一个更成熟的定时任务实现，至少应该做到：

- 调度规则明确
- Job 和业务逻辑分层
- 失败和耗时可观测
- 集群下不重复乱跑
- 复杂场景能平滑升级到调度平台

这才是真正能支撑业务长期运转的定时任务体系。
