# 批处理任务实现

## 1. 功能定义

批处理任务要解决的问题是：

- 系统如何在后台一次性处理大量数据，而不是依赖用户逐条触发

这是很多业务系统非常常见的一类任务。  
典型场景包括：

- 每天批量汇总订单数据
- 批量导入和清洗历史数据
- 批量发送站内信或邮件
- 批量修正异常记录
- 批量归档历史表数据

它和普通同步接口最大的区别在于：

- 普通接口强调单次请求实时返回
- 批处理强调大批量、后台执行、结果可追踪

## 2. 为什么批处理任务单独成类

因为批处理任务虽然也可能由定时触发，但它真正难的地方不在“什么时候跑”，而在：

- 数据量大
- 执行时间长
- 失败后恢复麻烦
- 对数据库压力大

所以批处理不是简单的“定时任务 + for 循环”，而是一套专门的大规模数据处理模式。

## 3. 常见批处理场景

最典型的批处理任务通常可以分成几类：

### 3.1 统计汇总型

例如：

- 每日交易汇总
- 用户行为汇总
- 部门绩效汇总

### 3.2 批量操作型

例如：

- 批量更新过期状态
- 批量发通知
- 批量调整标签

### 3.3 数据迁移清洗型

例如：

- 旧系统数据迁移
- 历史脏数据修复
- 表结构改造后的批量补数据

这三类虽然业务不同，但处理思路很像：

- 数据多
- 需要分批
- 需要可追踪

## 4. 核心设计

批处理任务实现时，我建议重点考虑：

1. 单次要处理多少数据
2. 数据怎么分批读
3. 每批怎么执行事务
4. 失败后是否能从中间继续
5. 结果如何记录

这里最关键的一点是：

- 批处理绝不能默认“全量查出来再处理”

只要数据量一大，这种写法几乎一定会出问题。

## 5. 批处理和普通分页查询的区别

很多人会觉得：

- 批处理不就是分页查出来处理吗

这只说对了一半。  
真正的差别在于，批处理除了“分批读”，还要额外考虑：

- 批次进度
- 失败恢复
- 批次事务边界
- 运行时资源影响

也就是说：

- 分页是手段
- 批处理是完整执行模式

## 6. 典型流程

一个比较成熟的批处理流程通常如下：

1. 创建任务执行记录
2. 计算本次处理范围
3. 分批拉取数据
4. 每批执行处理逻辑
5. 记录每批成功或失败情况
6. 更新总任务状态

## 7. 核心代码

## 7.1 分批处理核心实现

以下用“批量统计已完成订单”为例：

```java
@Component
public class OrderStatisticsBatchJob {

    private final OrderMapper orderMapper;
    private final OrderStatisticsService orderStatisticsService;

    public OrderStatisticsBatchJob(
            OrderMapper orderMapper,
            OrderStatisticsService orderStatisticsService) {
        this.orderMapper = orderMapper;
        this.orderStatisticsService = orderStatisticsService;
    }

    @Scheduled(cron = "0 0 1 * * ?")
    public void execute() {
        long pageNum = 1;
        long pageSize = 500;

        while (true) {
            Page<Order> page = new Page<>(pageNum, pageSize);
            Page<Order> resultPage = orderMapper.selectPage(
                    page,
                    new LambdaQueryWrapper<Order>()
                            .eq(Order::getStatus, "FINISHED")
                            .orderByAsc(Order::getId)
            );

            if (resultPage.getRecords().isEmpty()) {
                break;
            }

            orderStatisticsService.batchHandle(resultPage.getRecords());
            pageNum++;
        }
    }
}
```

这段代码的关键意义在于：

- 一次只处理一个批次
- 批次之间自然形成边界

## 7.2 批次处理逻辑独立封装

```java
@Service
public class OrderStatisticsServiceImpl implements OrderStatisticsService {

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void batchHandle(List<Order> orders) {
        for (Order order : orders) {
            // 处理单条订单统计
        }
    }
}
```

这里把每一批的数据处理放进独立 Service，有两个好处：

1. 批次事务边界清晰
2. 后续出问题时更容易定位是哪一批失败

## 8. 为什么批处理一定要分批

因为批处理最容易犯的错误就是：

- 一次查全量
- 一次处理全量

这会带来几个严重问题：

1. 应用内存暴涨
2. 单次 SQL 压力过大
3. 大事务时间过长
4. 失败回滚代价非常高

而分批处理至少能把问题控制在：

- 某一批

即使失败，影响范围和恢复成本也小得多。

## 9. 为什么批处理最好有任务执行记录

批处理和普通接口最大的不同之一，就是：

- 它不一定立刻有用户盯着结果

所以你必须能回答这些问题：

- 任务什么时候开始的
- 跑了多久
- 处理了多少条
- 成功多少条
- 失败多少条
- 当前跑到第几批

正式项目里，通常会配一张任务执行记录表，例如：

```json
{
  "jobName": "order_statistics_batch",
  "status": "RUNNING",
  "totalCount": 100000,
  "successCount": 50000,
  "failCount": 10,
  "currentBatchNo": 100
}
```

## 10. 为什么批处理要考虑断点续跑

因为有些任务真的会跑很久。  
例如：

- 几十万条历史数据迁移
- 大规模导出或对账

如果跑到一半失败，而系统又没有记录进度，就只能：

- 从头再来

这在很多场景下代价很高。  
所以成熟的批处理任务通常会考虑：

1. 记录最后处理到哪个 ID
2. 下次从该位置继续

这就是典型的断点续跑思想。

## 11. 批处理为什么容易影响线上系统

因为它天然就会：

- 扫大量数据
- 占用数据库连接
- 产生大量 IO
- 占用应用线程资源

所以正式项目里批处理通常要注意：

1. 尽量跑在低峰期
2. 控制批大小
3. 限制并发度
4. 必要时走从库或离线库

否则很容易出现：

- 批处理跑得很开心
- 线上接口却被拖慢了

## 12. 常见坑点

### 12.1 一次性全量查数据

这是批处理最危险的写法之一。

### 12.2 整个批处理只开一个大事务

失败回滚范围会非常夸张。

### 12.3 没有进度和结果记录

出问题后几乎不知道该从哪接着处理。

### 12.4 不控制批大小

每批过大时仍然可能把系统拖垮。

## 13. 总结

批处理任务的核心，不是“后台跑个循环”，而是围绕大批量数据操作建立一套分批读取、分批执行、结果可追踪、失败可恢复的后台执行机制。

一个成熟的批处理实现至少应该做到：

- 数据分批处理
- 批次边界清晰
- 执行结果可观测
- 支持断点续跑思路
- 对线上资源影响可控

这才是真正能长期稳定运行的批处理任务设计。
