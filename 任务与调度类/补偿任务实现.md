# 补偿任务实现

## 1. 功能定义

补偿任务要解决的问题是：

- 某个业务流程因为异常、中断、超时、回调丢失或跨服务处理失败，没有完整闭环时，系统如何在事后把它“补回来”

它不是主流程本身，而是主流程之外的一层兜底机制。  
这点非常重要，因为很多系统在设计上都有一个误区：

- 认为主流程只要大部分时候成功就够了

但在真实生产环境里，哪怕只有极少量的：

- 回调漏处理
- 消息消费失败
- 状态没改成功

如果不做补偿，时间一长就会积累成很大的业务问题。

所以补偿任务本质上是在做：

- 业务一致性的延后修复

## 2. 哪些场景最需要补偿任务

补偿任务最常出现于分布式流程或依赖外部系统的流程中。  
典型场景包括：

1. 支付成功了，但订单状态没改成功
2. 退款成功了，但退款单状态没同步回来
3. MQ 消息没消费成功，导致后续逻辑没跑完
4. 定时任务执行时中途异常，只处理了一部分数据
5. 对账发现渠道成功但本地失败，需要补单

这些场景的共同特点是：

- 业务曾经“应该成功”
- 但系统实际状态“没有最终成功”

补偿任务要做的，就是把这两者重新拉回一致。

## 3. 补偿和重试的区别

这两个词经常一起出现，但其实层级不同。

### 重试

更偏技术动作：

- 某次调用失败后，短时间内再试一次

例如：

- 邮件发送失败，5 分钟后重发

### 补偿

更偏业务修复：

- 主流程没有完整闭环，后续按业务规则把状态补回去

例如：

- 支付平台已经成功，但本地订单仍是待支付

所以可以把它们理解成：

- 重试偏“动作再来一次”
- 补偿偏“业务状态修回来”

## 4. 为什么补偿任务不是越多越好

这是一个很重要的工程判断。  
补偿任务确实很有价值，但它并不意味着：

- 主流程可以随便设计
- 反正后面再补就行

这是一种非常危险的思路。

更合理的关系应该是：

1. 主流程尽量正确
2. 补偿任务作为兜底

也就是说：

- 补偿任务是“最后一道保险”
- 不是“默认执行路径”

## 5. 补偿任务的核心设计原则

我建议补偿任务至少满足下面这些原则：

1. 补偿对象定义清晰  
必须明确“哪些数据属于该补偿任务负责修复的范围”。

2. 补偿条件明确  
不能模模糊糊扫一堆数据就改。

3. 补偿动作可幂等  
因为补偿任务通常会重复跑。

4. 补偿失败可记录  
否则你根本不知道哪些一直没修好。

5. 补偿结果可追踪  
至少要知道补偿过没有、补偿成功没有。

## 6. 典型流程

以“支付成功但订单状态未更新”为例，补偿流程通常如下：

1. 定时扫描“支付单已成功、订单仍待支付”的数据
2. 逐条核对是否真的应该改状态
3. 更新订单状态为已支付
4. 记录补偿日志
5. 如果失败，记录失败原因，下次继续扫

这个流程的重点不在“扫”，而在：

- 用明确的业务不一致条件筛出问题数据

## 7. 核心代码

## 7.1 支付补偿任务核心实现

```java
@Component
public class PayOrderCompensateJob {

    private final PayOrderMapper payOrderMapper;
    private final OrderMapper orderMapper;
    private final CompensateLogMapper compensateLogMapper;

    public PayOrderCompensateJob(
            PayOrderMapper payOrderMapper,
            OrderMapper orderMapper,
            CompensateLogMapper compensateLogMapper) {
        this.payOrderMapper = payOrderMapper;
        this.orderMapper = orderMapper;
        this.compensateLogMapper = compensateLogMapper;
    }

    @Scheduled(fixedDelay = 300000)
    public void execute() {
        List<PayOrder> payOrders = payOrderMapper.selectPaidButOrderNotUpdated();
        for (PayOrder payOrder : payOrders) {
            try {
                Order order = orderMapper.selectById(payOrder.getOrderId());
                if (order == null) {
                    continue;
                }
                if (!"WAIT_PAY".equals(order.getStatus())) {
                    continue;
                }

                Order update = new Order();
                update.setId(order.getId());
                update.setStatus("PAID");
                update.setPayTime(payOrder.getPayTime());
                orderMapper.updateById(update);

                saveCompensateLog("PAY_ORDER_STATUS", payOrder.getId(), "SUCCESS", null);
            } catch (Exception ex) {
                saveCompensateLog("PAY_ORDER_STATUS", payOrder.getId(), "FAIL", ex.getMessage());
            }
        }
    }

    private void saveCompensateLog(String taskType, Long bizId, String status, String failReason) {
        CompensateLog log = new CompensateLog();
        log.setTaskType(taskType);
        log.setBizId(bizId);
        log.setStatus(status);
        log.setFailReason(failReason);
        log.setCreateTime(LocalDateTime.now());
        compensateLogMapper.insert(log);
    }
}
```

这段代码看起来像个“扫表更新”，但它背后体现的是补偿任务最核心的设计：

- 用业务不一致条件筛数据
- 按业务规则修复
- 不论成功失败都留痕

## 8. 为什么补偿任务必须幂等

因为补偿任务天然就会重复执行。  
例如：

- 每 5 分钟扫一次
- 这次没补成功，下次还会再扫到

如果补偿逻辑不幂等，就可能造成新的问题：

- 已发过的积分再发一次
- 已回滚的库存再回滚一次
- 已经成功的状态被重复推进

所以补偿任务的一个黄金原则就是：

- 任何补偿动作都应该能“重复看见、重复判断，但不重复造成副作用”

## 9. 补偿任务的本质不是“扫全表”

很多人第一次写补偿任务，喜欢直接：

- 把整张表扫一遍

这在小系统里也许能跑，但工程上并不好。  
更成熟的做法应该是：

1. 定义异常状态
2. 精准筛选问题数据
3. 控制单次补偿量

例如：

- 只扫最近 1 天的异常支付数据
- 只扫状态明显不一致的数据
- 每次只处理 500 条

这样才能既补得稳，又不拖垮主库。

## 10. 补偿和人工介入的关系

不是所有补偿都应该全自动完成。  
有些异常数据可能涉及：

- 金额风险
- 外部渠道结果不明确
- 业务冲突

这类数据更合理的做法可能是：

1. 补偿任务发现异常
2. 记录到异常表或工单
3. 人工复核后再决定是否补

所以补偿任务本身也要分层：

- 自动补偿
- 发现异常转人工

## 11. 补偿任务和对账任务的关系

这两个能力经常一起出现。

### 对账

更偏：

- 发现差异

### 补偿

更偏：

- 修复差异

例如：

- 对账发现支付平台成功、本地失败
- 补偿任务再把本地订单修正为已支付

所以在很多系统里：

- 对账是发现问题的眼睛
- 补偿是修复问题的手

## 12. 常见坑点

### 12.1 补偿条件定义模糊

容易误改正常数据。

### 12.2 补偿逻辑不幂等

补一次可能变成二次事故。

### 12.3 补偿失败不记录

后面没人知道哪批数据一直修不好。

### 12.4 过度依赖补偿任务

把它当主流程替代品是很危险的。

## 13. 总结

补偿任务的核心，不是“再跑一遍代码”，而是围绕业务不一致状态，建立一套能精准识别、可幂等修复、失败可追踪的兜底机制。

一个成熟的补偿任务实现至少应该做到：

- 补偿对象边界清晰
- 补偿动作按业务规则执行
- 补偿过程可幂等
- 补偿成功失败可追踪

这才是分布式业务系统里真正靠谱的补偿能力。
