# 延迟任务实现

## 1. 功能定义

延迟任务要解决的问题是：

- 某个业务动作不是现在立刻执行，而是在未来某个时间点自动执行一次

这类任务在业务系统里非常常见，而且它和定时任务有明显区别：

- 定时任务强调“固定规则反复执行”
- 延迟任务强调“针对某个具体对象，在未来时间点执行一次”

最典型的例子就是：

- 订单创建 30 分钟后未支付自动关闭

这不是每天固定执行，也不是每小时固定执行，而是：

- 某一笔订单自己的未来时间点任务

## 2. 为什么延迟任务很重要

很多业务规则天然就是“稍后处理”，例如：

- 订单超时未支付自动取消
- 优惠券到期自动失效
- 审批超时自动催办
- 预约开始前 10 分钟发送提醒
- 活动截止后自动开奖

如果系统没有延迟任务能力，这些规则通常只能通过：

- 高频定时扫描数据库

来实现。  
扫描虽然能做，但并不总是最优解，尤其在数据量大、时效要求高时更明显。

## 3. 延迟任务和定时任务的真正区别

这个点一定要搞清楚。

### 定时任务

是：

- 某个逻辑按照固定时间周期执行

例如：

- 每分钟执行一次关单扫描

### 延迟任务

是：

- 某个对象在未来某个时刻触发一次

例如：

- 订单 5001 在 30 分钟后关单
- 订单 5002 在 30 分钟后关单

也就是说：

- 定时任务关注“任务自身的时间规则”
- 延迟任务关注“业务对象的到期时间”

## 4. 常见实现方式

延迟任务常见有几种做法。

### 4.1 定时扫描数据库

例如：

- 每分钟扫描一次 `expire_time <= now` 的订单

优点：

- 实现简单

缺点：

- 扫描成本会随数据量增长
- 实时性一般

### 4.2 Redis 有序集合

把待执行任务按时间戳放进 `ZSET`，定时取到期任务。

优点：

- 适合轻量任务

缺点：

- 需要自己维护取任务、幂等、补偿

### 4.3 MQ 延迟消息

例如：

- RabbitMQ TTL + 死信队列
- RocketMQ 延迟消息

优点：

- 和业务解耦
- 更适合事件驱动型场景

缺点：

- 需要配套消息可靠性治理

### 4.4 调度平台

例如：

- 调度中心注册一条未来执行任务

适合更复杂、更强可管理场景。

## 5. 延迟任务最典型的工程思路

在很多 Java 后端项目里，最常见的做法通常是：

1. 主业务完成后发送一条延迟消息
2. 到时间后消费这条消息
3. 消费时重新检查业务状态
4. 条件仍然成立才真正执行

这是一条非常稳、非常经典的延迟任务链路。

## 6. 典型流程

以“超时未支付关单”为例：

1. 用户创建订单
2. 系统写订单主表
3. 系统发送一条“30 分钟后检查订单是否超时”的延迟消息
4. 30 分钟后消息到达消费者
5. 消费者查询订单当前状态
6. 如果仍是 `WAIT_PAY`，则关单
7. 如果已经支付，直接忽略

注意这里最重要的一步不是“到时间关闭”，而是：

- 到时间后重新确认条件是否还成立

## 7. 核心设计

延迟任务实现时，我建议重点考虑：

1. 延迟时间怎么表达
2. 任务到点后由谁执行
3. 执行时如何校验业务状态
4. 任务丢失后有没有补偿
5. 执行动作是否幂等

其中第 3 点是整个延迟任务体系最重要的一点。

因为：

- 发送延迟任务时的业务状态
- 和未来真正执行时的业务状态

很可能已经不一样了。

## 8. 核心代码

## 8.1 发送延迟消息

下面用 RabbitMQ TTL + 死信转发思路举例。

```java
@Service
public class DelayTaskPublisher {

    private final RabbitTemplate rabbitTemplate;

    public DelayTaskPublisher(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    public void publishCloseOrderDelay(Long orderId) {
        rabbitTemplate.convertAndSend(
                "delay.order.exchange",
                "delay.order.close",
                orderId,
                message -> {
                    message.getMessageProperties().setExpiration(String.valueOf(30 * 60 * 1000));
                    return message;
                }
        );
    }
}
```

这段代码的意义很明确：

- 下单成功后，不直接关单
- 只是在消息系统里约一个“30 分钟后再处理”的动作

## 8.2 到期消费执行

```java
@Component
public class CloseOrderDelayConsumer {

    private final OrderMapper orderMapper;
    private final OrderCancelService orderCancelService;

    public CloseOrderDelayConsumer(
            OrderMapper orderMapper,
            OrderCancelService orderCancelService) {
        this.orderMapper = orderMapper;
        this.orderCancelService = orderCancelService;
    }

    @RabbitListener(queues = "order.close.delay.queue")
    public void consume(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            return;
        }
        if (!"WAIT_PAY".equals(order.getStatus())) {
            return;
        }

        orderCancelService.cancel(orderId, "支付超时自动取消", 0L);
    }
}
```

这里最核心的设计是：

- 消费时重新查单
- 只有状态仍然满足条件才执行

这就是延迟任务里非常典型的：

- 到期触发 + 状态二次确认

## 9. 为什么延迟任务必须做状态校验

因为从“发出任务”到“真正执行”，业务可能已经变化了。  
比如：

1. 下单时是待支付
2. 延迟任务还没触发时用户已经支付成功
3. 这时候如果你到点就直接关单，就会出事故

所以延迟任务一定不能理解成：

- 到点就无脑执行

而应该理解成：

- 到点后尝试执行
- 真正执行前先看业务是否还满足条件

## 10. 延迟任务为什么也需要幂等

因为在真实项目里，以下情况都可能导致同一个延迟动作被重复触发：

- MQ 重投
- 消费者处理超时
- 人工补偿重复下发
- 定时扫描兜底和延迟消息同时命中

例如超时关单场景，如果订单已经关闭，再收到一次同样的关单任务，应该直接忽略，而不是再次改状态、再次回滚库存。

所以延迟任务执行逻辑本身，最好具备：

- 状态幂等

## 11. 延迟任务丢失怎么办

这是延迟任务设计里非常现实的问题。  
很多系统如果只依赖延迟消息主链路，一旦出现：

- 消息发送失败
- 消息积压
- 消息丢失

就会造成延迟任务彻底漏执行。

所以更稳的工程方案通常是：

1. 延迟消息作为主路径
2. 定时扫描作为兜底路径

例如：

- 正常情况下靠 MQ 延迟关单
- 每 10 分钟再扫一次“超时未支付仍未关闭的订单”做补偿

这就是典型的：

- 主流程异步
- 补偿流程兜底

## 12. 延迟任务和定时扫描怎么选

可以这样简单判断：

### 更适合延迟任务的场景

- 每个业务对象都有明确到期时刻
- 希望触发更及时
- 触发量大但逻辑相对统一

例如：

- 超时关单
- 券到期失效

### 更适合定时扫描的场景

- 实时性要求不高
- 数据量相对可控
- 逻辑更像周期巡检

例如：

- 每 10 分钟扫一次异常订单

正式项目里，往往不是二选一，而是：

- 延迟任务为主
- 定时扫描补偿

## 13. 常见坑点

### 13.1 到时间后直接执行，不校验业务状态

这是延迟任务最危险的问题之一。

### 13.2 完全依赖延迟消息，没有兜底补偿

链路一旦漏掉就没人发现。

### 13.3 把所有延迟需求都做成高频扫库

随着数据量增长，数据库压力会越来越大。

### 13.4 不做幂等

重复消息或重复补偿很容易造成二次事故。

## 14. 总结

延迟任务的核心，不是“晚点执行一下代码”，而是围绕具体业务对象，在未来时间点触发一次带状态校验、可幂等、可补偿的后台动作。

一个成熟的延迟任务实现通常应该做到：

- 到期时间表达清晰
- 执行前重新校验业务状态
- 重复触发可幂等
- 主触发链路之外有补偿兜底

这才是后端系统里真正稳定可用的延迟任务能力。
