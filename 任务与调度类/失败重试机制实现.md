# 失败重试机制实现

## 1. 功能定义

失败重试机制要解决的问题是：

- 某个任务、调用或异步动作执行失败后，系统如何在可控范围内再次尝试，而不是一次失败就永久放弃

在真实系统里，很多失败并不是永久性的。  
例如：

- 网络抖动
- 第三方服务短时不可用
- 数据库瞬时锁冲突
- 邮件服务器短时超时

这类失败如果完全不重试，系统会变得很脆弱；  
但如果无脑重试，又会把系统拖进另一个坑。

所以失败重试真正要解决的，不是“有没有再来一次”，而是：

- 怎么有节制地再来一次

## 2. 哪些场景最需要失败重试

最常见的场景包括：

1. 短信发送失败
2. 邮件发送失败
3. MQ 消费处理失败
4. 外部接口调用失败
5. 批处理某批任务执行失败

这些场景有一个共性：

- 失败通常是暂时性的
- 再试一次有可能成功

## 3. 为什么不能无脑重试

因为很多失败根本不适合重试。  
例如：

- 手机号格式错误
- 业务对象不存在
- 参数缺失
- 逻辑条件不满足

这种错误就算再试 100 次，也不会变成功。  
如果无脑重试，只会带来：

- 无意义资源消耗
- 失败任务堆积
- 下游压力更大

所以一个成熟的重试系统，首先要学会区分：

- 临时失败
- 确定性失败

## 4. 失败重试和补偿的区别

这两个概念很接近，但层级还是不同。

### 失败重试

更偏技术层：

- 某个动作没成功，再试几次

### 补偿任务

更偏业务层：

- 主流程没闭环，后面按业务规则修回来

例如：

- 邮件没发成功，重发一次，这是重试
- 支付成功但订单没改状态，后续修状态，这是补偿

所以第八类里这两篇文档最好是配合看，而不是互相替代。

## 5. 核心设计

失败重试机制实现时，建议先明确下面这几个问题：

1. 哪些异常允许重试
2. 最多重试几次
3. 每次间隔多长
4. 重试任务状态如何记录
5. 最终失败后怎么处理

这五个问题如果不提前设计清楚，重试机制基本会越做越乱。

## 6. 常见重试策略

最常见的策略包括：

### 6.1 固定间隔重试

例如：

- 每 5 分钟重试一次，最多 3 次

优点：

- 简单

缺点：

- 不够灵活

### 6.2 指数退避重试

例如：

- 第 1 次 1 分钟后
- 第 2 次 5 分钟后
- 第 3 次 30 分钟后

优点：

- 对下游更友好

### 6.3 限次重试后转人工

适合：

- 强业务型失败任务
- 不能无限自动化处理的场景

## 7. 典型数据结构

一个比较完整的重试任务记录通常至少包括：

```json
{
  "id": 1,
  "taskType": "MAIL_SEND",
  "bizId": 90001,
  "payload": "{...}",
  "retryCount": 2,
  "maxRetryCount": 5,
  "nextRetryTime": "2026-06-02 15:00:00",
  "status": "WAIT_RETRY",
  "failReason": "SMTP timeout"
}
```

这些字段的意义分别是：

- `taskType`：重试任务类型
- `bizId`：关联业务主键
- `payload`：任务原始参数
- `retryCount`：当前已重试次数
- `maxRetryCount`：最大重试次数
- `nextRetryTime`：下一次触发时间
- `status`：当前状态
- `failReason`：最后一次失败原因

这张记录表，本质上就是重试机制的“大脑”。

## 8. 核心代码

## 8.1 记录失败任务

```java
@Service
public class RetryTaskServiceImpl implements RetryTaskService {

    private final RetryTaskMapper retryTaskMapper;

    public RetryTaskServiceImpl(RetryTaskMapper retryTaskMapper) {
        this.retryTaskMapper = retryTaskMapper;
    }

    @Override
    public void saveRetryTask(String taskType, Long bizId, String payload, String failReason) {
        RetryTask task = new RetryTask();
        task.setTaskType(taskType);
        task.setBizId(bizId);
        task.setPayload(payload);
        task.setRetryCount(0);
        task.setMaxRetryCount(5);
        task.setStatus("WAIT_RETRY");
        task.setNextRetryTime(LocalDateTime.now().plusMinutes(1));
        task.setFailReason(failReason);
        retryTaskMapper.insert(task);
    }
}
```

这一步的核心不是“插一条记录”，而是：

- 把本次失败正式纳入后续恢复体系

## 8.2 定时执行重试任务

```java
@Component
public class RetryTaskJob {

    private final RetryTaskMapper retryTaskMapper;
    private final MailService mailService;

    public RetryTaskJob(RetryTaskMapper retryTaskMapper, MailService mailService) {
        this.retryTaskMapper = retryTaskMapper;
        this.mailService = mailService;
    }

    @Scheduled(fixedDelay = 60000)
    public void execute() {
        List<RetryTask> tasks = retryTaskMapper.selectReadyRetryTasks(LocalDateTime.now());
        for (RetryTask task : tasks) {
            try {
                MailSendRequest request = JSON.parseObject(task.getPayload(), MailSendRequest.class);
                mailService.send(request);

                RetryTask update = new RetryTask();
                update.setId(task.getId());
                update.setStatus("SUCCESS");
                update.setRetryCount(task.getRetryCount() + 1);
                retryTaskMapper.updateById(update);
            } catch (Exception ex) {
                int nextCount = task.getRetryCount() + 1;
                RetryTask update = new RetryTask();
                update.setId(task.getId());
                update.setRetryCount(nextCount);
                update.setFailReason(ex.getMessage());

                if (nextCount >= task.getMaxRetryCount()) {
                    update.setStatus("FAIL");
                } else {
                    update.setStatus("WAIT_RETRY");
                    update.setNextRetryTime(LocalDateTime.now().plusMinutes(5));
                }

                retryTaskMapper.updateById(update);
            }
        }
    }
}
```

这段代码展示的是失败重试最核心的一条链路：

1. 找到到点可重试的任务
2. 再执行一次
3. 成功则结束
4. 失败则更新次数和下次时间
5. 超过次数则转最终失败

## 9. 为什么重试状态一定要持久化

因为失败重试通常不是一次性内存动作。  
它会跨越：

- 多次调度
- 多次重启
- 多次任务扫描

如果状态不落库或不持久化，你就无法回答：

- 这个任务已经试了几次
- 还要不要继续试
- 上次为什么失败

所以失败重试真正的关键不是“再调一次方法”，而是：

- 让重试任务具备状态生命周期

## 10. 为什么重试策略最好不是固定死的

因为不同任务对失败的容忍度不一样。  
例如：

- 验证码短信：强调及时性，重试次数不宜太多
- 报表邮件：允许晚一点到，重试策略可以更宽松
- 核心回调通知：失败要高度关注，甚至需要补偿升级

所以更成熟的设计通常会让不同任务类型拥有不同重试策略，例如：

- `taskType -> maxRetryCount -> retryInterval`

## 11. 为什么最终失败状态也很重要

很多系统只关心：

- 成功
- 等待重试

但真正要治理任务时，还必须有：

- 最终失败

因为你总得知道：

- 哪些任务系统已经尽力了但还是没成功

这时候它们可能需要：

- 人工处理
- 死信归档
- 补偿升级

## 12. 重试和死信的关系

失败重试和死信机制通常是串联关系：

1. 失败先进入重试
2. 重试超过上限
3. 转入最终失败或死信队列

也就是说：

- 重试是“给你几次恢复机会”
- 死信是“机会用完了，转治理”

## 13. 常见坑点

### 13.1 所有失败都重试

这会造成大量无意义重试。

### 13.2 无限重试

容易把系统拖进更深的故障里。

### 13.3 不记录失败原因

出了问题很难判断到底为什么一直失败。

### 13.4 成功后不及时结束任务状态

会造成重复重试。

## 14. 总结

失败重试机制的核心，不是“失败了再跑一次”，而是围绕失败任务建立一套：

- 有边界
- 有次数
- 有节奏
- 有状态
- 有终态

的恢复机制。

一个成熟的失败重试实现至少应该做到：

- 只对值得重试的异常开放重试
- 重试次数和间隔可配置
- 任务状态全程可追踪
- 超过上限后转最终失败治理

这才是真正稳定、可运营的失败重试体系。
