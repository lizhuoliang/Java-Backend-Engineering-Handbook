# 数据归档实现

## 1. 功能定义

数据归档要解决的问题是：

- 当系统历史数据越来越多时，如何把不再高频使用但仍需保留的数据，从主业务表中迁移到更适合长期保存的位置

这是很多系统发展到一定阶段后必然会面对的问题。  
因为只要业务持续运行，订单、日志、消息、行为数据都会不断累积。

如果什么都一直放在主表里，通常会出现：

1. 表越来越大
2. 查询和索引越来越慢
3. 运维成本越来越高

所以数据归档本质上是在做：

- 热数据和冷数据分层

## 2. 为什么数据归档不是“直接删除”

因为很多历史数据虽然不常用，但仍然有价值。  
例如：

- 历史订单
- 历史对账数据
- 历史审计日志
- 合规保留数据

这些数据可能在：

- 财务复核
- 投诉处理
- 合规审计
- 数据分析

中仍然会被需要。  
所以归档的重点通常不是：

- 丢掉

而是：

- 迁走
- 分层保存

## 3. 哪些数据适合归档

最常见适合归档的数据通常有这些特征：

1. 体量大
2. 历史久
3. 查询频率低
4. 仍有保留价值

典型例子包括：

- 一年前的订单明细
- 半年前的操作日志
- 老的用户行为事件
- 历史消息推送记录

## 4. 常见归档方式

数据归档最常见的几种方式包括：

1. 主表迁移到归档表
2. 迁移到独立归档库
3. 导出到对象存储 / 冷存储
4. 进入数仓或离线分析系统

不同数据类型适合不同归档方式。  
例如：

- 业务单据更常归档到归档表或归档库
- 日志和行为数据更适合进离线存储或数仓

## 5. 核心设计

数据归档实现时，建议重点考虑：

1. 归档边界怎么定义  
按时间、按状态、按业务类型。

2. 归档后怎么查
3. 归档任务如何批量执行
4. 归档后主表数据是否删除
5. 归档是否需要校验和审计

这里最关键的一点通常是：

- 归档不是单纯技术搬运，而是数据生命周期管理

## 6. 典型流程

以“归档一年以前已完成订单”为例，典型流程通常如下：

1. 定时任务筛选符合条件的数据
2. 分批迁移到归档表
3. 校验迁移结果
4. 删除主表数据或做逻辑删除
5. 记录归档批次日志

## 7. 核心代码

## 7.1 归档任务核心实现

```java
@Component
public class OrderArchiveJob {

    private final OrderMapper orderMapper;
    private final OrderArchiveMapper orderArchiveMapper;

    public OrderArchiveJob(OrderMapper orderMapper, OrderArchiveMapper orderArchiveMapper) {
        this.orderMapper = orderMapper;
        this.orderArchiveMapper = orderArchiveMapper;
    }

    @Scheduled(cron = "0 0 3 * * ?")
    public void execute() {
        LocalDateTime archiveBefore = LocalDateTime.now().minusYears(1);
        long lastId = 0L;
        int batchSize = 500;

        while (true) {
            List<Order> list = orderMapper.selectArchiveOrders(archiveBefore, lastId, batchSize);
            if (list == null || list.isEmpty()) {
                break;
            }

            for (Order order : list) {
                OrderArchive archive = new OrderArchive();
                archive.setOrderId(order.getId());
                archive.setOrderNo(order.getOrderNo());
                archive.setUserId(order.getUserId());
                archive.setPayAmount(order.getPayAmount());
                archive.setStatus(order.getStatus());
                archive.setCreateTime(order.getCreateTime());
                orderArchiveMapper.insert(archive);
            }

            List<Long> ids = list.stream().map(Order::getId).toList();
            orderMapper.deleteBatchIds(ids);
            lastId = list.get(list.size() - 1).getId();
        }
    }
}
```

这段代码体现了归档任务里最核心的几个动作：

1. 筛选归档范围
2. 分批迁移
3. 迁移后清理主表

## 8. 为什么归档最好分批做

因为归档本质上就是一类批处理任务。  
如果一次性迁移太多数据，会带来：

1. 长事务
2. 大量锁竞争
3. 数据库压力大
4. 一旦失败回滚代价高

所以成熟的归档策略通常会：

- 分批归档
- 分阶段校验
- 低峰期执行

## 9. 归档后的查询怎么处理

这也是归档体系中非常关键的问题。  
如果数据一归档就完全查不到，业务很容易反过来抵触归档。

常见做法包括：

1. 前台只查主表，历史数据去归档查询入口
2. 管理后台提供“历史归档数据查询”
3. 对接统一数据查询层

也就是说：

- 归档后不是不能查
- 而是查法变了

## 10. 为什么归档前要先确认保留策略

因为并不是所有数据都适合同样保留方式。  
例如：

- 审计日志可能要保留多年
- 临时行为数据可能半年后就可清除

所以归档通常和：

- 数据保留周期
- 合规要求
- 分析价值

一起定义，而不是只靠技术拍脑袋。

## 11. 常见坑点

### 11.1 归档等同于删除

会丢失很多仍有价值的数据。

### 11.2 归档没有查询方案

业务会很难接受。

### 11.3 一次性归档太大批量

容易影响线上数据库。

### 11.4 没有归档记录和校验

后续很难确认哪些数据到底迁没迁成功。

## 12. 总结

数据归档的核心，不是“把旧数据清掉”，而是围绕数据冷热分层、存储成本、查询需求和保留要求，建立一套长期可持续的数据生命周期管理机制。

一个成熟的数据归档实现至少应该做到：

- 归档边界明确
- 分批迁移可控
- 主表减负和归档查询兼顾
- 保留策略和合规要求清晰

这才是数据分析与长期治理体系里真正完整的归档能力。
