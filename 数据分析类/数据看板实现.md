# 数据看板实现

## 1. 功能定义

数据看板要解决的问题是：

- 系统如何把分散、抽象的统计结果，组织成一组可视化、可快速理解的经营或运行视图

如果说业务统计负责：

- 算出数字

那么数据看板负责：

- 把数字组织成可阅读的决策界面

最常见的数据看板包括：

- 经营看板
- 订单看板
- 运营活动看板
- 系统运行看板

## 2. 为什么数据看板不是简单“多个接口拼一起”

因为一个真正可用的看板，通常不只是堆数字。  
它至少要解决：

1. 当前最重要的指标是什么
2. 指标之间怎么分组
3. 哪些看趋势，哪些看实时值
4. 哪些角色应该看到哪些内容

所以数据看板本质上是：

- 指标组织与呈现层

而不只是若干统计接口的列表。

## 3. 常见看板结构

一个典型的经营看板，通常会包含：

1. 核心概览卡片  
例如新增用户、订单数、成交额。

2. 趋势图  
例如近 7 天成交额趋势。

3. 排行榜  
例如商品销量 Top10。

4. 结构分布  
例如订单来源占比。

所以看板天然具有“聚合多指标”的特点。

## 4. 核心设计

数据看板实现时，建议重点考虑：

1. 看板面向谁  
老板、运营、财务、管理员，不同角色关注点不同。

2. 看板刷新频率多高
3. 是否需要多维筛选
4. 指标是否允许缓存
5. 数据权限是否影响看板结果

其中非常关键的一点是：

- 看板不是越全越好，而是越聚焦越有价值

## 5. 典型流程

一个看板接口通常会这样工作：

1. 接收时间范围、部门、业务线等筛选条件
2. 调用多个统计服务
3. 聚合出概览、趋势、分布、排行数据
4. 返回给前端可视化页面

## 6.2 看板聚合服务核心实现

```java
@Service
public class DashboardServiceImpl implements DashboardService {

    private final BusinessStatService businessStatService;
    private final OrderTrendReportService orderTrendReportService;
    private final ProductRankService productRankService;

    public DashboardServiceImpl(
            BusinessStatService businessStatService,
            OrderTrendReportService orderTrendReportService,
            ProductRankService productRankService) {
        this.businessStatService = businessStatService;
        this.orderTrendReportService = orderTrendReportService;
        this.productRankService = productRankService;
    }

    @Override
    public DashboardVO query(DashboardQueryRequest request) {
        DashboardVO vo = new DashboardVO();
        vo.setOverview(businessStatService.queryOverview(request));
        vo.setTrend(orderTrendReportService.queryTrend(request));
        vo.setTopProducts(productRankService.topProducts(request));
        return vo;
    }
}
```

这段代码体现了看板层的关键角色：

- 它自己不一定计算所有指标
- 而是做多个统计服务的聚合编排

## 7. 为什么看板接口通常适合做缓存

因为看板有几个典型特点：

1. 被多人频繁查看
2. 同一时间范围条件重复率高
3. 不是每秒都必须强实时

所以很多看板类接口都适合加一层短期缓存，例如：

- 30 秒
- 1 分钟
- 5 分钟

这样既能保证体验，也能减轻数据库和统计服务压力。

## 8. 为什么数据权限会影响看板

很多系统里的看板并不是所有人看见同一份数据。  
例如：

- 总部能看全量数据
- 区域经理只能看本区域
- 部门负责人只能看本部门

所以看板实现通常不能只关注前端展示，而要考虑：

- 看板背后查询条件是否受数据权限约束

## 9. 看板和报表的区别

它们关系很近，但定位不同。

### 看板

更偏：

- 快速概览
- 实时观察
- 指标可视化

### 报表

更偏：

- 详细导出
- 深入分析
- 离线查看

可以简单理解为：

- 看板是“抬头看”
- 报表是“低头细看”

## 10. 常见坑点

### 10.1 看板把所有统计都实时查一遍

随着指标增多，性能压力会很大。

### 10.2 看板指标堆得太多

用户反而抓不到重点。

### 10.3 看板和统计口径不一致

同一个指标在不同地方看到不同数，会失去信任。

### 10.4 没有按角色控制看板范围

容易造成越权看数。

## 11. 总结

数据看板的核心，不是“做几个图表”，而是把多个关键指标按角色、按场景组织成一组可快速理解、可持续观测的分析视图。

一个成熟的数据看板实现至少应该做到：

- 看板目标明确
- 指标来源统一
- 聚合层和统计层分离
- 缓存与权限治理到位

这才是看板真正对业务有用的地方。
