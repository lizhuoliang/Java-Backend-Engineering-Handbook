# 业务统计实现

## 1. 功能定义

业务统计要解决的问题是：

- 系统如何把分散在订单、支付、用户、活动、消息等业务数据中的关键指标提炼出来，用来描述当前业务运行状态

它和普通查询的区别在于：

- 普通查询更关注“具体记录”
- 业务统计更关注“整体结果”

例如：

- 今日新增用户数
- 今日订单数
- 今日支付金额
- 本周退款率
- 某活动参与人数

这些都属于典型的业务统计指标。

## 2. 为什么业务统计很重要

因为很多系统即使功能都能用，如果不能回答下面这些问题，其实也很难真正支撑运营和管理：

- 今天业务增长了吗
- 哪个模块转化率低了
- 哪类订单异常变多了
- 某活动到底有没有效果

所以业务统计其实是系统从“能跑业务”走向“能理解业务”的第一步。

## 3. 业务统计通常统计什么

最常见的统计维度包括：

1. 用户维度  
新增、活跃、留存、登录次数。

2. 交易维度  
订单数、支付金额、退款率、客单价。

3. 内容维度  
文章发布数、阅读量、互动量。

4. 运营维度  
活动参与人数、优惠券使用率、消息触达率。

所以业务统计并不是某一个模块的能力，而是一种横跨多个业务域的统一分析方式。

## 4. 核心设计

业务统计实现时，建议重点考虑：

1. 统计口径是否明确
2. 指标是实时查还是离线汇总
3. 数据来源是哪几张表
4. 结果给谁看
5. 统计结果是否要落表

这里最关键的一点通常是：

- 统计口径一定要先说清楚

例如“今日成交额”到底指：

- 下单金额
- 支付金额
- 已完成订单金额

如果口径不明确，系统统计出来的数字即使技术上没错，业务上也会一直有争议。

## 5. 常见统计实现方式

### 5.1 实时统计

直接查业务表现算。

适合：

- 数据量不大
- 指标简单
- 对实时性要求高

### 5.2 离线汇总统计

定时把结果写入统计表。

适合：

- 数据量大
- 查询频繁
- 指标复杂

很多正式项目里，两者会混合使用。

## 6. 核心代码

## 6.1 一个基础业务统计接口

下面用“今日经营概览”举例。

```java
@RestController
@RequestMapping("/stat")
public class BusinessStatController {

    private final BusinessStatService businessStatService;

    public BusinessStatController(BusinessStatService businessStatService) {
        this.businessStatService = businessStatService;
    }

    @GetMapping("/today-overview")
    public Result<TodayOverviewVO> todayOverview() {
        return Result.success(businessStatService.todayOverview());
    }
}
```

## 6.2 实时统计核心实现

```java
@Service
public class BusinessStatServiceImpl implements BusinessStatService {

    private final UserMapper userMapper;
    private final OrderMapper orderMapper;
    private final PayOrderMapper payOrderMapper;

    public BusinessStatServiceImpl(
            UserMapper userMapper,
            OrderMapper orderMapper,
            PayOrderMapper payOrderMapper) {
        this.userMapper = userMapper;
        this.orderMapper = orderMapper;
        this.payOrderMapper = payOrderMapper;
    }

    @Override
    public TodayOverviewVO todayOverview() {
        LocalDateTime start = LocalDate.now().atStartOfDay();
        LocalDateTime end = LocalDate.now().plusDays(1).atStartOfDay();

        Long newUserCount = userMapper.countByCreateTimeRange(start, end);
        Long orderCount = orderMapper.countByCreateTimeRange(start, end);
        BigDecimal payAmount = payOrderMapper.sumSuccessPayAmountByTimeRange(start, end);

        TodayOverviewVO vo = new TodayOverviewVO();
        vo.setNewUserCount(newUserCount == null ? 0L : newUserCount);
        vo.setOrderCount(orderCount == null ? 0L : orderCount);
        vo.setPayAmount(payAmount == null ? BigDecimal.ZERO : payAmount);
        return vo;
    }
}
```

这段代码体现的是最基础的“实时汇总查询”思路。

## 7. 为什么很多统计最终要沉淀成统计表

因为随着业务量增长，很多统计查询会越来越重。  
例如：

- 按天、按部门、按商品分类、多维度统计近一年的订单数据

如果每次都实时扫大表，数据库压力会非常高。  
所以成熟系统往往会逐步走向：

1. 定时计算
2. 落统计结果表
3. 前台查统计表

这就是从“查业务表”走向“查分析结果表”的过程。

## 8. 为什么业务统计不能只看技术实现

因为业务统计非常依赖“指标定义”。  
例如：

- 活跃用户怎么定义
- 有效订单怎么定义
- 支付成功率的分母是什么

如果这些定义没统一，再漂亮的接口和 SQL 也很难形成可信的数据体系。

所以很多成熟团队在做业务统计时，都会同步维护：

- 指标口径文档

## 9. 常见坑点

### 9.1 统计口径不统一

这是业务统计里最典型的问题。

### 9.2 所有统计都实时扫大表

数据量一大，性能会迅速恶化。

### 9.3 只给结果，不记录计算来源

后续很难解释数字为什么是这样。

### 9.4 业务统计和数据权限脱节

不同部门看到的数据可能不该完全一样。

## 10. 总结

业务统计的核心，不是“写几条 count 和 sum”，而是围绕业务口径、指标体系和查询性能，建立一套对业务运行状态的量化描述能力。

一个成熟的业务统计实现至少应该做到：

- 统计口径清晰
- 指标来源明确
- 小统计可实时，大统计可汇总
- 输出结果便于后续看板和报表复用

这才是真正有管理价值的业务统计体系。
