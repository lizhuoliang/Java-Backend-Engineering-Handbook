# 报表导出实现

## 1. 功能定义

报表导出要解决的问题是：

- 系统如何把已经查询或统计好的分析结果，以文件形式导出给用户进行离线查看、分享、归档或二次处理

它和前面“基础数据管理类”里的“批量导出”有联系，但这里更偏：

- 分析结果导出
- 报表型导出

也就是说，这一篇强调的不是普通列表导出，而是：

- 带统计口径、带筛选条件、面向管理和分析的报表导出

## 2. 为什么报表导出在数据分析里很重要

因为很多分析结果不只是要在页面上看，还要进一步被：

- 下载留档
- 发给领导
- 发给财务
- 交给合作方

所以报表导出常常是：

- 看板展示之后的离线延伸能力

## 3. 常见导出形式

最常见的导出格式包括：

1. `Excel`
2. `CSV`
3. `PDF`

其中：

- `Excel` 最适合结构化表格
- `CSV` 最轻量
- `PDF` 更适合固定排版报表

大多数后台系统里，最常见的仍然是：

- Excel / CSV

## 4. 核心设计

报表导出实现时，建议重点考虑：

1. 导出数据是否和页面查询条件一致
2. 导出字段是否可控
3. 数据量大时是否异步导出
4. 导出是否受权限控制
5. 导出结果是否要记录日志

这里最关键的一点通常是：

- 导出不能变成“绕过权限的大口子”

很多系统页面看数据受控，但导出却把全量数据直接放出去了，这非常危险。

## 5. 典型流程

一个典型报表导出流程通常如下：

1. 用户在页面上选择筛选条件
2. 点击导出
3. 系统用同样的条件查询报表数据
4. 组装导出文件
5. 返回下载或生成异步导出任务

## 6. 核心代码

## 6.1 小数据量同步导出示例

下面用 CSV 报表示意：

```java
@GetMapping("/report/order/export")
public void export(OrderTrendReportRequest request, HttpServletResponse response) throws IOException {
    List<OrderTrendReportVO> list = orderReportService.trend(request);

    response.setContentType("text/csv;charset=UTF-8");
    response.setCharacterEncoding("UTF-8");
    response.setHeader("Content-Disposition", "attachment; filename=order-report.csv");

    try (PrintWriter writer = response.getWriter()) {
        writer.println("日期,订单数,支付金额");
        for (OrderTrendReportVO item : list) {
            writer.printf("%s,%d,%s%n",
                    item.getDate(),
                    item.getOrderCount(),
                    item.getPayAmount());
        }
    }
}
```

这段代码的关键不是 CSV 本身，而是：

- 导出使用的条件和统计查询复用同一套模型

## 7. 为什么导出条件必须和页面统计一致

因为用户通常是：

- 先筛选
- 再看结果
- 再点击导出

如果页面上看到的是 A，导出的却是 B，就会严重影响用户信任。  
所以更稳的做法通常是：

- 看板 / 报表查询和导出共用同一套 QueryRequest

## 8. 大报表为什么经常要异步导出

因为分析型报表经常存在这些特征：

- 时间跨度大
- 数据量大
- 聚合复杂
- 导出字段多

这时候同步导出很容易带来：

- 接口超时
- 内存压力大
- 用户体验差

所以正式项目里很常见的做法是：

1. 用户发起导出申请
2. 系统创建导出任务
3. 后台异步生成文件
4. 用户稍后下载

这类模式本质上已经和“批处理任务”很接近。

## 9. 为什么报表导出要留操作日志

因为报表导出通常涉及：

- 业务敏感数据
- 大批量数据离线流转

所以它往往不仅是一个功能点，也是一类需要审计的行为。  
系统通常应该至少记录：

- 谁导出的
- 导出了什么报表
- 用了什么筛选条件
- 什么时候导出的

## 10. 常见坑点

### 10.1 页面和导出使用两套查询逻辑

最终结果经常对不上。

### 10.2 大报表也同步导出

很容易超时或拖垮服务。

### 10.3 导出不校验权限

会变成严重的数据泄露入口。

### 10.4 没有导出审计

后续很难知道哪些人导出了敏感数据。

## 11. 总结

报表导出的核心，不是“生成一个文件”，而是把分析结果在保证口径一致、权限可控、规模可承受的前提下，可靠地输出给用户进行离线使用。

一个成熟的报表导出实现至少应该做到：

- 导出查询和页面查询口径一致
- 小报表可同步，大报表可异步
- 导出权限和审计到位
- 导出结果便于后续追踪

这才是真正有分析价值和治理价值的报表导出能力。
