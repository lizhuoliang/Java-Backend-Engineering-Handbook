# 操作日志实现

## 1. 功能定义

操作日志要解决的问题是：

- 系统里的用户、管理员、运营人员做了什么操作，系统如何把这些动作记录下来，供后续查询、审计、分析和问题追溯

很多人第一次做操作日志，会把它理解成：

- 某个接口被调用过一次

但在工程化系统里，操作日志的价值远不止“留痕”。  
它至少还承担几种作用：

1. 问题追溯  
某条数据为什么变了，是谁改的。

2. 审计合规  
某些敏感操作必须可查。

3. 运营分析  
哪些功能被用得多，哪些功能几乎没人点。

4. 异常识别  
某个账号是否短时间做了大量异常操作。

所以操作日志本质上是：

- 用户行为和系统操作的基础事件数据

## 2. 操作日志和审计日志的区别

这两个概念很像，但可以这样理解：

- 操作日志：范围更广，记录普通业务操作
- 审计日志：范围更严，聚焦高风险敏感操作

也就是说：

- 审计日志通常是操作日志中的“高等级子集”

例如：

- 查询列表、编辑资料，这些更像普通操作日志
- 删除用户、改角色、重置密码，更偏审计日志

## 3. 一个操作日志通常记录什么

一个比较实用的操作日志，通常至少包括：

```json
{
  "userId": 101,
  "username": "admin",
  "module": "订单管理",
  "operationType": "UPDATE",
  "bizId": 90001,
  "description": "修改订单备注",
  "clientIp": "10.0.0.1",
  "createTime": "2026-06-02 18:00:00"
}
```

如果系统要求更高，还会继续扩展：

- 请求路径
- 请求参数摘要
- 响应结果
- 操作耗时
- 操作前后差异

## 4. 为什么操作日志是数据分析类的一部分

因为操作日志不只是“给开发排错用”，它也是非常重要的分析数据来源。  
例如：

- 哪个功能使用率最高
- 哪个模块几乎没人用
- 某类操作在什么时候最活跃
- 某些敏感操作是否集中发生在特定账号

所以操作日志一旦做得规范，后面就可以自然衍生出：

- 使用行为统计
- 管理员行为分析
- 异常操作识别

## 5. 核心设计

操作日志实现时，建议重点考虑：

1. 记录哪些操作
2. 日志字段是否统一
3. 日志是否要异步落库
4. 是否保留请求上下文
5. 是否和行为分析体系打通

这里最重要的一点通常是：

- 操作日志要尽量结构化

否则后续很难做统计和检索。

## 6. 典型记录方式

在 Java 项目里，最常见的做法通常有两种：

1. 业务里手工记录
2. 用注解 + AOP 自动记录

手工记录更灵活，AOP 更统一。  
大多数系统最终会组合使用：

- 普通操作用注解切面统一记录
- 关键复杂操作单独补充业务字段

## 7. 核心代码

## 7.1 定义操作日志注解

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface OperationLog {

    String module();

    String type();

    String description() default "";
}
```

## 7.2 切面统一记录操作日志

```java
@Aspect
@Component
public class OperationLogAspect {

    private final OperationLogMapper operationLogMapper;

    public OperationLogAspect(OperationLogMapper operationLogMapper) {
        this.operationLogMapper = operationLogMapper;
    }

    @AfterReturning("@annotation(operationLog)")
    public void afterReturning(JoinPoint joinPoint, OperationLog operationLog) {
        OperationLogEntity log = new OperationLogEntity();
        log.setUserId(UserContext.get() != null ? UserContext.get().getUserId() : null);
        log.setUsername(UserContext.get() != null ? UserContext.get().getUsername() : null);
        log.setModule(operationLog.module());
        log.setOperationType(operationLog.type());
        log.setDescription(operationLog.description());
        log.setCreateTime(LocalDateTime.now());
        operationLogMapper.insert(log);
    }
}
```

## 7.3 业务接口使用示例

```java
@RestController
@RequestMapping("/user")
public class UserAdminController {

    @OperationLog(module = "用户管理", type = "UPDATE", description = "修改用户状态")
    @PostMapping("/status")
    public Result<Void> updateStatus(@RequestBody UpdateUserStatusRequest request) {
        userAdminService.updateStatus(request);
        return Result.success();
    }
}
```

这套写法的好处是：

- 业务代码侵入较小
- 记录规则比较统一

## 8. 为什么操作日志通常适合异步落库

因为日志记录本身通常不是主业务成功与否的核心条件。  
如果每次写操作日志都同步阻塞主流程，可能会带来：

- 接口耗时增加
- 高并发场景下日志表压力过大

所以正式项目里，经常会进一步演进成：

1. 先组装日志对象
2. 投递 MQ 或异步线程池
3. 后台落库

这样可以把：

- 主业务执行
- 日志写入

适当解耦。

## 9. 为什么日志字段要尽量统一

因为一旦你希望后续做统计分析，例如：

- 近 7 天哪个模块操作最多
- 哪个管理员操作最频繁

就必须保证不同模块的日志字段含义尽量一致。  
否则后面做统一分析会非常痛苦。

所以常见的统一字段包括：

- `module`
- `operationType`
- `userId`
- `bizId`
- `createTime`

## 10. 常见坑点

### 10.1 操作日志全靠业务手工写

模块一多就很容易漏。

### 10.2 日志内容不结构化

后续统计和检索价值会很差。

### 10.3 所有请求都记录成超细日志

数据量会迅速膨胀，也会引入很多噪音。

### 10.4 敏感信息直接写进日志

手机号、证件号、token、密码等需要谨慎处理。

## 11. 总结

操作日志实现的核心，不是“多打一条记录”，而是把用户和管理员在系统中的关键操作，沉淀成统一、可检索、可分析、可追溯的结构化事件数据。

一个成熟的操作日志实现至少应该做到：

- 记录对象和字段统一
- 普通操作和敏感操作分层
- 支持切面统一采集
- 日志能进一步用于分析和审计

这才是操作日志在数据分析体系中的真正价值。
