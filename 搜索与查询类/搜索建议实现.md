# 搜索建议实现

## 1. 功能定义

搜索建议要解决的问题是：

- 用户还没完整输入搜索词时，系统就提前给出可能想搜的内容

常见体验包括：

- 输入 `jav`，系统提示 `java 并发`、`java 集合`
- 输入商品关键词时，先出现推荐搜索项

它的目标不是直接给出结果列表，而是：

- 帮用户更快找到想搜的词
- 降低输入成本
- 提升搜索转化率

## 2. 搜索建议和联想词的区别

这两个概念很像，但可以这样理解：

- 搜索建议：更偏“推荐你搜索这些内容”
- 联想词：更偏“根据前缀或上下文补全你可能要输入的词”

很多系统里二者会部分重合，但从工程角度可以先拆开来看。

## 3. 常见来源

搜索建议的来源通常有几种：

1. 热门搜索词
2. 历史搜索词
3. 系统预置推荐词
4. 索引中真实存在的高频词

正式项目里通常不会只靠一种来源，而是做组合策略。

## 4. 核心设计

搜索建议实现时，建议重点考虑：

1. 建议词来源是什么
2. 建议词是否需要排序
3. 是否按前缀匹配
4. 是否有数量限制
5. 是否需要缓存

## 5. 典型流程

1. 用户输入前缀词
2. 系统按前缀查建议词
3. 返回前 N 个建议结果

## 6. 核心代码

## 6.1 建议词数据示例

```json
[
  {
    "keyword": "java并发",
    "hotScore": 98
  },
```

## 6.2 搜索建议核心实现

这里先给一个数据库版实现，适合做入门阶段的工程骨架。

```java
@Service
public class SearchSuggestServiceImpl implements SearchSuggestService {

    private final SearchSuggestMapper searchSuggestMapper;

    public SearchSuggestServiceImpl(SearchSuggestMapper searchSuggestMapper) {
        this.searchSuggestMapper = searchSuggestMapper;
    }

    @Override
    public List<String> suggest(String keywordPrefix) {
        if (!StringUtils.hasText(keywordPrefix)) {
            return Collections.emptyList();
        }
        if (keywordPrefix.length() > 20) {
            return Collections.emptyList();
        }

        return searchSuggestMapper.selectTopSuggestions(keywordPrefix, 10);
    }
}
```

Mapper 背后的核心思路通常是：

- 按前缀 `like 'keyword%'`
- 按热度排序
- 限制返回数量

## 7. 为什么搜索建议要限制数量

因为搜索建议的目标是：

- 帮用户快速选择

如果一下返回几十条，用户反而会无从判断。  
所以常见做法通常是：

- 返回前 5 条
- 或前 10 条

这也是典型的“体验型接口”，它和报表查询的设计思路完全不同。

## 8. 搜索建议为什么适合缓存

因为建议词通常有这些特点：

- 读多写少
- 热词重复率高
- 请求频率高

所以很多系统会把：

- 热门建议词
- 固定推荐词

提前缓存到 Redis，减少数据库压力。

## 9. 和搜索结果页的关系

搜索建议通常出现在“输入阶段”，而搜索结果页出现在“提交阶段”。  
它们是两个层次的能力：

1. 搜索建议解决“你可能想搜什么”
2. 搜索结果解决“你搜完后能看到什么”

如果建议词做得好，后面的搜索成功率通常也会提高。

## 10. 常见坑点

### 10.1 建议词和真实可搜索内容完全脱节

用户点进去后搜不到东西，体验会很差。

### 10.2 不限制返回数量

接口和前端体验都会变差。

### 10.3 完全实时查复杂大表

搜索建议通常是高频接口，最好不要查很重的业务表。

## 11. 总结

搜索建议的核心，不是“查几个关键词”，而是围绕用户输入过程提供一层轻量、快速、命中率高的提示能力。

如果把它做成一条工程原则，就是：

- 来源要清晰
- 前缀匹配要稳定
- 结果数量要克制
- 高频数据要适当缓存

这样搜索建议才真正有价值。
