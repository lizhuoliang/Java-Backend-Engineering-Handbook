# 多条件组合筛选实现

## 1. 功能定义

多条件组合筛选要解决的问题是：

- 用户不只想搜一个词，而是希望通过多个结构化条件把结果逐步筛小

常见场景包括：

- 订单按状态、时间、支付方式筛选
- 商品按分类、价格区间、品牌筛选
- 用户按部门、角色、状态筛选

如果说关键字搜索更偏“文本检索”，那么多条件组合筛选更偏“结构化检索”。

## 2. 这类能力为什么很重要

在后台系统里，很多高频使用场景并不是：

- 用户输入一个搜索词

而是：

- 我要查“上周、已支付、金额大于 100、某个部门的订单”

这种需求本质上就是多条件组合筛选。  
它是列表页真正走向“可运营、可分析”的关键一步。

## 3. 典型请求示例

```json
{
  "orderNo": "ORD202606",
  "status": "PAID",
  "payChannel": "ALIPAY",
  "startTime": "2026-06-01 00:00:00",
  "endTime": "2026-06-02 23:59:59",
  "minAmount": 100,
  "maxAmount": 1000,
  "pageNum": 1,
  "pageSize": 20
}
```

## 4. 核心设计

多条件组合筛选实现时，建议重点考虑：

1. 条件对象统一建模
2. 每个条件是否可选
3. 条件之间是并且还是或关系
4. 时间区间、数值区间如何表达
5. 查询和分页、排序要能一起工作

这里最常见的一个工程误区是：

- 每新增一个查询条件，就在接口里多加一个散乱参数

这样后期很快就会难维护。  
更好的方式通常是：

- 建一个专门的 QueryRequest 对象

## 5. 典型流程

1. 前端提交筛选条件
2. 后端接收统一查询对象
3. 只对有值的字段拼接条件
4. 执行分页查询
5. 返回筛选结果

## 6.2 组合筛选核心实现

```java
@Service
public class OrderQueryServiceImpl implements OrderQueryService {

    private final OrderMapper orderMapper;

    public OrderQueryServiceImpl(OrderMapper orderMapper) {
        this.orderMapper = orderMapper;
    }

    @Override
    public PageResult<OrderVO> page(OrderQueryRequest request) {
        if (request.getMinAmount() != null
                && request.getMaxAmount() != null
                && request.getMinAmount().compareTo(request.getMaxAmount()) > 0) {
            throw new BizException("最小金额不能大于最大金额");
        }

        Page<Order> page = new Page<>(request.getPageNum(), Math.min(request.getPageSize(), 100L));

        LambdaQueryWrapper<Order> wrapper = new LambdaQueryWrapper<Order>()
                .like(StringUtils.hasText(request.getOrderNo()), Order::getOrderNo, request.getOrderNo())
                .eq(StringUtils.hasText(request.getStatus()), Order::getStatus, request.getStatus())
                .eq(StringUtils.hasText(request.getPayChannel()), Order::getPayChannel, request.getPayChannel())
                .ge(request.getStartTime() != null, Order::getCreateTime, request.getStartTime())
                .le(request.getEndTime() != null, Order::getCreateTime, request.getEndTime())
                .ge(request.getMinAmount() != null, Order::getPayAmount, request.getMinAmount())
                .le(request.getMaxAmount() != null, Order::getPayAmount, request.getMaxAmount())
                .orderByDesc(Order::getCreateTime);

        Page<Order> resultPage = orderMapper.selectPage(page, wrapper);

        List<OrderVO> list = resultPage.getRecords().stream().map(item -> {
            OrderVO vo = new OrderVO();
            vo.setId(item.getId());
            vo.setOrderNo(item.getOrderNo());
            vo.setStatus(item.getStatus());
            vo.setPayAmount(item.getPayAmount());
            return vo;
        }).toList();

        return new PageResult<>(list, resultPage.getTotal(), request.getPageNum(), request.getPageSize());
    }
}
```

这段代码最核心的地方在于：

- 条件是可选拼接的
- 区间条件有基本校验
- 和分页、排序自然结合

## 7. 为什么组合筛选不能只靠前端过滤

有时候前端会把列表全量拿回来再自己筛，但这种方式只适合：

- 数据量很小

正式系统里，大部分筛选一定要放在后端。  
因为：

1. 数据量大
2. 涉及权限控制
3. 前端不该拿到全部数据

所以多条件筛选的真正实现主体，一定还是后端查询层。

## 8. 条件组合为什么容易越来越复杂

因为业务一旦成熟，用户的筛选需求会越来越细。  
最开始可能只是：

- 状态
- 时间

后面很快就会增加：

- 创建人
- 部门
- 金额区间
- 标签
- 来源渠道
- 是否异常

这时候如果查询对象和条件拼接方式设计得不好，代码会迅速失控。  
所以从一开始就要把筛选条件对象化、结构化。

## 9. 常见坑点

### 9.1 每个查询条件单独写一个接口参数

后期维护会非常难受。

### 9.2 区间条件不做边界校验

容易出现无意义查询或错误结果。

### 9.3 前端想查什么字段，后端就全放开

会导致查询接口边界越来越模糊。

### 9.4 查询条件和数据权限没结合

即使条件查得对，也可能越权看到不该看的数据。

## 10. 总结

多条件组合筛选的核心，不是“多写几个 where 条件”，而是把结构化查询需求抽象成统一模型，并让查询层能稳定地组合这些条件、分页、排序和权限控制。

这项能力是后台系统走向“真正可运营”的核心基础之一。
