# 复杂报表查询实现

## 1. 功能定义

复杂报表查询要解决的问题是：

- 系统如何把大量业务数据按某种维度、时间和指标组织起来，供运营、管理、财务或业务人员分析使用

它和普通列表查询最大的不同在于：

- 普通查询更关注“单条记录”
- 报表查询更关注“聚合结果”

例如：

- 每天订单金额趋势
- 各部门审批通过率
- 各商品销量排行
- 用户新增与留存统计

这些都属于复杂报表查询。

## 2. 为什么报表查询不能简单复用普通列表接口

因为报表关注的是：

- 分组
- 聚合
- 统计口径
- 维度切换

而不是单条记录明细。

例如一个订单列表接口关注：

- 订单号
- 用户
- 状态

而一个订单报表接口更关注：

- 每日成交额
- 支付转化率
- 退款率

它们在查询模型上完全不是同一类东西。

## 3. 常见报表维度

复杂报表最常见的维度包括：

1. 时间维度  
日、周、月、年

2. 组织维度  
部门、区域、门店

3. 商品维度  
分类、品牌、SKU

4. 用户维度  
新用户、老用户、会员等级

## 4. 核心设计

复杂报表实现时，建议至少考虑：

1. 报表口径先定义清楚
2. 明细查询和聚合查询分离
3. 统计维度和指标分开建模
4. 大报表不要无脑实时跑
5. 必要时引入预计算或宽表

这里最重要的一点其实是：

- 先定义统计口径

因为报表系统里很多争议，并不是代码算不出来，而是：

- “成交额”到底算支付成功还是订单创建
- “新增用户”到底按注册时间还是首次登录时间

口径不清，报表一定不稳。

## 7. 核心代码

## 7.1 报表查询对象

```java
public class OrderTrendReportRequest {

    private LocalDate startDate;
    private LocalDate endDate;
    private String groupBy;
    private Long deptId;

    public LocalDate getStartDate() {
        return startDate;
    }

    public void setStartDate(LocalDate startDate) {
        this.startDate = startDate;
    }

    public LocalDate getEndDate() {
        return endDate;
    }

    public void setEndDate(LocalDate endDate) {
        this.endDate = endDate;
    }

    public String getGroupBy() {
        return groupBy;
    }

    public void setGroupBy(String groupBy) {
        this.groupBy = groupBy;
    }

    public Long getDeptId() {
        return deptId;
    }

    public void setDeptId(Long deptId) {
        this.deptId = deptId;
    }
```

## 7.2 报表核心实现

```java
@Service
public class OrderReportServiceImpl implements OrderReportService {

    private final OrderReportMapper orderReportMapper;

    public OrderReportServiceImpl(OrderReportMapper orderReportMapper) {
        this.orderReportMapper = orderReportMapper;
    }

    @Override
    public List<OrderTrendReportVO> trend(OrderTrendReportRequest request) {
        if (request.getStartDate() == null || request.getEndDate() == null) {
            throw new BizException("开始时间和结束时间不能为空");
        }
        if (request.getStartDate().isAfter(request.getEndDate())) {
            throw new BizException("开始时间不能晚于结束时间");
        }
        if (!Set.of("DAY", "MONTH").contains(request.getGroupBy())) {
            throw new BizException("不支持的分组维度");
        }

        return orderReportMapper.selectTrend(
                request.getStartDate(),
                request.getEndDate(),
                request.getGroupBy(),
                request.getDeptId()
        );
    }
}
```

Mapper 背后的 SQL 核心思路通常是：

- 按日期范围过滤
- 按状态过滤，例如只统计已支付或已完成订单
- 按天/月分组
- 聚合 `count` 和 `sum`

## 8. 为什么报表要先讲“统计口径”

因为同样叫“订单金额”，可能有完全不同的统计方式：

1. 下单金额
2. 支付金额
3. 已完成金额
4. 扣除退款后的净成交额

如果这件事没定义清楚，报表做得越多，争议就越大。  
所以报表系统真正的第一步往往不是写 SQL，而是先确定口径文档。

## 9. 复杂报表为什么容易慢

因为报表查询往往具有这些特点：

- 时间跨度大
- 聚合字段多
- 分组维度复杂
- 还可能要关联多张表

比如：

- 查半年订单趋势
- 再按地区、部门、商品分类拆分

如果全部实时在事务表上跑，数据库压力会很大。

## 10. 报表查询的常见优化思路

复杂报表一旦变重，通常会往这些方向优化：

1. 建汇总表或宽表
2. 定时离线预计算
3. 明细库和报表库分离
4. 使用 OLAP / 数仓思路

也就是说，报表系统一开始可以直接查业务表，但数据量和复杂度上来后，通常要逐步走向：

- 预聚合
- 数据分层

## 11. 常见坑点

### 11.1 报表口径不统一

这是报表系统里最常见的问题。

### 11.2 明细接口和报表接口混在一起

会让查询模型越来越混乱。

### 11.3 所有统计都实时查业务大表

数据量一大后性能会明显恶化。

### 11.4 只返回结果，不说明统计范围

用户很容易误解数据含义。

## 12. 总结

复杂报表查询的核心，不是“写一条复杂 SQL”，而是围绕统计口径、维度分组、指标聚合和性能策略，构建一套能支撑运营和管理分析的数据查询能力。

一个成熟的报表实现至少应该做到：

- 口径先定义
- 查询对象清晰
- 聚合维度可控
- 重报表有预计算策略

这才是真正可落地的报表系统思路。
