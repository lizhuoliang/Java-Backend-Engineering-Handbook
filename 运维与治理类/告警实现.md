# 告警实现

## 1. 功能定义

告警要解决的问题是：

- 当系统指标、日志或业务状态出现异常时，如何把“问题正在发生”及时通知到人

监控负责看见问题，告警负责叫醒人。  
如果只有监控，没有告警，就会出现一种很常见的情况：

- 图表早就红了
- 但没人知道

所以告警是“可观测体系”真正闭环的关键一步。

## 2. 告警通常基于什么触发

最常见的告警触发来源包括：

1. 指标告警  
例如 CPU 超 90%、接口错误率超阈值。

2. 日志告警  
例如 ERROR 日志短时间暴增。

3. 业务告警  
例如支付成功率骤降、订单创建失败率升高。

4. 安全告警  
例如异常登录、撞库行为、敏感操作异常。

不同类型的告警适合不同的渠道和处理优先级。

## 3. 告警为什么不能只是“出错就发消息”

因为如果策略设计不好，很容易出现两个极端：

1. 告警太少  
真正有问题时没人知道。

2. 告警太多  
大家被刷麻了，真正严重问题反而被忽略。

所以告警系统最重要的，不是“能发出来”，而是：

- 有节制
- 有优先级
- 有可操作性

## 4. 核心设计

告警实现时，建议重点考虑：

1. 告警条件是什么
2. 告警对象是谁
3. 告警渠道是什么
4. 是否需要去重和抑制
5. 告警是否需要恢复通知

这里最关键的一点是：

- 告警一定要和可执行动作关联

也就是说，收到告警的人应该能大致知道：

- 问题是什么
- 影响多大
- 去哪排查

## 5. 常见告警渠道

常见的告警通知渠道包括：

1. 短信
2. 邮件
3. 企业微信
4. 钉钉
5. 飞书机器人
6. 电话语音

不同渠道通常适合不同等级的告警：

- 严重告警用强触达
- 普通告警用群消息或邮件

## 6. 核心代码

## 6.1 一个简化的业务告警服务

```java
@Service
public class AlertServiceImpl implements AlertService {

    private final MailService mailService;
    private final InboxMessageService inboxMessageService;

    public AlertServiceImpl(MailService mailService, InboxMessageService inboxMessageService) {
        this.mailService = mailService;
        this.inboxMessageService = inboxMessageService;
    }

    @Override
    public void sendBusinessAlert(String title, String content, String email) {
        MailSendRequest request = new MailSendRequest();
        request.setTo(email);
        request.setSubject(title);
        request.setContent(content);
        request.setHtml(false);
        mailService.send(request);
    }
}
```

## 6.2 告警触发示例

例如在任务中发现连续失败超阈值时：

```java
@Component
public class RetryTaskAlertJob {

    private final RetryTaskMapper retryTaskMapper;
    private final AlertService alertService;

    public RetryTaskAlertJob(RetryTaskMapper retryTaskMapper, AlertService alertService) {
        this.retryTaskMapper = retryTaskMapper;
        this.alertService = alertService;
    }

    @Scheduled(fixedDelay = 300000)
    public void execute() {
        long failCount = retryTaskMapper.countFinalFailTasks();
        if (failCount > 100) {
            alertService.sendBusinessAlert(
                    "失败重试任务告警",
                    "当前最终失败任务数超过阈值，count=" + failCount,
                    "ops@example.com"
            );
        }
    }
}
```

这段代码展示的是一个最基本的告警链路：

- 发现异常指标
- 告警服务触发通知

## 7. 为什么告警要做抑制和去重

因为有些故障会持续很长时间。  
如果每分钟都发一条一样的告警，就会造成：

- 告警风暴

这会让值班人员迅速疲劳，甚至忽略真正的新问题。

所以成熟的告警系统通常会做：

1. 告警去重  
同类问题短时间内只发一次。

2. 告警抑制  
某些已知故障期间，暂时压制重复告警。

3. 告警恢复通知  
问题恢复时再发一条“已恢复”。

## 8. 为什么业务告警特别重要

很多系统技术指标都看起来正常，但业务已经明显出问题了。  
例如：

- 服务器都没报警
- 但支付回调成功率从 99% 掉到 60%

这种情况下，如果没有业务告警，问题可能会很晚才被发现。  
所以成熟系统的告警体系通常不只是：

- CPU 高
- 内存高

而是还要包括：

- 订单失败率
- 支付异常率
- 消息发送失败率

## 9. 常见坑点

### 9.1 告警太多没有分级

严重和普通问题混在一起，很难快速响应。

### 9.2 告警内容太模糊

只写“系统异常”，排查成本会很高。

### 9.3 没有恢复通知

值班人员不知道问题是持续存在还是已经恢复。

### 9.4 只有技术告警，没有业务告警

很多真实业务故障会被漏掉。

## 10. 总结

告警的核心，不是“发一条通知”，而是围绕异常发现、告警分级、告警抑制和恢复通知，建立一套真正能把问题及时送达给处理人的机制。

一个成熟的告警实现至少应该做到：

- 技术指标和业务指标都可告警
- 告警内容明确可排查
- 支持去重、抑制、恢复通知
- 渠道按严重级别匹配

这才是真正有运维价值的告警体系。
