# 日志采集实现

## 1. 功能定义

日志采集要解决的问题是：

- 系统运行过程中产生的大量日志，如何被统一输出、汇聚、存储和检索

很多人刚开始做项目时，把日志理解成：

- `System.out.println`

但真实系统里，日志不是为了“开发时看两眼”，而是为了在系统上线后回答这些问题：

- 某个请求为什么失败了
- 哪个用户什么时候做了什么
- 某个接口最近是不是持续报错
- 某台机器是不是在大量打印异常

所以日志采集本质上是：

- 系统运行事实的基础记录能力

## 2. 为什么日志采集是运维治理的起点

因为后面的很多能力都建立在日志之上，例如：

- 故障排查
- 安全审计
- 异常统计
- 链路分析
- 告警触发

如果日志本身就很乱、没有统一格式、没有被集中采集，那么上线后的系统几乎就是“黑盒”。

## 3. 日志通常分哪几类

从工程实践看，日志通常至少可以分成：

1. 应用日志  
记录业务运行和异常信息。

2. 访问日志  
记录请求路径、状态码、耗时、来源 IP。

3. 审计日志  
记录敏感操作、登录行为、权限变更等。

4. 基础设施日志  
例如容器、Nginx、数据库、MQ 的运行日志。

真正的日志采集系统，通常不是只采应用日志，而是把这些层次都逐步汇聚起来。

## 4. 典型日志链路

一个常见的日志采集链路通常如下：

1. 应用通过 `SLF4J + Logback` 输出结构化日志
2. 日志写入本地文件或标准输出
3. 采集器抓取日志
4. 汇聚到日志平台
5. 在日志平台中按关键字段检索和分析

也就是说，日志采集不是单点技术，而是一整条链路。

## 5. 核心设计

日志采集实现时，建议重点考虑：

1. 日志格式是否统一
2. 日志是否包含关键上下文
3. 日志级别是否合理
4. 日志是否方便被机器检索
5. 日志是否能跨机器集中查看

这里最关键的一点通常是：

- 日志一定要结构化

否则日志一多之后，很难被真正利用起来。

## 6. 核心代码

## 6.1 基础业务日志输出示例

```java
@Service
public class OrderServiceImpl implements OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderServiceImpl.class);

    @Override
    public void createOrder(OrderCreateRequest request) {
        log.info("开始创建订单, userId={}, itemCount={}", request.getUserId(), request.getItems().size());

        try {
            // 执行业务逻辑
            log.info("订单创建成功, userId={}", request.getUserId());
        } catch (Exception ex) {
            log.error("订单创建失败, userId={}, error={}", request.getUserId(), ex.getMessage(), ex);
            throw ex;
        }
    }
}
```

这里至少体现了两个好习惯：

1. 不直接拼字符串，使用参数化日志
2. 关键上下文信息跟着日志一起输出

## 6.2 访问日志切面示例

```java
@Aspect
@Component
public class AccessLogAspect {

    private static final Logger log = LoggerFactory.getLogger(AccessLogAspect.class);

    @Around("execution(* com.example..controller..*(..))")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = joinPoint.proceed();
            long cost = System.currentTimeMillis() - start;
            log.info("access success, method={}, costMs={}", joinPoint.getSignature().toShortString(), cost);
            return result;
        } catch (Throwable ex) {
            long cost = System.currentTimeMillis() - start;
            log.error("access fail, method={}, costMs={}, error={}",
                    joinPoint.getSignature().toShortString(), cost, ex.getMessage(), ex);
            throw ex;
        }
    }
}
```

这类日志的价值在于：

- 请求是否成功
- 花了多久
- 哪个接口出问题最频繁

## 7. 为什么结构化日志这么重要

如果日志只是：

- “用户下单成功了”
- “订单又失败了”

这种自然语言句子，开发自己看可能还行，但一旦上线以后：

- 检索困难
- 统计困难
- 自动告警困难

而结构化日志至少可以让你按字段检索：

- `userId`
- `orderNo`
- `status`
- `traceId`

这才是日志真正能被治理平台利用起来的前提。

## 8. 日志采集为什么不能只靠本地文件

因为一旦系统进入：

- 多实例部署
- 容器化部署
- 动态扩缩容

你就很难再靠登录某台机器去手动翻日志。  
这时更合理的做法是：

1. 统一输出到标准日志
2. 用采集器汇总
3. 在集中平台查询

这样才具备真正的线上排障能力。

## 9. 日志级别怎么理解

最常见的日志级别通常是：

1. `DEBUG`  
开发调试信息，上线环境通常不开或少开。

2. `INFO`  
关键业务流程的正常运行信息。

3. `WARN`  
可疑但未必失败的问题。

4. `ERROR`  
明确失败、需要关注的问题。

一个成熟系统的重要能力之一，就是：

- 不滥用 ERROR
- 不把所有东西都打成 INFO

## 10. 常见坑点

### 10.1 用 `System.out.println` 代替日志框架

上线后几乎不可治理。

### 10.2 日志没有上下文

出了问题只能看到一句“失败了”，但不知道失败的是谁。

### 10.3 异常只打印 message，不打印堆栈

排查深层问题会非常痛苦。

### 10.4 日志里输出敏感明文

手机号、密码、token、身份证号等不应随意打出来。

## 11. 总结

日志采集的核心，不是“把日志写出来”，而是建立一套：

- 能统一输出
- 能结构化记录
- 能集中汇聚
- 能方便检索和分析

的系统运行事实记录机制。

一个成熟的日志采集实现至少应该做到：

- 使用标准日志框架
- 关键日志结构化
- 访问日志与业务日志分层
- 支持集中采集和检索

这才是运维治理真正的起点。
