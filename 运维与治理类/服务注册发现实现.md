# 服务注册发现实现

## 1. 功能定义

服务注册发现要解决的问题是：

- 在多服务、多实例环境下，一个服务如何找到另一个服务，而不是把对方地址硬编码在配置里

在单体项目里，这个问题几乎不存在。  
因为系统只有一个应用，自己调自己。

但一旦拆成微服务，例如：

- 用户服务
- 订单服务
- 商品服务
- 支付服务

问题就来了：

- 订单服务怎么知道用户服务在哪
- 用户服务扩容成 5 个实例后怎么选一个调用

这就是服务注册发现要解决的核心问题。

## 2. 为什么不能写死服务地址

如果服务地址写死，系统会遇到很多问题：

1. 实例扩缩容后地址变化
2. 容器重启后 IP 变化
3. 多实例负载均衡难做
4. 配置维护成本越来越高

所以微服务一旦规模稍微大一点，都会需要：

- 服务注册
- 服务发现

## 3. 注册和发现分别是什么意思

这两个概念要分开理解。

### 服务注册

是：

- 服务启动后把自己的地址、端口、元数据上报到注册中心

### 服务发现

是：

- 调用方在需要时，从注册中心查询目标服务可用实例列表

也就是说：

- 提供者负责报到
- 消费者负责查找

## 4. 常见实现方案

Java 体系里最常见的服务注册发现方案包括：

- Nacos
- Eureka
- Consul

现在国内项目里很常见的是：

- Spring Cloud + Nacos

## 5. 典型流程

一个服务注册发现链路通常如下：

1. 订单服务启动
2. 把自己注册到注册中心
3. 用户服务启动
4. 也注册自己
5. 订单服务调用用户服务时
6. 先从注册中心拿到用户服务实例列表
7. 通过负载均衡选一个实例发请求

## 6. 核心设计

服务注册发现实现时，建议重点考虑：

1. 服务实例如何注册
2. 心跳和健康状态如何维护
3. 调用方如何负载均衡
4. 服务上下线如何感知
5. 环境、命名空间、分组如何隔离

## 7. 最基础的工程接入思路

以 Nacos 为例，一个最常见的配置大致是：

```yaml
spring:
  application:
    name: order-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

有了这个配置后，服务启动时就会向注册中心报到。

## 8. 服务发现调用示意

例如订单服务调用用户服务，可以通过服务名而不是固定 IP：

```java
@Service
public class UserRemoteService {

    private final RestTemplate restTemplate;

    public UserRemoteService(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    public UserVO queryUser(Long userId) {
        return restTemplate.getForObject(
                "http://user-service/user/" + userId,
                UserVO.class
        );
    }
}
```

这里的关键点不是 `RestTemplate` 本身，而是：

- 调用目标写的是服务名 `user-service`
- 具体实例地址由注册发现体系去解析

## 9. 为什么服务发现通常和负载均衡一起出现

因为一个服务通常不止一个实例。  
例如：

- `user-service` 有 3 台

服务发现只能告诉你：

- 现在有哪些可用实例

但真正发请求前，还需要做：

- 实例选择

这就是负载均衡的职责。  
所以注册发现和负载均衡通常是天然配套的。

## 10. 为什么健康检查和注册发现强相关

如果一个实例已经挂了，但注册中心还认为它活着，那么调用方就可能继续打过去。  
所以成熟的注册发现体系通常都要依赖：

- 心跳
- 健康检查

来决定：

- 这个实例还能不能继续被发现和调用

## 11. 常见坑点

### 11.1 服务名和环境隔离规则混乱

测试环境和生产环境可能互相串调用。

### 11.2 实例已经异常但还在注册中心里

会导致大量调用失败。

### 11.3 调用方只做服务发现，不做超时和熔断

发现到了实例，不代表调用一定安全。

## 12. 总结

服务注册发现的核心，不是“把服务名写成字符串”，而是在微服务环境里，让服务实例的上下线、地址变化、可用性和负载均衡都能被统一管理。

一个成熟的注册发现体系至少应该做到：

- 服务自动注册
- 调用方按服务名发现实例
- 多实例可负载均衡
- 心跳和健康状态可感知

这才是微服务环境下真正可用的基础治理能力。
