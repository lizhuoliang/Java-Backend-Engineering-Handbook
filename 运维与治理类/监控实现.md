# 监控实现

## 1. 功能定义

监控要解决的问题是：

- 系统运行过程中，哪些关键指标正在变差、变慢、变满、变错，运维和开发如何第一时间看见

很多系统“出问题”之前，其实早就已经出现了信号，例如：

- CPU 持续升高
- 接口错误率上升
- 请求耗时变长
- JVM 内存逼近上限
- 数据库连接池快打满

监控的意义，就是把这些信号从“事后翻日志”变成“实时可见”。

## 2. 为什么监控和日志不是一回事

它们都会帮助排障，但侧重点不同：

- 日志更像“离散事件记录”
- 监控更像“连续指标观测”

例如：

- 日志能告诉你某个接口报错了
- 监控能告诉你最近 10 分钟报错率正在持续上涨

所以日志更适合“看细节”，监控更适合“看趋势”。

## 3. 监控通常监什么

从工程实践看，监控通常至少包括四层：

1. 机器监控  
CPU、内存、磁盘、网络。

2. JVM 监控  
堆内存、GC、线程数。

3. 应用监控  
QPS、响应时间、错误率、接口耗时。

4. 中间件监控  
数据库连接池、Redis、MQ、线程池。

一个成熟系统通常不是只盯其中一层，而是把这些层串起来看。

## 4. 监控的核心设计

监控实现时，建议重点考虑：

1. 监控指标是否足够代表系统健康
2. 指标是否可长期连续采集
3. 指标维度是否合理
4. 监控是否支持趋势和聚合查看
5. 监控能否和告警联动

这里最关键的一点是：

- 监控不是“采得越多越好”，而是“采集真正有判断价值的指标”

## 5. 常见关键指标

一个 Java 服务最常关注的指标通常包括：

1. 请求量  
QPS、TPS。

2. 耗时  
平均耗时、P95、P99。

3. 错误率  
4xx、5xx、业务异常比率。

4. JVM 指标  
堆内存、线程数、GC 次数和耗时。

5. 数据源指标  
连接池使用量、慢查询数。

## 6. 核心代码

## 6.1 基于 Micrometer 的接口指标示例

```java
@Service
public class OrderServiceImpl implements OrderService {

    private final MeterRegistry meterRegistry;

    public OrderServiceImpl(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    @Override
    public void createOrder(OrderCreateRequest request) {
        Timer.Sample sample = Timer.start(meterRegistry);
        try {
            meterRegistry.counter("order.create.count").increment();

            // 执行业务逻辑

            meterRegistry.counter("order.create.success").increment();
        } catch (Exception ex) {
            meterRegistry.counter("order.create.fail").increment();
            throw ex;
        } finally {
            sample.stop(Timer.builder("order.create.cost")
                    .publishPercentileHistogram()
                    .register(meterRegistry));
        }
    }
}
```

这段代码表达的是监控里最常见的三类指标：

1. 次数
2. 成功/失败
3. 耗时

## 6.2 应用健康与监控暴露

Spring Boot 中最常见的基础做法是接入：

- `spring-boot-starter-actuator`

并暴露诸如：

- `/actuator/metrics`
- `/actuator/health`

这相当于给监控系统提供了标准采集入口。

## 7. 为什么响应时间不能只看平均值

因为平均值会掩盖很多真实问题。  
例如：

- 90% 请求 50ms
- 10% 请求 5s

平均值可能看起来还行，但用户体验已经明显变差。  
所以正式系统里通常会关注：

- P95
- P99

这比平均值更能反映“尾部慢请求”。

## 8. 为什么监控必须和业务结合

很多团队一开始只盯：

- CPU
- 内存
- JVM

这些当然重要，但还不够。  
真正有业务价值的监控还应该包含：

- 下单成功率
- 支付回调成功率
- 短信发送失败率
- 退款成功率

因为：

- 技术指标告诉你系统是否健康
- 业务指标告诉你业务是否真的在正常运转

## 9. 常见技术方案

Java 系统里非常常见的一套组合是：

- Spring Boot Actuator
- Micrometer
- Prometheus
- Grafana

它们的关系通常可以理解为：

1. 应用暴露指标
2. Prometheus 负责抓取
3. Grafana 负责展示

## 10. 常见坑点

### 10.1 只监控机器，不监控应用

很多业务异常会被漏掉。

### 10.2 只看平均耗时

尾部高延迟问题很容易被掩盖。

### 10.3 指标很多，但没人知道该看什么

说明指标体系没有围绕关键目标设计。

### 10.4 没有业务监控

技术看起来正常，业务其实已经出问题了。

## 11. 总结

监控的核心，不是“把指标采出来”，而是围绕系统健康和业务健康，建立一套能持续观测趋势、快速发现异常、并支持后续告警和排障的指标体系。

一个成熟的监控实现至少应该做到：

- 机器、JVM、应用、中间件多层覆盖
- 请求量、耗时、错误率清晰可见
- 业务关键指标有独立监控
- 能与告警系统联动

这才是真正有价值的运维监控体系。
