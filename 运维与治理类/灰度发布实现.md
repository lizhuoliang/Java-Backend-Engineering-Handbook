# 灰度发布实现

## 1. 功能定义

灰度发布要解决的问题是：

- 新版本上线时，不是一口气让所有用户都切到新版本，而是先让一小部分流量试运行，再逐步扩大范围

它的核心目标是：

- 降低上线风险

因为真实项目里，哪怕测试做得再多，新版本上线也可能出现：

- 隐藏 bug
- 兼容性问题
- 特定流量下才会暴露的问题

灰度发布的意义就在于：

- 先小范围观察
- 再决定是否全量放开

## 2. 为什么不能每次都直接全量发布

因为全量发布的风险非常集中。  
如果版本有问题，影响通常是：

- 所有用户一起受影响
- 所有机器一起出问题

而灰度发布则把这种风险拆开了：

- 先影响一小部分
- 观察稳定后再扩大

这在高可用系统里是非常重要的工程实践。

## 3. 常见灰度维度

灰度发布最常见的流量切分方式包括：

1. 按机器实例  
部分实例跑新版本，部分实例跑旧版本。

2. 按用户  
只有部分用户命中新版本。

3. 按请求头 / 标签  
特定调用方先走新版本。

4. 按地域 / 租户 / 商户

不同业务适合的灰度粒度不完全一样。

## 4. 核心设计

灰度发布实现时，建议重点考虑：

1. 流量怎么分
2. 灰度比例怎么调
3. 如何快速回滚
4. 新旧版本是否兼容
5. 灰度期间监控看什么

这里最关键的一点其实不是切流量，而是：

- 新旧版本能否共存一段时间

如果数据库结构、接口协议完全不兼容，灰度就会非常困难。

## 5. 典型灰度流程

一个比较标准的灰度发布流程通常如下：

1. 新版本先部署到少量实例
2. 先放少量测试流量
3. 观察监控、日志、错误率、业务指标
4. 如果稳定，再逐步扩大流量比例
5. 最终全量发布

如果中途发现问题，则：

6. 快速切回旧版本

## 6. 一个简单的用户灰度思路

很多系统里，可以先通过用户 ID 做简单流量分流。  
例如：

- 10% 用户命中新版本

```java
@Service
public class GrayRuleServiceImpl implements GrayRuleService {

    @Override
    public boolean hitGray(Long userId, int grayPercent) {
        long hash = Math.abs(userId.hashCode()) % 100;
        return hash < grayPercent;
    }
}
```

这段代码的意义在于：

- 同一个用户会稳定命中同一侧
- 可以通过比例逐步放量

## 7. 为什么灰度发布不只是技术动作

灰度真正要成功，往往不只是部署工具支持，还要业务和架构配合。  
例如：

1. 数据库变更要前后兼容
2. 新旧接口要能短时间共存
3. 日志和监控要能区分灰度流量

否则即使你做了流量切分，也很难真正安全地观测灰度结果。

## 8. 灰度期间重点看什么

灰度发布时，最重要的不是“新版本机器起来了没有”，而是：

1. 接口错误率是否升高
2. 响应时间是否变差
3. 关键业务成功率是否下降
4. 是否出现新类型异常日志

也就是说，灰度真正依赖的是：

- 可观测性体系

如果监控和告警做得很弱，灰度的意义也会被大打折扣。

## 9. 为什么灰度发布一定要能回滚

因为灰度的本质不是“保证一定成功”，而是：

- 让失败成本可控

而“成本可控”的前提，就是：

- 有快速回滚能力

如果新版本有问题，但系统又很难回滚，那灰度带来的收益就会变小很多。

## 10. 常见坑点

### 10.1 灰度期间新旧版本不兼容

最常见的是数据库字段和接口协议问题。

### 10.2 只有灰度流量，没有灰度监控

流量切过去了，但没人知道效果如何。

### 10.3 灰度用户命中不稳定

同一个用户一会儿走新版本，一会儿走旧版本，体验和排查都会混乱。

### 10.4 没有回滚预案

出问题时会非常被动。

## 11. 总结

灰度发布的核心，不是“分一点流量过去”，而是通过流量逐步放量、监控重点观察和随时可回滚，把上线风险控制在一个可接受范围内。

一个成熟的灰度发布体系至少应该做到：

- 流量切分规则明确
- 新旧版本短期兼容
- 灰度效果可监控
- 问题可快速回滚

这才是真正有生产价值的发布治理能力。
