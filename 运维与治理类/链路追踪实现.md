# 链路追踪实现

## 1. 功能定义

链路追踪要解决的问题是：

- 一个请求从入口进来后，经过了哪些服务、哪些方法、哪些远程调用，最终在哪一步慢了、错了、断了

在单体项目里，排查问题很多时候还能靠日志手工串起来。  
但一旦系统拆成多个服务，就会出现一个非常现实的问题：

- 日志散落在不同服务、不同机器里

这时候你想回答：

- 这次请求到底经过了哪些系统

就变得很困难。  
链路追踪就是为了解决这个问题。

## 2. 为什么链路追踪很重要

因为在分布式系统里，很多问题都不是“这个服务单独报错”，而是：

- 上游调用下游慢
- 下游又去调用下游
- 最终某一步超时，整条链路都被拖垮

这时如果没有统一的追踪标识，你就只能在多个系统日志里盲猜。  
而链路追踪能帮你把一次请求串成一整条路径。

## 3. 链路追踪的核心概念

理解链路追踪，至少要先认识两个概念：

### 3.1 Trace

表示：

- 一次完整请求的全链路

### 3.2 Span

表示：

- 链路中的一个子操作

例如：

- 网关接收请求是一个 span
- 订单服务处理是一个 span
- 调支付服务是另一个 span

很多 span 串起来，就形成了一条 trace。

## 4. 典型链路结构

例如一个下单请求，可能形成这样一条链路：

```text
Gateway
 -> OrderService
 -> InventoryService
 -> CouponService
 -> PayService
```

如果某次下单很慢，你真正想知道的通常不是：

- 整体慢了 3 秒

而是：

- 到底是库存慢、优惠券慢，还是支付前置校验慢

这就是链路追踪存在的意义。

## 5. 核心设计

链路追踪实现时，建议重点考虑：

1. traceId 如何生成
2. traceId 如何跨线程、跨服务传播
3. 哪些关键步骤要记录 span
4. 日志是否带 traceId
5. 链路数据如何上报到可视化平台

其中最关键的一点是：

- traceId 必须贯穿整条调用链

否则你还是只能得到一堆分散日志。

## 6. 最基础的链路思路：日志上下文透传

即使没有完整接入 SkyWalking、Zipkin、Jaeger 这类平台，也至少应该做到：

- 给每次请求一个 traceId
- 所有日志都带上 traceId

这样你至少能在日志系统中把一次请求串出来。

## 7. 核心代码

## 7.1 请求入口生成 traceId

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {

        String traceId = request.getHeader("X-Trace-Id");
        if (!StringUtils.hasText(traceId)) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }

        MDC.put("traceId", traceId);
        response.setHeader("X-Trace-Id", traceId);
        try {
            filterChain.doFilter(request, response);
        } finally {
            MDC.remove("traceId");
        }
    }
}
```

这段代码的意义在于：

- 每个请求进入系统时先拥有一个统一 traceId

## 7.2 日志模板中输出 traceId

例如在 `logback-spring.xml` 中：

```xml
<pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level traceId=%X{traceId} %logger - %msg%n</pattern>
```

这意味着后续所有日志都会自动带上：

- `traceId=xxx`

## 7.3 跨服务调用透传 traceId

```java
@Component
public class TraceFeignInterceptor implements RequestInterceptor {

    @Override
    public void apply(RequestTemplate template) {
        String traceId = MDC.get("traceId");
        if (StringUtils.hasText(traceId)) {
            template.header("X-Trace-Id", traceId);
        }
    }
}
```

这一步的价值非常关键：

- 上游生成的 traceId
- 被透传给下游服务

这样整条链路才能串起来。

## 8. 为什么链路追踪和日志必须配合

很多人会把：

- 链路追踪
- 日志系统

当成两个完全独立的东西。  
但在工程里，它们通常是强配合关系。

链路追踪负责回答：

- 请求走了哪条路径

日志负责回答：

- 每一步具体发生了什么

所以最理想的状态通常是：

- trace 平台看整体路径
- 日志平台看具体上下文

## 9. 正式项目常见方案

更成熟的链路追踪通常会接入：

- SkyWalking
- Zipkin
- Jaeger
- OpenTelemetry

这些方案的价值在于，它们不仅能记录 traceId，还能做：

1. span 耗时分析
2. 服务调用拓扑
3. 错误节点定位
4. 采样上报

也就是说，它们把“日志串 traceId”升级成了真正的“分布式追踪平台”。

## 10. 常见坑点

### 10.1 只在入口生成 traceId，不往下游透传

链路会在服务边界处断掉。

### 10.2 线程切换后 traceId 丢失

异步任务、线程池场景特别容易出现这个问题。

### 10.3 日志里没有 traceId

就算接了链路追踪平台，排查具体问题时也会很痛苦。

## 11. 总结

链路追踪的核心，不是“多一个请求编号”，而是让一次请求在跨服务、跨线程、跨远程调用的过程中，都能被统一串起来并被观察。

一个成熟的链路追踪实现至少应该做到：

- 请求入口生成或接收 traceId
- 日志统一携带 traceId
- 跨服务调用透传 traceId
- 能接入链路分析平台

这才是分布式系统真正可排障、可观测的关键基础。
