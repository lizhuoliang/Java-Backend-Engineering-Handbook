# 健康检查实现

## 1. 功能定义

健康检查要解决的问题是：

- 系统当前是否还能正常对外提供服务，以及它依赖的关键组件是否仍然处于可用状态

健康检查的核心不是“服务进程有没有活着”，而是：

- 这个服务是不是处于可用状态

一个 Java 进程哪怕还在运行，也可能：

- 数据库连不上
- Redis 挂了
- 线程池打满
- 下游依赖不可用

所以健康检查是比“进程还活着”更有业务意义的一层判断。

## 2. 健康检查通常解决什么问题

最常见的作用包括：

1. 容器编排判断实例能否接流量
2. 注册中心判断实例是否可用
3. 运维和监控平台感知系统健康状况
4. 上线或灰度时判断版本是否准备好

可以说，健康检查是服务治理体系中的一个基础信号源。

## 3. 常见健康状态

最常见的健康状态通常可以简单分成：

1. `UP`  
健康，可正常对外服务。

2. `DOWN`  
不健康，不应继续接流量。

3. `OUT_OF_SERVICE`  
服务在运行，但不希望接收流量。

在更复杂系统里，还可能细分更多状态，但这三类已经足够表达大多数场景。

## 4. 健康检查通常分几层

工程里常见的健康检查大致包括：

1. 存活检查（Liveness）  
进程是不是还活着。

2. 就绪检查（Readiness）  
服务是不是准备好接流量。

这两个概念很重要。

### Liveness

更关心：

- 应用有没有死锁
- 进程是不是彻底不可恢复

### Readiness

更关心：

- 应用是否已经完成初始化
- 关键依赖是否连接正常
- 当前是否适合接流量

## 5. 核心设计

健康检查实现时，建议重点考虑：

1. 检查哪些依赖
2. 哪些依赖异常会判定整体不可用
3. 健康检查接口能否被快速调用
4. 健康状态是否和注册发现、负载均衡联动

这里很关键的一点是：

- 健康检查不能做成一个重接口

因为它会被：

- 容器
- 注册中心
- 监控平台

高频访问。

## 6. 核心代码

## 6.1 基础健康检查接口

在 Spring Boot 里，最常见的是接入：

- `Spring Boot Actuator`

默认就会提供：

- `/actuator/health`

如果要自定义某个依赖的健康状态，可以这样做：

```java
@Component
public class RedisHealthIndicator implements HealthIndicator {

    private final StringRedisTemplate stringRedisTemplate;

    public RedisHealthIndicator(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public Health health() {
        try {
            stringRedisTemplate.opsForValue().get("health_check");
            return Health.up().withDetail("redis", "ok").build();
        } catch (Exception ex) {
            return Health.down(ex).withDetail("redis", "fail").build();
        }
    }
}
```

这段代码体现的是：

- 健康检查不仅看进程，还看关键依赖是否正常

## 7. 为什么健康检查要区分“关键依赖”和“非关键依赖”

因为不是所有依赖失败都应该让整个服务直接判死。  
例如：

- 推荐服务挂了，首页推荐功能也许可以降级

但如果：

- 主数据库连不上

那对于大多数业务服务来说，几乎就意味着不可用。

所以健康检查不能简单地“只要任何依赖失败就全部 DOWN”，而要结合业务关键路径判断。

## 8. 健康检查和注册中心的关系

在微服务里，健康检查通常直接影响：

- 这个实例是否还能被注册中心继续返回给调用方

如果实例已经不健康但还继续被流量命中，就会带来：

- 大量失败请求

所以健康检查通常不只是“自我安慰型接口”，它往往会和：

- 服务摘除
- 流量切断

直接关联。

## 9. 健康检查和灰度发布的关系

灰度发布时，新版本实例并不是一启动就应该立刻接流量。  
通常更合理的是：

1. 实例启动
2. 完成依赖初始化
3. Readiness 检查通过
4. 再逐步接流量

所以健康检查其实也是发布治理的一部分。

## 10. 常见坑点

### 10.1 健康检查只返回“进程活着”

对真实可用性帮助有限。

### 10.2 健康检查逻辑太重

会反过来给系统增加压力。

### 10.3 所有依赖异常都直接判死

有些场景其实可以降级，不需要完全下线。

## 11. 总结

健康检查的核心，不是“给运维看一个 ok”，而是为系统提供一条关于当前服务可用性的标准信号，让容器、注册中心、监控和发布体系都能据此做出正确决策。

一个成熟的健康检查实现至少应该做到：

- 区分存活和就绪
- 检查关键依赖
- 响应足够轻量
- 能和流量治理联动

这才是健康检查真正的工程价值。
