# 分布式锁实现

## 1. 功能定义

分布式锁要解决的问题是：

- 在多实例、多线程、多进程环境下，某一段关键逻辑如何保证同一时刻只有一个执行者

在单机系统里，我们可以用：

- `synchronized`
- `ReentrantLock`

但一旦系统部署成多台机器，这些本地锁就失效了。  
因为它们只能锁住“当前进程”，锁不住其他机器上的实例。

这时就需要分布式锁。

## 2. 哪些场景需要分布式锁

最常见的场景包括：

- 同一用户重复下单控制
- 秒杀库存扣减保护
- 定时任务集群只执行一次
- 同一业务单据防止重复处理
- 账户余额并发操作保护

这里要先强调一个很重要的原则：

- 分布式锁不是默认方案

只有在“多实例并发修改同一共享资源”且难以用数据库原子操作解决时，才应该引入它。

## 3. 常见实现方式

分布式锁常见有三类实现：

1. 基于数据库
2. 基于 Redis
3. 基于 ZooKeeper

在 Java 业务系统里，最常见的是：

- 基于 Redis 的分布式锁

因为它实现简单、接入方便、性能也较好。

## 4. 核心设计

分布式锁实现时，最重要的不是“抢到锁”这一步，而是：

1. 锁的 key 怎么设计
2. 锁是否有过期时间
3. 释放锁时如何保证不会误删别人加的锁
4. 抢锁失败时怎么处理

真正危险的地方往往不是加锁，而是解锁。

## 5. 典型流程

一个典型的 Redis 分布式锁流程如下：

1. 用 `setIfAbsent` 抢锁
2. 抢锁成功后执行业务
3. 执行业务结束后释放锁
4. 释放时校验锁归属

## 6. 核心代码

## 6.1 加锁核心实现

```java
@Service
public class RedisDistributedLockService {

    private final StringRedisTemplate stringRedisTemplate;

    public RedisDistributedLockService(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    public String tryLock(String lockKey, Duration expireDuration) {
        String requestId = UUID.randomUUID().toString();
        Boolean success = stringRedisTemplate.opsForValue()
                .setIfAbsent(lockKey, requestId, expireDuration);
        return Boolean.TRUE.equals(success) ? requestId : null;
    }

    public void unlock(String lockKey, String requestId) {
        String value = stringRedisTemplate.opsForValue().get(lockKey);
        if (Objects.equals(value, requestId)) {
            stringRedisTemplate.delete(lockKey);
        }
    }
}
```

这段代码表达了分布式锁里最基础的两个动作：

- 抢锁
- 只释放自己持有的锁

## 6.2 业务使用示例

以“用户重复提交订单”场景举例：

```java
@Service
public class OrderSubmitServiceImpl implements OrderSubmitService {

    private final RedisDistributedLockService lockService;

    public OrderSubmitServiceImpl(RedisDistributedLockService lockService) {
        this.lockService = lockService;
    }

    @Override
    public void submitOrder(Long userId, OrderCreateRequest request) {
        String lockKey = "lock:order:submit:" + userId;
        String requestId = lockService.tryLock(lockKey, Duration.ofSeconds(10));
        if (requestId == null) {
            throw new BizException("操作过于频繁，请稍后再试");
        }

        try {
            // 执行业务逻辑
        } finally {
            lockService.unlock(lockKey, requestId);
        }
    }
}
```

这里的核心思想是：

- 对同一用户的关键动作做串行保护

## 7. 为什么锁一定要带过期时间

因为如果加锁成功后，服务异常崩溃了：

- 没执行到 finally
- 没来得及解锁

那这把锁就会永久残留。  
这会导致后续所有请求都拿不到锁。

所以分布式锁必须设置过期时间，这是最基础的自恢复能力。

## 8. 为什么解锁不能直接 delete

因为存在这样一种风险：

1. A 拿到锁
2. A 执行太久，锁超时
3. B 拿到了新锁
4. A 执行完直接 delete

这时 A 会把 B 的锁删掉，导致并发保护失效。

所以解锁时一定要校验：

- 当前锁是不是自己加的

## 9. Redis 锁的进一步工程化做法

如果系统要求更高，通常会继续引入：

1. Lua 脚本原子解锁
2. Redisson
3. 看门狗续期机制

尤其是：

- “先 get 再 delete”并不是严格原子

正式项目里很多团队会直接用 `Redisson`，因为它把：

- 原子加锁
- 原子解锁
- 自动续期

这些细节都封装好了。

## 10. 常见坑点

### 10.1 没有过期时间

一旦服务异常，锁容易永久残留。

### 10.2 解锁不校验 requestId

会误删别人的锁。

### 10.3 什么并发问题都上分布式锁

很多场景其实可以直接靠数据库原子更新解决。

### 10.4 锁粒度过大

会把系统吞吐量压得很低。

## 11. 总结

分布式锁的核心，不是“让代码同步执行”，而是在多实例环境下，为共享资源争用建立一层可跨节点生效的互斥保护。

一个成熟的分布式锁实现至少应该做到：

- 锁 key 设计清晰
- 加锁带过期时间
- 解锁校验锁归属
- 关键场景下考虑原子解锁和自动续期

这才是真正可用于生产的分布式锁能力。
