# 降级实现

## 1. 功能定义

降级要解决的问题是：

- 当系统部分能力不可用、压力过大或依赖异常时，如何用一个“可接受但不完美”的结果继续对外提供服务

简单说，降级不是追求“完全正常”，而是追求：

- 在坏情况下，系统仍然能勉强用

例如：

- 推荐服务挂了，首页先返回默认推荐
- 非核心统计查不到，页面先返回空数据
- 评论服务超时，商品详情先不展示评论区

## 2. 为什么降级很重要

因为系统并不是每个功能都同等重要。  
在高压或异常场景下，真正应该优先保住的是：

- 核心主链路

例如电商系统里：

- 下单、支付比推荐、评论更核心

如果为了一个非核心能力把整个页面都拖慢甚至拖挂，那就是不合理的。

降级的意义就在于：

- 主动舍弃一部分次要能力
- 保住核心能力可用

## 3. 常见降级场景

1. 下游服务异常
2. 系统流量过高
3. 某些非核心模块压力过大
4. 临时运维开关关闭某能力

## 4. 降级和熔断的关系

可以简单理解为：

- 熔断是“不再调用”
- 降级是“那我返回什么”

例如：

- 不再调用推荐服务，这是熔断
- 返回一组兜底推荐商品，这是降级

## 5. 核心设计

降级实现时，建议重点考虑：

1. 哪些能力可以降级
2. 哪些能力绝不能降级
3. 降级后的结果是什么
4. 降级是自动触发还是手动开关

最重要的一点是：

- 降级策略一定要按业务优先级设计

## 6. 常见降级方式

最常见的降级方式包括：

1. 返回默认值
2. 返回缓存数据
3. 返回空结果
4. 返回静态兜底内容
5. 暂时关闭某功能入口

其中比较常用、也比较稳的方式通常是：

- 默认值
- 缓存值

## 7. 核心代码

## 7.1 查询推荐商品降级示例

```java
@Service
public class RecommendServiceImpl implements RecommendService {

    private final RecommendRemoteClient recommendRemoteClient;

    public RecommendServiceImpl(RecommendRemoteClient recommendRemoteClient) {
        this.recommendRemoteClient = recommendRemoteClient;
    }

    @Override
    public List<ProductVO> queryRecommendProducts(Long userId) {
        try {
            return recommendRemoteClient.query(userId);
        } catch (Exception ex) {
            return defaultRecommendProducts();
        }
    }

    private List<ProductVO> defaultRecommendProducts() {
        ProductVO product = new ProductVO();
        product.setId(1L);
        product.setName("默认推荐商品");
        return List.of(product);
    }
}
```

这段代码体现的是最基础的一种降级：

- 主逻辑失败
- 返回兜底结果

## 7.2 基于缓存降级

```java
@Override
public List<ProductVO> queryRecommendProducts(Long userId) {
    try {
        return recommendRemoteClient.query(userId);
    } catch (Exception ex) {
        String cache = stringRedisTemplate.opsForValue().get("recommend:default");
        if (cache != null) {
            return JSON.parseArray(cache, ProductVO.class);
        }
        return Collections.emptyList();
    }
}
```

这种方式比纯默认值更实用，因为：

- 结果更接近真实业务内容

## 8. 为什么降级结果也要被业务接受

降级不是随便返回点东西就行。  
如果返回的结果业务根本无法接受，例如：

- 下单金额查询失败却返回 0 元

那就不是降级，而是事故。

所以真正适合降级的，通常是：

- 非核心
- 可替代
- 可容忍短时不准确

例如：

- 推荐
- 统计
- 辅助信息

## 9. 手动降级开关怎么理解

很多正式项目里，降级不仅靠自动异常触发，还会配置手动开关。  
例如：

- 活动大促期间，临时关闭某些非核心功能

这类开关通常会配合：

- 配置中心
- 动态开关

来使用。

## 10. 常见坑点

### 10.1 核心业务做不合理降级

例如支付金额、库存结果这类核心数据通常不能随便降级。

### 10.2 降级结果毫无业务意义

用户体验和业务判断都会出错。

### 10.3 异常一来就整站级降级

范围过大，影响用户体验。

## 11. 总结

降级的核心，不是“出了问题随便糊一个结果”，而是按业务优先级，提前设计好哪些能力在异常时可以退一步，以及退到什么程度仍然能被接受。

一个成熟的降级实现通常会做到：

- 核心和非核心能力分层
- 降级结果可接受
- 自动和手动策略结合

这才是真正对系统稳定性有帮助的降级能力。
