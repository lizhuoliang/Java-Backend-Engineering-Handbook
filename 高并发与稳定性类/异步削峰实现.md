# 异步削峰实现

## 1. 功能定义

异步削峰要解决的问题是：

- 当某个时刻请求量突然暴涨时，系统如何不让所有请求都瞬间压到核心业务和数据库上

“削峰”这两个字很形象。  
本质上它想做的是：

- 把尖锐的流量洪峰，变成后端可以逐步消化的平滑流量

在高并发系统里，这是一个非常经典的思路。

## 2. 哪些场景最适合异步削峰

最典型的场景包括：

- 秒杀下单
- 活动报名
- 批量通知发送
- 大批量订单导入
- 高峰期写日志或行为采集

这些场景有一个共同特点：

- 用户请求量会在短时间内暴增
- 但后端实际处理能力是有限的

## 3. 异步削峰的核心思想

最常见的做法通常是：

1. 请求先进入 MQ 或缓冲层
2. 后端消费者按自己的处理能力慢慢消费

这样前端洪峰和后端处理能力就被“解耦”了。

也就是说，异步削峰本质上不是提升瞬时处理能力，而是：

- 延缓后端承压时间
- 限制后端消费速率

## 4. 典型流程

以秒杀下单为例，异步削峰流程通常是：

1. 用户请求秒杀
2. 系统先做基础校验
3. 请求写入消息队列
4. 快速返回“排队中”
5. 消费者异步创建订单
6. 用户稍后查询结果

## 5. 核心设计

异步削峰实现时，建议重点考虑：

1. 哪些请求适合异步
2. 队列积压多大可以接受
3. 消费失败怎么处理
4. 用户结果怎么反馈
5. 是否需要去重和幂等

这里最容易出问题的一点是：

- 系统虽然削了峰，但业务结果不可追踪

所以异步化之后，一定要把“状态回查”设计好。

## 6. 核心代码

## 6.1 生产者：先入队

```java
@Service
public class SeckillRequestServiceImpl implements SeckillRequestService {

    private final RabbitTemplate rabbitTemplate;

    public SeckillRequestServiceImpl(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    @Override
    public void submit(SeckillRequest request) {
        rabbitTemplate.convertAndSend(
                "seckill.exchange",
                "seckill.order.create",
                request
        );
    }
}
```

## 6.2 消费者：按后端能力慢慢处理

```java
@Component
public class SeckillOrderConsumer {

    private final OrderService orderService;

    public SeckillOrderConsumer(OrderService orderService) {
        this.orderService = orderService;
    }

    @RabbitListener(queues = "seckill.order.queue")
    public void consume(SeckillRequest request) {
        orderService.createSeckillOrder(request);
    }
}
```

这两段代码背后的核心思想是：

- 前端洪峰不直接打穿订单服务
- 先排队
- 后端按节奏消费

## 7. 为什么削峰后通常要让用户“查询结果”

因为异步处理后，用户往往不能立刻拿到最终结果。  
所以系统通常会返回：

```json
{
  "status": "QUEUING",
  "message": "请求已受理，请稍后查询结果"
}
```

后面再提供一个查询接口，例如：

- 查询秒杀申请状态
- 查询异步导入结果
- 查询通知发送结果

这一步非常重要，否则异步后用户体验会断掉。

## 8. 为什么异步削峰不等于问题解决了

因为 MQ 只是“缓冲池”，不是无限吞吐机器。  
如果后端消费能力长期跟不上，最终还是会出现：

- 消息积压
- 延迟越来越大
- 下游处理不过来

所以削峰真正有意义的前提是：

- 峰值是短时的
- 后端总处理能力最终能消化掉这些请求

## 9. 常见坑点

### 9.1 只入队，不做结果回查

用户根本不知道最终结果。

### 9.2 消费端没有幂等

消息重复消费时会产生重复订单或重复任务。

### 9.3 队列无限堆积没人管

削峰就会变成“把问题延后爆炸”。

## 10. 总结

异步削峰的核心，不是“把同步改异步”这么简单，而是通过 MQ 或缓冲层，把短时间的流量洪峰转化成系统可以逐步消化的处理节奏。

一个成熟的异步削峰实现至少应该做到：

- 入队和消费解耦
- 消费端幂等
- 队列积压可监控
- 用户结果可回查

这才是真正能抗高峰流量的设计。
