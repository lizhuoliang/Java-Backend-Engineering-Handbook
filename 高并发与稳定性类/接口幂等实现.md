# 接口幂等实现

## 1. 功能定义

接口幂等要解决的问题是：

- 同一个请求被重复提交多次时，系统最终只产生一次符合预期的效果

例如：

- 用户重复点击支付
- 网络重试导致回调重复到达
- MQ 消息重复消费

这些都可能让同一业务动作被执行多次。  
如果没有幂等保护，后果通常很严重，例如：

- 重复创建订单
- 重复扣库存
- 重复发积分
- 重复退款

所以幂等并不是“可有可无的优化”，而是很多核心业务的基础保护能力。

## 2. 幂等和防重复提交的区别

这两个概念经常被混用，但侧重点不同：

- 防重复提交：更偏用户侧短时间重复点击保护
- 幂等：更偏系统侧无论请求重来多少次，结果都一致

也就是说：

- 防重复提交更像入口防抖
- 幂等更像业务语义保障

真正的关键业务，一般两者都要做。

## 3. 哪些接口最需要幂等

最常见的高风险接口包括：

- 订单创建
- 支付回调
- 退款回调
- 发积分
- 发优惠券
- 扣库存

只要这个接口有“重复执行会产生严重副作用”的风险，就要认真考虑幂等。

## 4. 常见幂等实现思路

幂等最常见的实现方式有三类：

1. 基于唯一业务键
2. 基于幂等 token
3. 基于状态机控制

在真实项目里，这三种往往不是互斥的，而是组合使用。

## 5. 核心设计

接口幂等实现时，建议先明确：

1. 这类请求的“唯一业务身份”是什么
2. 重复请求时是直接返回成功，还是返回已有结果
3. 幂等记录存在哪
4. 幂等窗口有多长

很多幂等设计失败，不是因为不会写 Redis，而是因为根本没想清楚：

- 到底什么才算“同一个请求”

## 6. 典型实现方式一：基于业务唯一约束

例如：

- 同一个订单号只能对应一笔支付单
- 同一个外部流水号只能处理一次

这种方式的优点是：

- 最贴近业务本质

例如支付回调里，最常见的幂等判断就是：

- 这笔支付单是否已经处理成功

## 7. 典型实现方式二：基于 Redis 幂等 key

例如前端提交订单时，先生成一个 `requestNo`：

```json
{
  "requestNo": "req_202606020001",
  "items": [...]
}
```

后端处理时：

- 先写入 `idempotent:order:create:req_202606020001`
- 如果已存在，说明已经处理过

## 8. 核心代码

## 8.1 Redis 幂等控制核心实现

```java
@Service
public class IdempotentServiceImpl implements IdempotentService {

    private final StringRedisTemplate stringRedisTemplate;

    public IdempotentServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean tryAcquire(String key, Duration duration) {
        Boolean success = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", duration);
        return Boolean.TRUE.equals(success);
    }
}
```

## 8.2 订单创建幂等示例

```java
@Service
public class OrderCreateServiceImpl implements OrderCreateService {

    private final IdempotentService idempotentService;

    public OrderCreateServiceImpl(IdempotentService idempotentService) {
        this.idempotentService = idempotentService;
    }

    @Override
    public void create(OrderCreateRequest request) {
        String key = "idempotent:order:create:" + request.getRequestNo();
        boolean acquired = idempotentService.tryAcquire(key, Duration.ofMinutes(10));
        if (!acquired) {
            throw new BizException("请勿重复提交");
        }

        // 执行订单创建逻辑
    }
}
```

这段代码体现的是：

- 同一个 requestNo 在幂等窗口内只能处理一次

## 9. 典型实现方式三：基于状态机幂等

很多核心业务其实并不一定需要额外幂等表或 Redis key，直接依赖状态机就够了。

例如支付回调：

- 如果支付单状态已经是 SUCCESS
- 再来一次回调，直接返回

这其实就是一种非常实用、非常贴近业务的幂等方式。

## 10. 为什么幂等不能只靠前端

因为重复请求的来源不一定是用户点了两次。  
还可能是：

- 前端超时自动重试
- 网关重试
- MQ 重投
- 第三方回调重复通知

所以幂等必须是后端能力，不能只靠前端按钮置灰解决。

## 11. 常见坑点

### 11.1 把“重复请求”简单等同于“同一个用户”

这样定义太粗，容易误伤正常请求。

### 11.2 幂等窗口过长或过短

太短可能挡不住重复请求，太长可能影响正常业务重试。

### 11.3 只做入口幂等，不做业务状态幂等

复杂系统里这通常是不够的。

## 12. 总结

接口幂等的核心，不是“拦一次重复点击”，而是明确同一业务请求的唯一身份，并确保它无论被触发多少次，最终只产生一次有效结果。

一个成熟的幂等实现通常会组合使用：

- 请求级幂等 key
- 业务唯一约束
- 状态机幂等判断

这才是高并发系统里真正稳的做法。
