# 隔离实现

## 1. 功能定义

隔离要解决的问题是：

- 当某一类请求、某个依赖或某个模块出现异常时，如何避免它影响到整个系统的其他部分

它的核心思想很简单：

- 不要让所有流量、线程、连接池、依赖都混在一起共用同一份资源

否则只要某一块出问题，就很容易把全系统拖下水。

## 2. 为什么隔离很重要

高并发系统里，很多事故并不是“某个功能坏了”，而是：

- 某个功能坏了以后，抢占了所有公共资源

例如：

- 一个慢接口把 Tomcat 线程占满
- 一个下游服务超时导致线程池打满
- 某个大查询把数据库连接池耗光

这时候真正的问题不是局部失败，而是“故障扩散”。

隔离的目的就是：

- 把故障控制在局部

## 3. 常见隔离类型

工程里最常见的隔离通常包括：

1. 线程池隔离
2. 连接池隔离
3. 服务隔离
4. 资源隔离
5. 流量隔离

最典型、最容易理解的是：

- 线程池隔离

## 4. 典型场景

例如一个接口里同时调用：

- 用户服务
- 推荐服务
- 评论服务

其中推荐服务经常慢。  
如果三个调用共享同一个线程执行模型，那么推荐服务一慢，整个接口都被拖住。

更合理的做法通常是：

- 把推荐调用放进独立线程池

这样推荐挂了，至少不会把主线程资源全部占住。

## 5. 核心设计

隔离实现时，建议重点考虑：

1. 哪些资源最容易被抢光
2. 哪些模块最容易成为拖累源
3. 哪些调用必须隔离
4. 隔离后的容量怎么配

这里最关键的一点是：

- 隔离不是万能优化，而是“故障扩散阻断器”

## 6. 核心代码

## 6.1 线程池隔离示例

```java
@Configuration
public class ThreadPoolConfig {

    @Bean("recommendExecutor")
    public Executor recommendExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("recommend-");
        executor.initialize();
        return executor;
    }
}
```

## 6.2 隔离调用核心实现

```java
@Service
public class HomePageServiceImpl implements HomePageService {

    private final RecommendRemoteClient recommendRemoteClient;
    private final Executor recommendExecutor;

    public HomePageServiceImpl(
            RecommendRemoteClient recommendRemoteClient,
            @Qualifier("recommendExecutor") Executor recommendExecutor) {
        this.recommendRemoteClient = recommendRemoteClient;
        this.recommendExecutor = recommendExecutor;
    }

    @Override
    public HomePageVO queryHomePage(Long userId) {
        CompletableFuture<List<ProductVO>> recommendFuture =
                CompletableFuture.supplyAsync(() -> recommendRemoteClient.query(userId), recommendExecutor)
                        .exceptionally(ex -> Collections.emptyList());

        HomePageVO vo = new HomePageVO();
        vo.setRecommendProducts(recommendFuture.join());
        return vo;
    }
}
```

这段代码体现了隔离的核心思路：

- 推荐服务有自己独立的执行资源
- 推荐失败不会直接拖垮整个主流程

## 7. 为什么线程池隔离很常见

因为远程调用最典型的问题就是：

- 慢
- 堵
- 不可控

如果所有远程调用都占主线程或同一个公共线程池，问题就会被放大。  
线程池隔离至少可以做到：

- 某个依赖慢，只影响它自己的资源池

## 8. 隔离和降级的关系

它们通常是配套使用的：

1. 先隔离  
让问题别拖垮全局。

2. 再降级  
给用户返回可接受结果。

例如：

- 推荐服务调用超时
- 只影响推荐线程池
- 页面主流程继续走
- 推荐位降级成默认内容

## 9. 常见坑点

### 9.1 所有远程调用共用一个线程池

一个依赖慢下来就可能拖死全部。

### 9.2 隔离资源容量配置过小

正常流量都可能被误伤。

### 9.3 做了隔离但没做超时和降级

问题仍然只是换了个地方卡住。

## 10. 总结

隔离的核心，不是“把代码拆开”，而是把可能互相影响的资源和调用链路隔开，让局部问题不要扩散成全局故障。

一个成熟的隔离实现通常会做到：

- 慢依赖独立资源池
- 关键路径和非关键路径分离
- 和超时、熔断、降级组合使用

这才是系统稳定性体系中非常有价值的一环。
