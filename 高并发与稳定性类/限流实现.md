# 限流实现

## 1. 功能定义

限流要解决的问题是：

- 当请求量过大时，系统如何限制单位时间内允许通过的请求数量，避免服务被打垮

高并发系统里，“性能问题”很多时候并不是因为服务逻辑本身有 bug，而是因为请求量超过了承载上限。  
这时限流的意义就在于：

- 主动舍弃一部分流量
- 保住整体系统

限流不是为了让所有请求都成功，而是为了让系统在压力下仍然可控。

## 2. 哪些场景最常需要限流

常见场景包括：

- 登录接口
- 验证码接口
- 秒杀接口
- 搜索接口
- 第三方回调入口
- 高频写接口

这些接口的共同特点通常是：

- 高频
- 容易被打爆
- 容易被恶意攻击

## 3. 限流和防刷的区别

这两个概念相关，但不完全相同：

- 限流：更偏保护系统承载能力
- 防刷：更偏识别和拦截异常行为

例如：

- 每秒最多 100 个请求，这是限流
- 某个 IP 一分钟只能发 5 次验证码，这是防刷

所以限流通常更偏系统层，防刷更偏业务安全层。

## 4. 常见限流算法

最常见的限流算法包括：

1. 固定窗口
2. 滑动窗口
3. 漏桶
4. 令牌桶

在业务系统里，最容易落地的往往是：

- Redis 固定窗口
- 网关层令牌桶

## 5. 核心设计

限流实现时，建议重点考虑：

1. 限流维度是什么  
按接口、按用户、按 IP、按商户，还是按全局。

2. 限流窗口多大  
每秒、每分钟、每小时。

3. 超限后怎么处理  
直接拒绝、排队等待还是降级返回。

4. 限流是在网关做还是业务做

## 6. 核心代码

## 6.1 Redis 固定窗口限流核心实现

```java
@Service
public class RateLimitServiceImpl implements RateLimitService {

    private final StringRedisTemplate stringRedisTemplate;

    public RateLimitServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean allow(String key, long limit, Duration duration) {
        Long count = stringRedisTemplate.opsForValue().increment(key);
        if (count != null && count == 1L) {
            stringRedisTemplate.expire(key, duration);
        }
        return count != null && count <= limit;
    }
}
```

## 6.2 接口限流使用示例

以“短信发送接口每分钟最多 5 次”为例：

```java
@Service
public class SmsCodeServiceImpl implements SmsCodeService {

    private final RateLimitService rateLimitService;

    public SmsCodeServiceImpl(RateLimitService rateLimitService) {
        this.rateLimitService = rateLimitService;
    }

    @Override
    public void sendLoginCode(String phone, String clientIp) {
        String key = "rate_limit:sms:" + phone + ":" + LocalDateTime.now().getMinute();
        boolean allow = rateLimitService.allow(key, 5, Duration.ofMinutes(1));
        if (!allow) {
            throw new BizException("请求过于频繁，请稍后再试");
        }

        // 执行短信发送逻辑
    }
}
```

这段代码体现的是最基础的限流思路：

- 同一窗口内，超过阈值就拒绝

## 7. 为什么限流通常不只做一层

正式系统里，限流往往会分层做：

1. 网关层限流  
挡住整体流量洪峰。

2. 应用层限流  
保护特定业务接口。

3. 业务维度限流  
例如按用户、按手机号、按商户限流。

因为单层限流通常无法同时兼顾：

- 系统整体保护
- 业务精细控制

## 8. 固定窗口的局限性

固定窗口实现简单，但有一个典型问题：

- 窗口边界可能被“突刺流量”钻空子

例如：

- 59 秒发 5 次
- 60 秒又发 5 次

短时间内还是可能打进很多请求。  
如果系统要求更精细，就要进一步考虑：

- 滑动窗口
- 令牌桶

## 9. 常见坑点

### 9.1 限流维度太粗

比如只按全局限流，容易误伤正常用户。

### 9.2 限流维度太细

会导致保护效果不明显。

### 9.3 被限流后没有明确提示

前端和用户都不知道发生了什么。

## 10. 总结

限流的核心，不是“少让几个人进来”，而是在超出系统承载能力时，主动用规则保护服务稳定性。

一个成熟的限流实现至少应该做到：

- 限流维度明确
- 时间窗口明确
- 超限行为明确
- 网关层和业务层分层保护

这样系统在流量上涨时才不会失控。
