# 热点数据处理实现

## 1. 功能定义

热点数据处理要解决的问题是：

- 当某些数据被极高频访问或修改时，系统如何避免这些“极热对象”成为性能瓶颈甚至故障源

高并发系统里，很多问题并不是“整体流量都很高”，而是：

- 某一个商品特别火
- 某一个用户特别活跃
- 某一个 key 被疯狂访问

这类数据就叫热点数据。

## 2. 常见热点数据场景

典型场景包括：

- 秒杀商品库存
- 爆款商品详情
- 排行榜前几名数据
- 首页热门推荐
- 大 V 用户主页

热点数据的问题通常不是“查不到”，而是：

- 大量请求在极短时间内集中打到同一个点

## 3. 为什么热点数据危险

因为热点数据很容易引发：

1. 热点 key 被打爆
2. 单条数据库记录竞争激烈
3. 缓存击穿
4. 锁竞争严重

也就是说，热点问题往往不是普通性能优化能完全解决的，它需要专门设计。

## 4. 核心设计

热点数据处理时，建议先明确：

1. 热点是读热点还是写热点
2. 热点数据有没有缓存
3. 热点是否会集中在单个 key
4. 热点请求是否允许异步化

因为：

- 读热点
- 写热点

它们的治理思路通常完全不同。

## 5. 读热点怎么处理

读热点最常见的处理方式包括：

1. 本地缓存 + Redis 缓存
2. 热点 key 永不过期或逻辑过期
3. 预热缓存
4. CDN / 静态化

例如热门商品详情页，最典型的思路就是：

- 尽量让请求打缓存，不打数据库

## 6. 写热点怎么处理

写热点更难，因为很多请求会同时改同一份数据。  
常见做法包括：

1. 原子更新
2. 分布式锁
3. 队列串行化
4. 分段热点拆分

例如秒杀库存，通常就不适合直接让所有请求同时打数据库 update。

## 7. 核心代码

## 7.1 热点读缓存示例

```java
@Service
public class HotProductServiceImpl implements HotProductService {

    private static final String HOT_PRODUCT_KEY = "product:detail:";

    private final StringRedisTemplate stringRedisTemplate;
    private final ProductMapper productMapper;

    public HotProductServiceImpl(
            StringRedisTemplate stringRedisTemplate,
            ProductMapper productMapper) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.productMapper = productMapper;
    }

    @Override
    public ProductVO detail(Long productId) {
        String key = HOT_PRODUCT_KEY + productId;
        String cache = stringRedisTemplate.opsForValue().get(key);
        if (cache != null) {
            return JSON.parseObject(cache, ProductVO.class);
        }

        Product product = productMapper.selectById(productId);
        if (product == null) {
            return null;
        }

        ProductVO vo = new ProductVO();
        vo.setId(product.getId());
        vo.setName(product.getName());
        vo.setPrice(product.getPrice());

        stringRedisTemplate.opsForValue().set(key, JSON.toJSONString(vo), Duration.ofMinutes(30));
        return vo;
    }
}
```

这是最基础的热点读处理方式：

- 热门详情尽量走缓存

## 7.2 热点库存串行化处理思路

```java
@Service
public class HotStockServiceImpl implements HotStockService {

    private final RedisDistributedLockService lockService;

    public HotStockServiceImpl(RedisDistributedLockService lockService) {
        this.lockService = lockService;
    }

    @Override
    public void deduct(Long skuId, Integer quantity) {
        String lockKey = "hot_stock:lock:" + skuId;
        String requestId = lockService.tryLock(lockKey, Duration.ofSeconds(5));
        if (requestId == null) {
            throw new BizException("当前请求过多，请稍后再试");
        }

        try {
            // 执行库存扣减
        } finally {
            lockService.unlock(lockKey, requestId);
        }
    }
}
```

这段代码只是表达热点写保护的一种思路：

- 对极热对象加互斥保护

但正式系统里，真正的秒杀库存热点通常更常结合：

- Redis 预扣
- MQ 异步下单
- 数据库最终落地

而不是只靠锁。

## 8. 为什么热点 key 过期很危险

如果一个超级热点 key 同时过期，大量请求会瞬间打回源数据库。  
这就是热点数据最典型的“缓存击穿”问题。

常见处理方式包括：

1. 热点 key 逻辑过期
2. 热点数据提前续期
3. 热点 key 单独预热
4. 互斥重建缓存

## 9. 分片热点怎么理解

有些热点写压力特别大时，会做“分片计数”或“热点拆分”。  
例如一个超热门点赞数，不一定每次都直接改同一条记录，而可能先分散写：

- `like_count:post:1:bucket1`
- `like_count:post:1:bucket2`

后续再汇总。  
这是一种典型的“把单点热点打散”的思路。

## 10. 常见坑点

### 10.1 热点数据和普通数据一视同仁

最终热点会把整个系统拖到瓶颈。

### 10.2 热点 key 过期策略和普通 key 一样

很容易触发击穿。

### 10.3 热点写场景只靠数据库硬扛

并发一高就容易出问题。

## 11. 总结

热点数据处理的核心，不是“再加点机器”，而是识别那些真正集中的读写压力点，然后针对性地做缓存、串行化、打散、预热和异步化设计。

一个成熟的热点数据处理体系通常会先区分：

- 读热点
- 写热点

然后分别设计不同治理手段。  
这才是高并发系统里真正有效的热点治理思路。
