# 分库分表实现

## 1. 功能定义

分库分表要解决的问题是：

- 当单库单表的数据量和访问压力越来越大时，系统如何把数据拆开存储和访问

它通常不是系统一开始就要上的能力，而是当业务量发展到一定阶段后，为了继续承载数据规模和流量，不得不做的一次架构升级。

最典型的场景包括：

- 订单表数据量极大
- 用户行为日志量极大
- 支付流水、消息流水持续增长

## 2. 为什么单库单表会遇到瓶颈

最常见的瓶颈包括：

1. 单表数据过大  
索引膨胀，查询变慢。

2. 单库写入压力过高
3. 数据库连接、CPU、IO 达到上限
4. 备份、迁移、DDL 风险变大

所以分库分表本质上是在解决：

- 数据规模和访问压力超出单点承载能力

## 3. 分库分表的基本思路

最常见的拆分方式包括：

### 3.1 垂直拆分

按业务域拆库，例如：

- 用户库
- 订单库
- 商品库

### 3.2 水平拆分

把同一张大表按规则拆成多张，例如：

- `order_00`
- `order_01`
- `order_02`

或者拆到多个库里。

本文重点讲高并发语境下最常见的：

- 水平分表 / 分库分表

## 4. 分库分表最常见的分片键

分片键通常要选择：

- 查询高频
- 分布均匀
- 不易变化

常见选择包括：

1. 用户 ID
2. 订单 ID
3. 商户 ID
4. 时间维度

例如订单系统里，经常会按：

- 用户 ID
- 订单号 hash

来分片。

## 5. 核心设计

分库分表不是简单“多建几张表”，实现时至少要考虑：

1. 分片键怎么选
2. 路由规则怎么定
3. 主键怎么生成
4. 跨分片查询怎么做
5. 跨分片事务怎么处理

这里最关键的一点是：

- 分片键一旦选错，后期改起来非常痛苦

## 6. 核心代码

## 6.1 简单路由规则示例

下面用“按用户 ID 分表”举例。

```java
public class OrderTableRouter {

    public String routeTable(Long userId) {
        long index = userId % 4;
        return "order_" + index;
    }
}
```

这段代码虽然简单，但它已经体现了分表最核心的思想：

- 同类数据不再只落一张表
- 而是按规则路由到不同表

## 6.2 插入时按路由写入

```java
@Service
public class ShardingOrderServiceImpl implements ShardingOrderService {

    private final OrderTableRouter orderTableRouter;
    private final JdbcTemplate jdbcTemplate;

    public ShardingOrderServiceImpl(OrderTableRouter orderTableRouter, JdbcTemplate jdbcTemplate) {
        this.orderTableRouter = orderTableRouter;
        this.jdbcTemplate = jdbcTemplate;
    }

    @Override
    public void save(Order order) {
        String tableName = orderTableRouter.routeTable(order.getUserId());
        String sql = "insert into " + tableName + " (order_no, user_id, pay_amount, status) values (?, ?, ?, ?)";
        jdbcTemplate.update(sql, order.getOrderNo(), order.getUserId(), order.getPayAmount(), order.getStatus());
    }
}
```

这里的重点不是推荐你手写 SQL 路由，而是帮助你理解：

- 分库分表的核心是路由

正式项目里更常见的做法通常是：

- ShardingSphere
- MyCat
- 自研路由层

## 7. 为什么主键生成要单独考虑

因为分库分表后，单表自增 ID 通常就不再适合作为全局唯一主键了。  
常见做法通常包括：

- 雪花算法
- 号段模式
- 全局 ID 服务

否则会出现：

- 不同分片里自增 ID 冲突

## 8. 分库分表后最痛的几个问题

### 8.1 跨分片查询

例如：

- 按订单号查单个订单还好
- 但按条件查用户全量订单、做全局统计就变复杂了

### 8.2 分页

跨多个分片分页会明显比单表分页难很多。

### 8.3 排序和聚合

像：

- 全局按时间倒序
- 全局 topN

都会变复杂。

### 8.4 跨分片事务

这通常是分库分表架构最麻烦的部分之一。

## 9. 为什么分库分表不是越早上越好

因为它会明显增加系统复杂度。  
一旦上了分库分表，很多原本简单的事情都会变难：

- 查询
- 统计
- 运维
- 迁移
- 事务

所以工程上通常是：

- 单库单表能扛住时，先别急着拆

等真正遇到容量或性能瓶颈，再结合业务热点决定是否上分库分表。

## 10. 常见坑点

### 10.1 分片键选错

后面很多查询都绕不过去。

### 10.2 先分表后想查询需求

会发现很多报表和检索非常痛苦。

### 10.3 以为分库分表能自动解决一切性能问题

很多热点问题、慢 SQL、糟糕索引设计并不会因为分片自动消失。

## 11. 总结

分库分表的核心，不是“把一张表拆成几张”，而是为系统的数据规模和访问压力提供横向扩展能力。

一个成熟的分库分表方案至少应该先想清楚：

- 分片键
- 路由规则
- 主键生成
- 跨分片查询成本

只有这些问题都想清楚，分库分表才不是“复杂化架构”，而是真正有效的容量扩展手段。
