# 防刷实现

## 1. 功能定义

防刷要解决的问题是：

- 系统如何识别和拦截异常高频、恶意或非正常的访问行为

它和普通限流不同的地方在于：

- 限流更偏保护系统承载
- 防刷更偏识别异常用户行为

例如：

- 某个手机号不断刷验证码
- 某个 IP 大量撞库登录
- 某个接口被脚本高频调用

这些都属于典型的刷接口行为。

## 2. 为什么防刷是业务安全的一部分

因为很多“刷”行为本身并不一定立即打垮系统，但会带来：

- 短信成本损失
- 验证码资源浪费
- 账号安全风险
- 营销活动被薅羊毛

所以防刷的目标不仅是稳态保护，还有业务安全和成本控制。

## 3. 常见防刷对象

防刷最常见的维度通常有：

1. IP
2. 用户 ID
3. 手机号
4. 设备 ID
5. token / session

正式项目里，防刷往往不会只看一个维度，而是多维组合判断。

## 4. 核心设计

防刷实现时，建议重点考虑：

1. 刷的定义是什么
2. 统计窗口多长
3. 拦截阈值是多少
4. 命中后处罚多久
5. 是否需要黑名单机制

这里最重要的一点是：

- 防刷不是单一阈值逻辑，而是一套行为识别策略

## 5. 常见防刷手段

最基础的防刷手段包括：

1. 频率限制
2. 验证码
3. 黑名单
4. 风险分级
5. 设备指纹

在一般 Java 后端工程里，最常见的第一步通常是：

- Redis 计数 + 短期封禁

## 6. 核心代码

## 6.1 基于 Redis 的简单防刷实现

```java
@Service
public class AntiSpamServiceImpl implements AntiSpamService {

    private final StringRedisTemplate stringRedisTemplate;

    public AntiSpamServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public void checkSmsSendRisk(String phone, String ip) {
        String phoneKey = "anti_spam:sms:phone:" + phone;
        String ipKey = "anti_spam:sms:ip:" + ip;

        Long phoneCount = stringRedisTemplate.opsForValue().increment(phoneKey);
        if (phoneCount != null && phoneCount == 1L) {
            stringRedisTemplate.expire(phoneKey, Duration.ofMinutes(10));
        }

        Long ipCount = stringRedisTemplate.opsForValue().increment(ipKey);
        if (ipCount != null && ipCount == 1L) {
            stringRedisTemplate.expire(ipKey, Duration.ofMinutes(10));
        }

        if ((phoneCount != null && phoneCount > 5) || (ipCount != null && ipCount > 20)) {
            throw new BizException("操作过于频繁，请稍后再试");
        }
    }
}
```

这段代码体现了防刷的两个典型维度：

- 手机号维度
- IP 维度

## 7. 为什么防刷通常要多维判断

因为只看单一维度很容易被绕过。  
例如：

- 只按手机号限制，攻击者可以换很多手机号
- 只按 IP 限制，攻击者可以切换代理 IP

所以更稳的做法通常是：

- 多维叠加判断

例如：

- `手机号 + IP + 设备`

## 8. 防刷和验证码的关系

很多系统在命中轻度风险时，不会立刻彻底拒绝，而是升级校验强度，例如：

1. 正常状态：直接可请求
2. 轻度异常：要求图形验证码
3. 严重异常：直接拒绝

这种思路比“一刀切全拒绝”更适合实际业务。

## 9. 黑名单怎么理解

当某些对象持续命中风险规则时，可以临时加入黑名单，例如：

- 某 IP 10 分钟内封禁
- 某设备 1 小时内禁止发送验证码

Redis 里可以用：

```json
{
  "key": "blacklist:ip:1.2.3.4",
  "ttl": 3600
}
```

来做短时封禁。

## 10. 常见坑点

### 10.1 只做简单限流，不做行为识别

这样防刷能力会比较弱。

### 10.2 阈值定得过死

容易误伤正常用户。

### 10.3 触发风控后没有分级策略

不是所有异常都应该直接彻底封死。

## 11. 总结

防刷的核心，不是“拦人”，而是通过多维度行为识别，在保护业务安全和不影响正常用户之间找到平衡。

一个成熟的防刷实现通常会组合：

- Redis 计数
- 多维度判断
- 风险分级
- 黑名单和验证码升级策略

这才是更贴近真实项目的防刷体系。
