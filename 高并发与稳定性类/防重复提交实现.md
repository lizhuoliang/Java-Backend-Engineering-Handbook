# 防重复提交实现

## 1. 功能定义

防重复提交要解决的问题是：

- 用户在短时间内重复点击提交按钮时，系统如何避免同一个动作被执行多次

最常见的场景包括：

- 重复下单
- 重复支付
- 重复提交表单
- 重复申请审批

它经常和“接口幂等”一起出现，但更偏用户入口层面的保护。

## 2. 为什么会出现重复提交

最常见的原因包括：

1. 用户连续点击按钮
2. 页面卡顿导致用户以为没点上
3. 网络重试
4. 前端重复发请求

如果业务没有保护，就可能直接导致：

- 多笔订单
- 多条申请单
- 多条重复记录

## 3. 防重复提交和幂等的关系

可以这样理解：

- 防重复提交：入口级短时间去重
- 幂等：业务级语义去重

例如下单场景里：

1. 防重复提交先挡掉“1 秒内连续点 3 次”
2. 幂等再兜底“即使重复请求打进来了，也只会创建一次订单”

正式项目里，关键写接口通常两层都要有。

## 4. 核心设计

防重复提交实现时，建议重点考虑：

1. 重复窗口多长
2. 以什么维度去重  
用户 ID、请求 token、请求摘要。

3. 拦住后怎么返回
4. 是前后端配合，还是纯后端控制

## 5. 常见实现方式

最常见的方式包括：

1. 前端按钮置灰
2. 后端 Redis 短期 key
3. 请求唯一 token

其中真正可靠的一层还是：

- 后端控制

## 6. 核心代码

## 6.1 基于 Redis 的重复提交拦截

```java
@Service
public class RepeatSubmitServiceImpl implements RepeatSubmitService {

    private final StringRedisTemplate stringRedisTemplate;

    public RepeatSubmitServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public void check(String key, Duration duration) {
        Boolean success = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", duration);
        if (Boolean.FALSE.equals(success)) {
            throw new BizException("请勿重复提交");
        }
    }
}
```

## 6.2 下单场景使用示例

```java
@Service
public class OrderCreateServiceImpl implements OrderCreateService {

    private final RepeatSubmitService repeatSubmitService;

    public OrderCreateServiceImpl(RepeatSubmitService repeatSubmitService) {
        this.repeatSubmitService = repeatSubmitService;
    }

    @Override
    public void create(Long userId, OrderCreateRequest request) {
        String key = "repeat_submit:order:create:" + userId;
        repeatSubmitService.check(key, Duration.ofSeconds(3));

        // 执行下单逻辑
    }
}
```

这段代码适合挡住：

- 同一个用户极短时间内的连续重复点击

## 7. 为什么防重复提交通常只适合“短窗口”

因为它本质上不是业务唯一性约束，而是一个短期入口保护。  
例如：

- 3 秒内不允许重复下单

这很合理。  
但如果你把窗口拉成 10 分钟，就可能误伤正常业务。

所以防重复提交通常更适合：

- 秒级窗口
- 入口保护

而不是拿它代替真正的业务幂等。

## 8. 请求摘要去重怎么理解

有些系统会把：

- 用户 ID
- 接口路径
- 请求参数摘要

拼成一个去重 key。  
这样可以更精细地判断：

- 是不是同一个用户提交了完全相同的一次请求

这种方式通常比只按用户 ID 粗暴拦截更合理。

## 9. 常见坑点

### 9.1 只靠前端按钮置灰

用户仍然可以通过抓包或重放请求绕过。

### 9.2 窗口时间设置过长

会影响正常重复操作。

### 9.3 把防重复提交当成幂等

它们解决的问题层级不同，不能互相替代。

## 10. 总结

防重复提交的核心，是为高频写操作增加一层短时间去重保护，避免用户侧重复点击直接转化成后端重复业务执行。

一个成熟的实现通常会做到：

- 前端交互层防抖
- 后端 Redis 短期拦截
- 核心业务仍有幂等兜底

这样才既不容易误伤正常用户，也能有效挡住重复提交问题。
