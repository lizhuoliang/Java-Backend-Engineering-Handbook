# 熔断实现

## 1. 功能定义

熔断要解决的问题是：

- 当某个下游服务持续异常或响应极慢时，当前系统如何主动停止继续调用它，避免问题不断扩大

“熔断”这个名字来自电路保险丝。  
本质上它想表达的是：

- 下游已经明显出问题了
- 这时不应该继续硬扛调用
- 应该先断开，保护自己

在微服务、第三方依赖、远程 RPC 调用较多的系统里，熔断是一项非常重要的稳定性能力。

## 2. 为什么需要熔断

想象一个系统依赖了短信平台、支付平台、用户中心。  
如果其中一个服务开始大量超时，而你的系统还持续无脑重试调用，就可能出现：

- 线程被大量占满
- 请求响应越来越慢
- 整体服务被拖垮

这时真正的问题已经不是“某个接口失败”，而是：

- 下游故障开始向上游扩散

熔断的意义就是：

- 在故障扩散前主动切断依赖

## 3. 熔断和降级的区别

这两个词经常一起出现，但可以这样区分：

- 熔断：先断开调用
- 降级：断开后给一个兜底结果

例如：

- 熔断：不再访问推荐服务
- 降级：推荐位先返回默认商品

也就是说：

- 熔断更偏保护
- 降级更偏结果兜底

## 4. 核心设计

熔断实现时，建议先明确：

1. 对哪些下游调用做熔断
2. 触发熔断的条件是什么  
失败率、超时率、异常次数。

3. 熔断多久
4. 熔断恢复时怎么试探下游是否正常

这其实就是一个典型的状态机问题。

## 5. 熔断器常见状态

一个经典熔断器通常有 3 个状态：

1. `CLOSED`  
正常状态，请求可以通过。

2. `OPEN`  
熔断状态，请求不再调用下游，直接失败或走降级。

3. `HALF_OPEN`  
半开状态，允许少量请求试探下游是否恢复。

## 6. 核心代码

## 6.1 简化版熔断器实现

```java
public class SimpleCircuitBreaker {

    private volatile String state = "CLOSED";
    private final AtomicInteger failCount = new AtomicInteger(0);
    private volatile long openUntil = 0L;

    public boolean allowRequest() {
        long now = System.currentTimeMillis();
        if ("OPEN".equals(state)) {
            if (now > openUntil) {
                state = "HALF_OPEN";
                return true;
            }
            return false;
        }
        return true;
    }

    public void recordSuccess() {
        failCount.set(0);
        state = "CLOSED";
    }

    public void recordFailure() {
        int count = failCount.incrementAndGet();
        if (count >= 5) {
            state = "OPEN";
            openUntil = System.currentTimeMillis() + 10000;
        }
    }
}
```

这段代码是一个非常简化的熔断思路，但已经足以说明问题：

- 连续失败达到阈值就打开熔断
- 熔断一段时间后再试探恢复

## 6.2 业务调用示例

```java
@Service
public class UserRemoteService {

    private final SimpleCircuitBreaker circuitBreaker = new SimpleCircuitBreaker();

    public UserInfo queryUser(Long userId) {
        if (!circuitBreaker.allowRequest()) {
            throw new BizException("用户服务暂不可用");
        }

        try {
            UserInfo userInfo = doRemoteCall(userId);
            circuitBreaker.recordSuccess();
            return userInfo;
        } catch (Exception ex) {
            circuitBreaker.recordFailure();
            throw new BizException("用户服务调用失败");
        }
    }

    private UserInfo doRemoteCall(Long userId) {
        return new UserInfo();
    }
}
```

这里体现的核心思想是：

- 下游连续失败后，不再继续硬调

## 7. 为什么熔断必须和超时控制配合

因为很多时候下游并不是立即报错，而是：

- 一直慢
- 一直卡住

如果不设置超时，请求会大量堆积在线程池中。  
所以熔断通常一定要和：

- 超时
- 重试
- 线程隔离

一起看，不能孤立设计。

## 8. 正式项目一般怎么做

实际工程里，通常不会手写一个简易熔断器长期使用，而是更常用：

- Resilience4j
- Sentinel

因为它们已经把这些能力做得更完整：

- 失败率统计
- 慢调用比例
- 半开探测
- 监控指标

但理解底层原理仍然很重要。

## 9. 常见坑点

### 9.1 下游一直超时还持续重试调用

会迅速拖垮上游。

### 9.2 熔断后没有恢复探测机制

会导致服务明明恢复了，调用方还一直断着。

### 9.3 熔断阈值拍脑袋设置

过于敏感或过于迟钝都不好。

## 10. 总结

熔断的核心，不是“某次失败就报错”，而是在下游持续异常时主动切断调用，把局部问题限制在局部范围内。

一个成熟的熔断实现至少应该做到：

- 明确触发条件
- 熔断状态可切换
- 熔断恢复可探测
- 和超时、重试、隔离一起设计

这才是真正能保护系统稳定性的熔断能力。
