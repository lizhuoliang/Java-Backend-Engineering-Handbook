# 认证鉴权实现

## 1. 功能定义

认证鉴权通常分成两部分：

- 认证：确认当前请求是谁发起的
- 鉴权：确认这个人有没有权限访问当前资源

很多初学者会把这两个概念混在一起，但在真实项目里，它们是两层不同的能力：

1. 先认证，解决“你是谁”
2. 再鉴权，解决“你能干什么”

如果和前面几篇串起来看：

- 注册：创建账号
- 登录：签发 `token`
- 退出：让 `token` 失效
- 认证鉴权：拦截后续所有请求并判断是否允许访问

## 2. 典型流程

在 `JWT + Redis` 方案里，一个请求进入系统后的典型流程如下：

1. 前端在请求头中携带 `token`
2. 过滤器或拦截器读取 `Authorization`
3. 校验 `token` 格式是否正确
4. 去 Redis 校验登录态是否存在
5. 解析出当前用户信息
6. 将当前用户放入上下文
7. 进入业务接口
8. 如果接口需要特定权限，再继续做权限判断

## 3. 请求示例

```http
GET /user/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.xxx.xxx
```

## 4. 核心设计

认证鉴权最核心的设计点有 4 个：

1. 哪些接口需要放行，例如登录、注册、验证码接口
2. 如何统一拦截请求，而不是每个接口手动判断
3. 如何获取当前登录用户
4. 如何判断当前用户是否有某个权限

所以这篇的重点不是“写很多代码”，而是把这条链路设计完整。

## 5. 认证核心代码

## 5.1 当前用户上下文

后续业务代码经常需要拿到当前登录人，所以一般会做一个线程上下文工具类。

```java
public class UserContext {

    private static final ThreadLocal<LoginUser> THREAD_LOCAL = new ThreadLocal<>();

    public static void set(LoginUser loginUser) {
        THREAD_LOCAL.set(loginUser);
    }

    public static LoginUser get() {
        return THREAD_LOCAL.get();
    }

    public static void clear() {
        THREAD_LOCAL.remove();
    }
}
```

当前登录用户对象只保留最核心的信息即可：

```java
public class LoginUser {

    private Long userId;
    private String username;

    public LoginUser(Long userId, String username) {
        this.userId = userId;
        this.username = username;
    }

    public Long getUserId() {
        return userId;
    }

    public String getUsername() {
        return username;
    }
}
```

## 5.2 JWT 解析核心方法

这里只保留认证流程里最关键的解析代码。

```java
@Component
public class JwtTokenProvider {

    private static final String SECRET = "replace-with-your-secret-key";

    public Claims parseToken(String token) {
        return Jwts.parserBuilder()
                .setSigningKey(Keys.hmacShaKeyFor(SECRET.getBytes(StandardCharsets.UTF_8)))
                .build()
                .parseClaimsJws(token)
                .getBody();
    }
}
```

## 5.3 认证拦截器

这一段是整篇最核心的代码。  
它负责统一完成“取 token -> 校验 token -> 查 Redis -> 放入上下文”。

```java
@Component
public class AuthInterceptor implements HandlerInterceptor {

    private static final String TOKEN_PREFIX = "Bearer ";
    private static final String LOGIN_TOKEN_PREFIX = "login:token:";

    private final StringRedisTemplate stringRedisTemplate;
    private final JwtTokenProvider jwtTokenProvider;

    public AuthInterceptor(
            StringRedisTemplate stringRedisTemplate,
            JwtTokenProvider jwtTokenProvider) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.jwtTokenProvider = jwtTokenProvider;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String authorization = request.getHeader("Authorization");
        if (authorization == null || !authorization.startsWith(TOKEN_PREFIX)) {
            throw new BizException("未登录");
        }

        String token = authorization.substring(TOKEN_PREFIX.length()).trim();
        if (token.isEmpty()) {
            throw new BizException("未登录");
        }

        Claims claims;
        try {
            claims = jwtTokenProvider.parseToken(token);
        } catch (Exception ex) {
            throw new BizException("登录已失效");
        }

        String loginJson = stringRedisTemplate.opsForValue().get(LOGIN_TOKEN_PREFIX + token);
        if (loginJson == null) {
            throw new BizException("登录已失效");
        }

        Long userId = Long.valueOf(claims.getSubject());
        String username = claims.get("username", String.class);
        UserContext.set(new LoginUser(userId, username));
        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex) {
        UserContext.clear();
    }
}
```

这段代码做了 4 件事：

- 检查请求头里有没有 `token`
- 校验 `JWT` 是否合法
- 去 Redis 检查登录态是否还存在
- 把当前用户放进 `ThreadLocal`

## 5.4 拦截器注册

真正做项目时，不是所有接口都要拦截。  
像注册、登录、发送验证码这种接口通常需要放行。

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final AuthInterceptor authInterceptor;

    public WebMvcConfig(AuthInterceptor authInterceptor) {
        this.authInterceptor = authInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/**")
                .excludePathPatterns(
                        "/auth/login",
                        "/auth/register",
                        "/auth/sendCode"
                );
    }
}
```

## 5.5 在业务代码中获取当前用户

有了 `UserContext` 之后，业务层拿当前登录人会非常方便。

```java
@GetMapping("/profile")
public Result<Map<String, Object>> profile() {
    LoginUser loginUser = UserContext.get();
    return Result.success(Map.of(
            "userId", loginUser.getUserId(),
            "username", loginUser.getUsername()
    ));
}
```

## 6. 鉴权核心思路

认证通过之后，接下来才是鉴权。

最常见的做法是基于权限标识判断，例如：

- `user:add`
- `user:delete`
- `role:list`

权限数据通常来自数据库，登录后可以缓存到 Redis，或者在请求时动态查询。

## 7. 权限校验核心代码

这里先给一个轻量但足够说明问题的版本。

## 7.1 权限注解

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequirePermission {

    String value();
}
```

## 7.2 权限校验拦截器

```java
@Component
public class PermissionInterceptor implements HandlerInterceptor {

    private final PermissionService permissionService;

    public PermissionInterceptor(PermissionService permissionService) {
        this.permissionService = permissionService;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;
        }

        RequirePermission requirePermission = handlerMethod.getMethodAnnotation(RequirePermission.class);
        if (requirePermission == null) {
            return true;
        }

        LoginUser loginUser = UserContext.get();
        if (loginUser == null) {
            throw new BizException("未登录");
        }

        boolean hasPermission = permissionService.hasPermission(loginUser.getUserId(), requirePermission.value());
        if (!hasPermission) {
            throw new BizException("无权限访问");
        }

        return true;
    }
}
```

## 7.3 权限校验服务

这里只保留最核心的方法签名和一个最简单的思路。

```java
public interface PermissionService {

    boolean hasPermission(Long userId, String permissionCode);
}
```

```java
@Service
public class PermissionServiceImpl implements PermissionService {

    private final StringRedisTemplate stringRedisTemplate;

    public PermissionServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean hasPermission(Long userId, String permissionCode) {
        String key = "permission:user:" + userId;
        Set<String> permissionSet = stringRedisTemplate.opsForSet().members(key);
        return permissionSet != null && permissionSet.contains(permissionCode);
    }
}
```

## 7.4 权限使用示例

```java
@RequirePermission("user:list")
@GetMapping("/user/list")
public Result<String> listUser() {
    return Result.success("ok");
}
```

这就形成了一条完整链路：

1. `AuthInterceptor` 负责认证
2. `PermissionInterceptor` 负责鉴权
3. 业务接口只关心自己需要什么权限

## 9. 为什么认证和鉴权要分开

这样设计有几个明显好处：

1. 职责清晰  
认证只关心“你是不是合法登录用户”，鉴权只关心“你能不能访问这个接口”。

2. 易于扩展  
以后即使登录方式从用户名密码扩展到短信登录、单点登录、第三方登录，鉴权逻辑仍然可以复用。

3. 易于维护  
认证问题和权限问题排查路径不同，拆开后更容易定位问题。

## 10. 常见坑点

### 10.1 只校验 JWT，不查 Redis

这会导致退出登录、踢下线失效。

### 10.2 忘记清理 ThreadLocal

如果请求结束后不执行 `UserContext.clear()`，可能会造成线程复用带来的脏数据问题。

### 10.3 把权限判断写死在 Controller 里

这样后面接口一多，代码会变得非常难维护。

### 10.4 放行路径配置不完整

登录、注册、验证码接口如果没有正确放行，会导致系统连获取 `token` 的入口都被拦住。

### 10.5 权限缓存不更新

如果用户角色或权限变了，但 Redis 没有及时刷新，可能出现“权限已经修改，但仍按旧权限运行”的问题。

## 11. 面试中常见问法

### 11.1 认证和鉴权有什么区别

回答重点：

- 认证解决“你是谁”
- 鉴权解决“你能访问什么”

### 11.2 为什么 JWT 还要配合 Redis

回答重点：

- Redis 控制登录态是否有效
- 支持退出登录、踢下线、续期

### 11.3 当前登录用户信息一般怎么传递

回答重点：

- 拦截器解析 `token`
- 放入 `ThreadLocal`
- 业务层统一读取

### 11.4 为什么要做权限注解

回答重点：

- 让接口权限声明更清晰
- 避免把权限逻辑散落在业务代码里

## 12. 总结

一个工程化的认证鉴权实现，核心不是把所有逻辑堆在登录接口里，而是建立一条完整的请求校验链路：

请求进入系统后，先通过拦截器完成 `token` 解析、Redis 登录态校验和当前用户上下文注入；认证通过后，再根据接口声明的权限标识执行权限判断，最终决定是否允许访问资源。

这套设计足够轻量，但已经具备真实项目里最关键的认证和鉴权骨架。
