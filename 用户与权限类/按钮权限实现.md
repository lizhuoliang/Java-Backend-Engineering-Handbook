# 按钮权限实现

## 1. 功能定义

按钮权限要解决的问题是：

- 当前用户能不能看到“新增”按钮
- 能不能点“删除”“编辑”“导出”

它通常比菜单权限更细，因为同一个页面里，不同按钮往往代表不同操作能力。

例如在“用户管理”页面里：

- 有人只能查看列表
- 有人可以新增用户
- 有人可以删除用户

这些差异通常就是通过按钮权限来控制。

## 2. 典型数据结构

按钮权限在很多系统里其实也是一种权限标识，只是它落在页面按钮上。

```json
[
  "user:list",
  "user:add",
  "user:update",
  "user:delete",
  "user:export"
]
```

前端页面会根据后端返回的权限标识来决定某个按钮是否展示：

```json
{
  "page": "用户管理",
  "buttons": [
    {
      "name": "新增",
      "permissionCode": "user:add"
    },
    {
      "name": "删除",
      "permissionCode": "user:delete"
    }
  ]
}
```

## 3. 核心设计

按钮权限一般不单独做一套系统，而是直接复用 `RBAC` 里已有的权限标识。

也就是说：

- 菜单权限决定页面能不能看到
- 按钮权限决定页面里的操作能不能做
- 接口权限决定后端是否真正放行

这三层最好使用一致的权限标识体系。

## 4. 典型流程

1. 用户登录
2. 后端查询用户拥有的权限标识集合
3. 前端保存这批权限标识
4. 页面渲染按钮时判断是否包含对应权限
5. 即使前端按钮隐藏，后端接口仍然继续做权限校验

注意：  
按钮权限首先是“前端展示控制”，但最终安全边界仍然在后端接口权限。

## 5. 核心代码

## 5.1 查询当前用户权限标识

这个接口通常登录成功后就会调用一次。

```java
@RestController
@RequestMapping("/permission")
public class PermissionController {

    private final PermissionService permissionService;

    public PermissionController(PermissionService permissionService) {
        this.permissionService = permissionService;
    }

    @GetMapping("/my-codes")
    public Result<Set<String>> myPermissionCodes() {
        Long userId = UserContext.get().getUserId();
        return Result.success(permissionService.getPermissionCodesByUserId(userId));
    }
}
```

## 5.2 权限查询核心实现

按钮权限最核心的后端逻辑，就是返回当前用户的权限标识集合。

```java
@Service
public class PermissionServiceImpl implements PermissionService {

    private static final String PERMISSION_KEY_PREFIX = "permission:user:";

    private final StringRedisTemplate stringRedisTemplate;
    private final PermissionMapper permissionMapper;

    public PermissionServiceImpl(
            StringRedisTemplate stringRedisTemplate,
            PermissionMapper permissionMapper) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.permissionMapper = permissionMapper;
    }

    @Override
    public Set<String> getPermissionCodesByUserId(Long userId) {
        String key = PERMISSION_KEY_PREFIX + userId;
        Set<String> cacheSet = stringRedisTemplate.opsForSet().members(key);
        if (cacheSet != null && !cacheSet.isEmpty()) {
            return cacheSet;
        }

        Set<String> permissionSet = permissionMapper.selectPermissionCodesByUserId(userId);
        if (permissionSet != null && !permissionSet.isEmpty()) {
            stringRedisTemplate.opsForSet().add(key, permissionSet.toArray(new String[0]));
        }
        return permissionSet;
    }
}
```

## 5.3 后端接口仍然要做权限校验

前端隐藏按钮只是用户体验优化，不是安全控制。

所以后端接口仍然应该保留权限注解：

```java
@RequirePermission("user:delete")
@DeleteMapping("/user/{id}")
public Result<Void> deleteUser(@PathVariable Long id) {
    userService.deleteUser(id);
    return Result.success();
}
```

这样即使有人手动构造请求，也会被后端拦下来。

## 6. 前后端协作方式

### 6.1 后端返回权限集合

```json
[
  "user:list",
  "user:add",
  "user:update"
]
```

### 6.2 前端判断按钮是否展示

逻辑本质上就是：

```text
如果当前用户权限集合包含 user:add -> 显示新增按钮
否则隐藏
```

## 7. 为什么按钮权限不能只靠前端控制

因为前端代码是用户可见的，也可以被人为绕过。

如果只做：

- 没权限就隐藏按钮

但不做：

- 后端接口鉴权

那么攻击者仍然可以直接请求接口。

所以正确做法永远是：

1. 前端用按钮权限控制展示
2. 后端用接口权限控制安全

## 8. 常见坑点

### 8.1 把按钮权限当成纯前端逻辑

按钮隐藏不代表接口安全。

### 8.2 权限标识不统一

前端写的是 `userAdd`，后端校验的是 `user:add`，最后很容易对不上。

### 8.3 每个页面单独写一堆 if 判断

如果没有统一权限标识体系，页面越多越难维护。

## 9. 总结

按钮权限本质上是 `RBAC` 权限标识在页面操作层面的落地。

后端负责返回当前用户的权限标识集合，前端根据这些标识控制按钮展示，后端接口再通过统一鉴权保证真正的安全边界。这样才是一套完整的按钮权限实现。
