# 数据权限实现

## 1. 功能定义

数据权限要解决的问题不是“能不能访问接口”，而是：

- 访问同一个接口时，不同用户能看到哪些数据

例如：

- 普通员工只能看自己的数据
- 部门经理可以看本部门数据
- 区域负责人可以看本区域数据
- 管理员可以看全部数据

这就是典型的数据权限场景。

所以数据权限比菜单权限、按钮权限更进一步，它控制的是“结果集范围”。

## 2. 常见数据权限类型

工程里最常见的数据权限可以抽象成这几种：

```json
[
  "ALL",
  "DEPT",
  "DEPT_AND_CHILD",
  "SELF",
  "CUSTOM"
]
```

含义分别是：

- `ALL`：全部数据
- `DEPT`：本部门数据
- `DEPT_AND_CHILD`：本部门及子部门数据
- `SELF`：仅本人数据
- `CUSTOM`：自定义部门范围

## 3. 核心设计

数据权限实现最关键的点有 3 个：

1. 数据权限通常挂在角色上，而不是直接挂在用户上
2. 数据权限最终要转成 SQL 查询条件
3. 不同业务表的数据归属字段要统一，例如 `creator_id`、`dept_id`

如果这些前提没有设计好，后面做数据权限会非常痛苦。

## 4. 典型流程

1. 当前用户发起请求
2. 系统查出当前用户的数据权限范围
3. 把权限范围转换成查询条件
4. 拼接到业务查询中
5. 返回当前用户可见的数据

## 5. 核心数据示例

假设角色表里有一个字段 `dataScope`：

```json
[
  {
    "roleCode": "admin",
    "dataScope": "ALL"
  },
  {
    "roleCode": "manager",
    "dataScope": "DEPT"
  },
  {
    "roleCode": "employee",
    "dataScope": "SELF"
  }
]
```

用户信息里则能查到：

```json
{
  "userId": 101,
  "deptId": 20
}
```

## 6. 核心代码

## 6.1 数据权限范围对象

```java
public class DataScope {

    private String type;
    private Long userId;
    private Long deptId;
    private Set<Long> deptIds;

    public String getType() {
        return type;
    }

    public void setType(String type) {
        this.type = type;
    }

    public Long getUserId() {
        return userId;
    }

    public void setUserId(Long userId) {
        this.userId = userId;
    }

    public Long getDeptId() {
        return deptId;
    }

    public void setDeptId(Long deptId) {
        this.deptId = deptId;
    }

    public Set<Long> getDeptIds() {
        return deptIds;
    }

    public void setDeptIds(Set<Long> deptIds) {
        this.deptIds = deptIds;
    }
}
```

## 6.2 Service 接口

```java
public interface DataPermissionService {

    DataScope getCurrentUserDataScope();
}
```

## 6.3 Service 核心实现

这一段的目标是：根据当前用户角色，计算出数据范围。

```java
@Service
public class DataPermissionServiceImpl implements DataPermissionService {

    private final RoleMapper roleMapper;
    private final DeptMapper deptMapper;

    public DataPermissionServiceImpl(RoleMapper roleMapper, DeptMapper deptMapper) {
        this.roleMapper = roleMapper;
        this.deptMapper = deptMapper;
    }

    @Override
    public DataScope getCurrentUserDataScope() {
        LoginUser loginUser = UserContext.get();
        Role role = roleMapper.selectMainRoleByUserId(loginUser.getUserId());

        DataScope scope = new DataScope();
        scope.setType(role.getDataScope());
        scope.setUserId(loginUser.getUserId());
        scope.setDeptId(role.getDeptId());

        if ("DEPT_AND_CHILD".equals(role.getDataScope())) {
            Set<Long> deptIds = deptMapper.selectDeptIdsWithChildren(role.getDeptId());
            scope.setDeptIds(deptIds);
        }

        if ("CUSTOM".equals(role.getDataScope())) {
            Set<Long> deptIds = deptMapper.selectCustomDeptIdsByRoleId(role.getId());
            scope.setDeptIds(deptIds);
        }

        return scope;
    }
}
```

## 6.4 在业务查询中拼接数据权限

数据权限最终一定要落到查询条件上。

例如一个“查询用户列表”的接口：

```java
@Service
public class UserQueryService {

    private final UserMapper userMapper;
    private final DataPermissionService dataPermissionService;

    public UserQueryService(
            UserMapper userMapper,
            DataPermissionService dataPermissionService) {
        this.userMapper = userMapper;
        this.dataPermissionService = dataPermissionService;
    }

    public List<User> listUsers() {
        DataScope scope = dataPermissionService.getCurrentUserDataScope();
        return userMapper.selectByDataScope(scope);
    }
}
```

Mapper 核心方法：

```java
public interface UserMapper {

    List<User> selectByDataScope(@Param("scope") DataScope scope);
}
```

SQL 的核心思路大概是：

```text
ALL -> 不加限制
DEPT -> where dept_id = 当前部门
DEPT_AND_CHILD -> where dept_id in (...)
SELF -> where creator_id = 当前用户
CUSTOM -> where dept_id in (自定义部门集合)
```

## 7. 为什么数据权限通常放在角色层

因为数据范围往往是某一类岗位共同拥有的能力。

例如：

- 所有部门经理都看本部门数据
- 所有普通员工都只能看自己数据

如果把数据权限直接绑在每个用户身上，后面会非常难维护。

## 8. 常见坑点

### 8.1 只做页面控制，不做 SQL 限制

这样接口一旦被直接调用，仍然可能把全部数据查出来。

### 8.2 业务表没有统一归属字段

如果有的表叫 `creator_id`，有的表叫 `userId`，有的表根本没有部门字段，数据权限会非常难统一实现。

### 8.3 多角色数据权限取值规则不清

一个用户可能有多个角色，这时到底取最大范围、最小范围还是主角色范围，必须提前定好规则。

## 9. 总结

数据权限的核心不是“用户有没有权限点这个按钮”，而是“同样一个查询接口，不同用户最终能看到哪些数据”。

它通常建立在 `RBAC` 之上，由角色决定数据范围，再通过服务层和 SQL 条件把这个范围真正落实到查询结果里。这是后台系统工程化能力里非常关键的一环。
