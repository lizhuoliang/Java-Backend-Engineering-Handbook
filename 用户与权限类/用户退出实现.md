# 用户退出实现

## 1. 功能定义

用户退出的目标，是让当前登录用户主动结束本次会话，并让当前 `token` 失效。

从表面看，退出登录像是一个很简单的功能，但工程上真正要解决的是：

- 如何识别当前是谁在退出
- 如何让当前 `token` 立即失效
- 退出后后续请求如何被拦截
- 多端登录时是退出当前端，还是全部端

本文默认沿用前一篇登录方案：

- `Spring Boot`
- `MyBatis-Plus`
- `Redis`
- `JWT`

## 2. 典型退出流程

最常见的退出流程如下：

1. 前端携带当前 `token` 调用退出接口
2. 后端解析请求头中的 `token`
3. 删除 Redis 中对应的登录态
4. 返回退出成功
5. 前端清理本地保存的 `token`

如果后续再拿这个 `token` 访问接口，因为 Redis 里已经查不到登录态，所以请求会被判定为未登录。

## 3. 请求与返回示例

### 3.1 退出请求

```http
POST /auth/logout
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.xxx.xxx
```

### 3.2 退出成功返回

```json
{
  "code": 200,
  "message": "success"
}
```

## 4. 核心设计

如果你的登录方案是“`JWT + Redis` 登录态”，那么退出登录最核心的动作只有一个：

- 删除 Redis 中当前 `token` 对应的会话数据

也就是说，退出并不是“销毁 JWT 本身”，而是“让系统不再承认这个 JWT 对应的登录态”。

## 5. 核心代码

## 5.1 Controller

```java
@RestController
@RequestMapping("/auth")
public class AuthController {

    private final AuthService authService;

    public AuthController(AuthService authService) {
        this.authService = authService;
    }

    @PostMapping("/logout")
    public Result<Void> logout(HttpServletRequest request) {
        authService.logout(request);
        return Result.success();
    }
}
```

## 5.2 Service 接口

```java
public interface AuthService {

    void logout(HttpServletRequest request);
}
```

## 5.3 Service 核心实现

退出功能真正重要的逻辑，就是从请求头里拿到 `token`，然后删除 Redis 登录态。

```java
@Service
public class AuthServiceImpl implements AuthService {

    private static final String TOKEN_PREFIX = "Bearer ";
    private static final String LOGIN_TOKEN_PREFIX = "login:token:";

    private final StringRedisTemplate stringRedisTemplate;

    public AuthServiceImpl(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public void logout(HttpServletRequest request) {
        String authorization = request.getHeader("Authorization");
        if (authorization == null || !authorization.startsWith(TOKEN_PREFIX)) {
            return;
        }

        String token = authorization.substring(TOKEN_PREFIX.length()).trim();
        if (token.isEmpty()) {
            return;
        }

        stringRedisTemplate.delete(LOGIN_TOKEN_PREFIX + token);
    }
}
```

这段代码的关键点很简单：

- 从请求头中取出 `Authorization`
- 去掉 `Bearer ` 前缀
- 拿到真实 `token`
- 删除 Redis 中 `login:token:token值`

## 6. 为什么退出登录只删 Redis 就够了

因为在这套方案里，真正决定“当前用户是否在线”的不是 `JWT` 字符串本身，而是 Redis 里的登录态是否存在。

比如 Redis 中原来的数据是：

```json
{
  "key": "login:token:eyJhbGciOiJIUzI1NiJ9.xxx.xxx",
  "value": {
    "userId": 1,
    "username": "zhangsan"
  },
  "ttl": 7200
}
```

退出后这条数据被删除，那么后面的认证拦截器在校验时就会发现：

- `token` 虽然格式还合法
- 但 Redis 中已经没有对应登录态

于是系统会把它视为未登录。

## 7. 后续请求为什么会失效

退出登录真正生效，依赖的是后续的认证拦截逻辑。

后续接口一般会这样校验：

1. 解析请求头中的 `token`
2. 检查 `JWT` 格式是否正确
3. 去 Redis 查询 `login:token:token值`
4. 如果查不到，就认定当前登录态已失效

所以退出功能和认证拦截器，其实是一套联动设计。

## 8. 为什么退出接口通常设计成幂等

一个用户可能会连续点两次“退出登录”，也可能前端已经清掉了本地 `token` 后又重复调用一次接口。

这时候退出接口最好保持幂等：

- Redis 里有这个 `token`，就删除
- Redis 里没有这个 `token`，也直接返回成功

这样前后端对接会更稳定。

上面的实现里，如果请求头为空，或者 Redis 本来就没有这条记录，也不会报错，这就是一种典型的幂等处理方式。

## 9. 单端退出和全端退出

退出登录常见有两种模式。

### 9.1 当前端退出

只让当前 `token` 失效。  
这也是最常见的退出方式。

### 9.2 全部端退出

让这个用户在所有设备上的登录态全部失效。

这种情况下，Redis 键设计通常不会只按 `token` 来存，还会额外维护一个用户和多个 `token` 的关系，例如：

```json
{
  "userId": 1,
  "tokens": [
    "tokenA",
    "tokenB",
    "tokenC"
  ]
}
```

当用户点击“退出全部设备”时，就可以一次性删除这个用户关联的全部 `token`。

## 10. 常见坑点

### 10.1 前端只删本地 token，后端不删 Redis

这样看起来像退出了，但如果本地 `token` 被恢复，服务端仍然可能承认它。

### 10.2 只校验 JWT，不校验 Redis

如果认证拦截器不查 Redis，那么退出登录删除 Redis 就没有意义。

### 10.3 退出后没有统一走认证拦截

后续接口如果绕过认证校验，就会出现“明明退出了还能访问”的问题。

### 10.4 请求头格式不统一

前后端必须统一使用：

```http
Authorization: Bearer token值
```

否则退出、认证、中间件解析都容易出问题。

## 11. 面试中常见问法

### 11.1 用户退出登录你会怎么实现

回答重点：

- 从请求头获取当前 `token`
- 删除 Redis 中对应登录态
- 后续请求在认证拦截器中查 Redis
- 查不到则判定未登录

### 11.2 为什么 JWT 退出还要依赖 Redis

回答重点：

- 纯 JWT 天生不方便服务端主动失效
- Redis 可以控制会话失效
- 便于做退出登录、踢下线、单端登录

### 11.3 为什么退出接口最好做成幂等

回答重点：

- 避免重复点击导致异常
- 提升前后端交互稳定性
- Redis 删除不存在的 key 本身就适合做幂等处理

## 12. 总结

一个工程化的用户退出实现，本质上不是“通知前端跳回登录页”，而是服务端主动让当前 `token` 的登录态失效。

在 `JWT + Redis` 方案里，最核心的做法就是：前端带着当前 `token` 调用退出接口，后端删除 Redis 中对应的登录态，后续所有请求再统一通过认证拦截器判定该 `token` 是否仍然有效。

这套设计简单，但很实用，也是大多数 Java 后端项目里最常见的退出实现方式。
