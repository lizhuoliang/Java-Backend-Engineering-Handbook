# 文件版本管理实现

## 1. 功能定义

文件版本管理要解决的问题是：

- 同一个业务文件在多次修改后，如何保留历史版本

典型场景包括：

- 合同修改记录
- 制度文档版本迭代
- 需求文档多次上传
- 附件替换后保留旧版本

如果没有版本管理，新的文件一上传，旧文件就被覆盖掉，后续很难追溯变化历史。

## 2. 版本管理和普通文件管理的区别

普通文件管理更关注：

- 文件能不能上传、下载、预览

版本管理额外关注：

- 这份文件的历史演进关系是什么
- 当前最新版本是哪一个
- 旧版本能不能回看、回滚

所以版本管理的重点不是存储，而是“版本关系”。

## 3. 常见设计方式

文件版本管理常见有两种建模方式。

### 3.1 主文件表 + 版本表

最常见，也最推荐。

例如：

- `file_document`：表示逻辑上的“这份文档”
- `file_document_version`：表示这份文档的每次具体版本

### 3.2 每次上传都当新文件，再用业务字段串起来

也能做，但后续维护起来通常没有主从表清晰。

## 4. 典型数据结构

```json
{
  "documentId": 3001,
  "documentName": "合同模板",
  "currentVersion": 3,
  "versions": [
    {
      "versionNo": 1,
      "fileId": 1001
    },
    {
      "versionNo": 2,
      "fileId": 1002
    },
    {
      "versionNo": 3,
      "fileId": 1003
    }
  ]
}
```

这个结构里最重要的点是：

- 逻辑文件是一个概念
- 每次上传只是新增一个版本

## 5. 典型流程

1. 第一次上传文件，创建逻辑文档和版本 1
2. 后续上传新文件，不覆盖旧文件，而是新增版本 2、3、4
3. 业务默认读取当前最新版本
4. 如果需要追溯历史，再查看版本列表

## 6. 核心设计

文件版本管理时，建议先明确这几个规则：

1. 版本号如何生成  
最常见的是简单递增：1、2、3……

2. 当前版本如何标识  
可以在主表存 `currentVersion` 或 `currentVersionId`

3. 历史版本是否允许删除  
很多正式系统里，历史版本通常不允许随意删

4. 替换文件时是覆盖还是新增版本  
更推荐新增版本

## 7. 核心代码

## 7.1 新增版本接口思路

上传新版本通常不是直接重新造一份文档，而是对已有文档追加版本。

```json
{
  "documentId": 3001,
  "fileId": 1003,
  "remark": "更新了合同条款"
}
```

## 7.2 Service 核心实现

```java
@Service
public class FileVersionServiceImpl implements FileVersionService {

    private final FileDocumentMapper fileDocumentMapper;
    private final FileDocumentVersionMapper fileDocumentVersionMapper;
    private final FileRecordMapper fileRecordMapper;

    public FileVersionServiceImpl(
            FileDocumentMapper fileDocumentMapper,
            FileDocumentVersionMapper fileDocumentVersionMapper,
            FileRecordMapper fileRecordMapper) {
        this.fileDocumentMapper = fileDocumentMapper;
        this.fileDocumentVersionMapper = fileDocumentVersionMapper;
        this.fileRecordMapper = fileRecordMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void addVersion(Long documentId, Long fileId, String remark) {
        FileDocument document = fileDocumentMapper.selectById(documentId);
        if (document == null) {
            throw new BizException("文档不存在");
        }

        FileRecord fileRecord = fileRecordMapper.selectById(fileId);
        if (fileRecord == null) {
            throw new BizException("文件不存在");
        }

        int nextVersionNo = document.getCurrentVersion() + 1;

        FileDocumentVersion version = new FileDocumentVersion();
        version.setDocumentId(documentId);
        version.setVersionNo(nextVersionNo);
        version.setFileId(fileId);
        version.setRemark(remark);
        fileDocumentVersionMapper.insert(version);

        FileDocument updateDoc = new FileDocument();
        updateDoc.setId(documentId);
        updateDoc.setCurrentVersion(nextVersionNo);
        updateDoc.setCurrentVersionId(version.getId());
        fileDocumentMapper.updateById(updateDoc);
    }
}
```

这段代码的核心思想是：

- 新版本不会覆盖旧文件
- 只是新增一条版本记录
- 然后把主文档指向最新版本

## 8. 为什么版本管理不建议直接覆盖旧文件

因为一旦覆盖，历史信息就丢了。

而很多真实业务里，文件历史版本很重要，例如：

- 谁在什么时候改了合同
- 某次审批看到的是哪个版本
- 出问题后要回溯旧文档

所以工程上更推荐：

- 保留全部版本
- 用“当前版本”指向最新

## 9. 版本回滚怎么理解

版本回滚并不一定真的要删除新版本。  
更常见的做法是：

- 选择某个旧版本
- 把它重新设为当前版本

或者：

- 基于旧版本重新生成一个新版本

这样历史链路会更完整。

## 10. 常见坑点

### 10.1 新版本直接覆盖旧文件路径

会导致历史版本彻底不可追溯。

### 10.2 只在文件表里改名字，不保留版本关系

这样系统其实并没有真正的版本管理能力。

### 10.3 当前版本和历史版本关系不清

后面查询最新文档、查看历史列表时都会很混乱。

## 11. 总结

文件版本管理的核心，不是“多存几份文件”，而是围绕一个逻辑文档，把每次上传形成的历史演进关系管理起来。

一个成熟的实现通常会做到：

- 主文件和版本表分离
- 新上传生成新版本而不是覆盖旧文件
- 当前版本单独标识
- 历史版本可追溯

这类能力在合同、制度、知识库、审批附件等场景里都非常有价值。
