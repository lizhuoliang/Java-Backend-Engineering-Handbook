# 附件管理实现

## 1. 功能定义

附件管理要解决的问题是：

- 某个业务对象下挂了哪些文件
- 这些文件如何查看、下载、删除、替换

它和普通文件上传不同的地方在于：

- 文件上传只解决“文件进系统”
- 附件管理解决“文件如何和业务建立关系”

例如：

- 合同记录下挂多个附件
- 工单下挂截图和日志文件
- 文章下挂资料压缩包

这些都属于附件管理。

## 2. 核心设计

附件管理最关键的设计点不是文件本身，而是“业务绑定关系”。

通常会有两种做法：

### 2.1 业务表直接存单个 fileId

适合：

- 一个业务对象只对应一个文件

例如：

- 用户头像
- 单个合同扫描件

### 2.2 单独做业务附件关系表

适合：

- 一个业务对象对应多个附件

例如：

- 工单附件
- 文章附件
- 商品资料包

正式项目里，第二种更常见，也更灵活。

## 3. 典型数据结构

```json
{
  "bizType": "order",
  "bizId": 5001,
  "attachments": [
    {
      "fileId": 1001,
      "fileName": "付款截图.png"
    },
    {
      "fileId": 1002,
      "fileName": "补充说明.pdf"
    }
  ]
}
```

关系表通常最少会有：

- `bizType`
- `bizId`
- `fileId`

## 4. 典型流程

1. 先上传文件
2. 拿到 `fileId`
3. 调用附件绑定接口，把文件绑定到业务对象
4. 后续查询业务详情时，同时查询附件列表

## 5.1 绑定附件请求

## 5.2 Service 接口

```java
public interface AttachmentService {

    void bindAttachments(String bizType, Long bizId, List<Long> fileIds);

    List<FileSimpleVO> listByBiz(String bizType, Long bizId);
}
```

## 5.3 绑定附件核心实现

```java
@Service
public class AttachmentServiceImpl implements AttachmentService {

    private final AttachmentRelationMapper attachmentRelationMapper;
    private final FileRecordMapper fileRecordMapper;

    public AttachmentServiceImpl(
            AttachmentRelationMapper attachmentRelationMapper,
            FileRecordMapper fileRecordMapper) {
        this.attachmentRelationMapper = attachmentRelationMapper;
        this.fileRecordMapper = fileRecordMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void bindAttachments(String bizType, Long bizId, List<Long> fileIds) {
        attachmentRelationMapper.deleteByBiz(bizType, bizId);

        if (fileIds == null || fileIds.isEmpty()) {
            return;
        }

        for (Long fileId : fileIds) {
            FileRecord record = fileRecordMapper.selectById(fileId);
            if (record == null) {
                throw new BizException("附件不存在: " + fileId);
            }
            attachmentRelationMapper.insertRelation(bizType, bizId, fileId);
        }
    }

    @Override
    public List<FileSimpleVO> listByBiz(String bizType, Long bizId) {
        return attachmentRelationMapper.selectFilesByBiz(bizType, bizId);
    }
}
```

这段代码的核心思想是：

- 文件和业务解耦
- 通过关系表建立绑定

这样后面一个业务对象要挂一个附件、多个附件、替换附件，都比较灵活。

## 6. 为什么附件管理不能只在业务表里存路径

如果业务表直接存很多路径字符串，会有几个问题：

1. 不利于统一管理  
后续删除、统计、审计都不方便。

2. 很难支持多附件  
尤其是一个对象挂多个文件时会很别扭。

3. 不利于更换存储方案  
路径一旦写死在业务表里，迁移成本会很高。

所以更推荐的方式是：

- 文件先进入统一文件表
- 业务通过关系表引用它

## 7. 附件删除要注意什么

附件删除通常分两层：

1. 解除业务绑定
2. 是否真正删除物理文件

很多时候，一个文件可能被多个业务引用。  
所以直接删除物理文件之前，最好先判断：

- 是否还有别的业务在引用这个文件

这一步如果不做，很容易误删仍在使用中的文件。

## 8. 常见坑点

### 8.1 业务表直接堆一长串文件 URL

后期维护成本会越来越高。

### 8.2 解绑附件时直接删物理文件

如果该文件还被别处引用，就会出问题。

### 8.3 文件上传和附件绑定混成一个接口

短期看方便，长期不利于复用。

## 9. 总结

附件管理的核心，不是文件本身，而是“文件和业务对象之间的关系管理”。一个成熟的实现，应该把上传、存储、关系绑定、引用检查这几层拆清楚，这样后续任何业务都能复用同一套附件体系。
