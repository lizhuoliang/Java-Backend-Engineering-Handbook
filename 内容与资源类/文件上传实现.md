# 文件上传实现

## 1. 功能定义

文件上传要解决的问题是：

- 前端把用户选择的文件安全地传到后端
- 后端完成校验、命名、存储，并返回可访问地址或文件标识

看起来它只是一个“把文件存起来”的功能，但在工程化项目里，真正要考虑的问题远不止这些：

- 允许上传哪些文件类型
- 文件大小怎么限制
- 文件名是否可信
- 文件应该存本地、对象存储还是数据库
- 如何避免重名覆盖
- 如何记录文件元数据
- 如何保证后续下载、预览、删除都能找到这份文件

所以，文件上传本质上不是一个单接口问题，而是一套“上传入口 + 存储策略 + 文件元数据管理”的基础能力。

## 2. 常见应用场景

文件上传在真实系统里非常常见，例如：

- 用户头像上传
- 富文本图片上传
- 附件上传
- Excel 导入模板上传
- 合同、发票、证件等业务文件上传

不同场景对上传能力的要求不一样：

- 头像更关注图片格式和尺寸
- 附件更关注安全与权限
- 导入模板更关注后续解析
- 合同类文件更关注归档和元数据记录

所以工程上通常不会把上传接口只当作“存一个 byte[]”。

## 3. 常见存储方案

文件上传最常见的存储方式有 3 种。

### 3.1 本地磁盘存储

适合：

- 单机项目
- 内网工具
- 学习阶段

优点：

- 简单直接
- 调试方便

缺点：

- 不适合多机部署
- 扩容困难
- 容器化环境里不稳定

### 3.2 对象存储

例如：

- `OSS`
- `COS`
- `MinIO`

适合：

- 大多数正式项目
- 需要高可用和扩展能力的场景

优点：

- 扩展性强
- 访问方便
- 适合云化部署

缺点：

- 需要额外接入配置

### 3.3 数据库存储

通常不推荐把大文件直接存数据库，除非是很特殊的小文件场景。  
因为数据库更适合存“文件元数据”，而不是存大体积二进制内容。

## 4. 一个典型的上传流程

一个工程化的上传流程通常如下：

1. 前端通过 `multipart/form-data` 提交文件
2. 后端接收 `MultipartFile`
3. 校验文件是否为空
4. 校验文件大小
5. 校验文件类型
6. 生成安全文件名
7. 写入目标存储
8. 记录文件元数据
9. 返回文件访问地址、文件 ID 或存储路径

## 5. 典型请求与返回

### 5.1 前端请求

```http
POST /file/upload
Content-Type: multipart/form-data
```

### 5.2 成功返回

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "fileId": 1001,
    "fileName": "avatar.png",
    "url": "/static/upload/20260601/8f7a2d1a.png",
    "size": 24567
  }
}
```

## 6. 核心设计

文件上传实现时，我建议至少提前定好下面这几个设计点：

1. 上传接口只负责“接收 + 校验 + 存储 + 记录元数据”
2. 文件内容和文件元数据分开处理
3. 文件名不要直接使用原始文件名
4. 文件路径尽量分日期目录，避免单目录文件过多
5. 上传接口和业务表解耦，业务只引用 `fileId` 或 URL

其中第 5 点很重要。  
例如用户头像表、合同表、文章附件表，不一定都直接存文件路径，很多系统会让业务表只引用文件表主键。

## 7. 文件元数据示例

上传成功后，通常会在数据库里保存一条文件记录：

```json
{
  "id": 1001,
  "originName": "avatar.png",
  "storageName": "8f7a2d1a.png",
  "contentType": "image/png",
  "size": 24567,
  "storagePath": "/static/upload/20260601/8f7a2d1a.png",
  "bizType": "avatar",
  "uploadUserId": 1
}
```

这些字段的意义分别是：

- `originName`：原始文件名，方便展示
- `storageName`：实际存储文件名，避免冲突
- `contentType`：文件类型
- `size`：文件大小
- `storagePath`：真实存储路径或访问地址
- `bizType`：业务类型，例如头像、合同、附件
- `uploadUserId`：上传人

## 8. 核心代码

## 8.1 Controller

上传接口的 Controller 一般比较薄，只接收文件和业务类型。

```java
@RestController
@RequestMapping("/file")
public class FileController {

    private final FileService fileService;

    public FileController(FileService fileService) {
        this.fileService = fileService;
    }

    @PostMapping("/upload")
    public Result<FileUploadVO> upload(
            @RequestParam("file") MultipartFile file,
            @RequestParam(value = "bizType", required = false) String bizType) {
        return Result.success(fileService.upload(file, bizType));
    }
}
```

## 8.2 Service 接口

```java
public interface FileService {

    FileUploadVO upload(MultipartFile file, String bizType);
}
```

## 8.3 Service 核心实现

这里先用“本地磁盘存储”举例，因为最容易理解，也最适合打基础。  
真正上线时，这一层可以很自然地切到 `MinIO` 或 `OSS`。

```java
@Service
public class LocalFileServiceImpl implements FileService {

    private static final long MAX_SIZE = 10 * 1024 * 1024L;
    private static final Set<String> ALLOW_SUFFIX = Set.of("jpg", "jpeg", "png", "pdf", "docx");

    private final FileRecordMapper fileRecordMapper;

    @Value("${file.upload.base-path}")
    private String basePath;

    public LocalFileServiceImpl(FileRecordMapper fileRecordMapper) {
        this.fileRecordMapper = fileRecordMapper;
    }

    @Override
    public FileUploadVO upload(MultipartFile file, String bizType) {
        validateFile(file);

        String originName = file.getOriginalFilename();
        String suffix = getSuffix(originName);
        String dateDir = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
        String storageName = UUID.randomUUID().toString().replace("-", "") + "." + suffix;

        Path dirPath = Paths.get(basePath, dateDir);
        Path targetPath = dirPath.resolve(storageName);

        try {
            Files.createDirectories(dirPath);
            file.transferTo(targetPath.toFile());
        } catch (IOException ex) {
            throw new BizException("文件上传失败");
        }

        String storagePath = "/static/upload/" + dateDir + "/" + storageName;

        FileRecord record = new FileRecord();
        record.setOriginName(originName);
        record.setStorageName(storageName);
        record.setContentType(file.getContentType());
        record.setSize(file.getSize());
        record.setStoragePath(storagePath);
        record.setBizType(bizType);
        record.setUploadUserId(UserContext.get().getUserId());
        fileRecordMapper.insert(record);

        FileUploadVO vo = new FileUploadVO();
        vo.setFileId(record.getId());
        vo.setFileName(originName);
        vo.setUrl(storagePath);
        vo.setSize(file.getSize());
        return vo;
    }

    private void validateFile(MultipartFile file) {
        if (file == null || file.isEmpty()) {
            throw new BizException("上传文件不能为空");
        }

        if (file.getSize() > MAX_SIZE) {
            throw new BizException("文件大小超过限制");
        }

        String suffix = getSuffix(file.getOriginalFilename());
        if (!ALLOW_SUFFIX.contains(suffix.toLowerCase())) {
            throw new BizException("文件类型不支持");
        }
    }

    private String getSuffix(String fileName) {
        if (!StringUtils.hasText(fileName) || !fileName.contains(".")) {
            throw new BizException("文件名不合法");
        }
        return fileName.substring(fileName.lastIndexOf('.') + 1);
    }
}
```

这段代码做了上传功能里最关键的几件事：

- 校验文件是否为空
- 校验文件大小
- 校验后缀名
- 生成随机文件名
- 按日期目录存储
- 保存文件元数据
- 返回访问结果

public class FileUploadVO {

## 9. 为什么文件名不能直接用原始文件名

如果直接使用原始文件名，会有几个问题：

1. 重名覆盖  
两个用户都上传 `test.png`，后一个可能把前一个覆盖掉。

2. 安全问题  
原始文件名可能包含特殊字符、路径片段、脚本风险字符。

3. 路径不可控  
系统很难保证统一的命名规范。

所以工程上通常会这样做：

- 展示时保留 `originName`
- 存储时使用 `UUID` 或雪花 ID 作为 `storageName`

## 10. 为什么文件元数据要单独存表

因为后续很多能力都会依赖它，例如：

- 文件下载
- 文件预览
- 文件删除
- 统计某类附件数量
- 判断某个文件是否被业务引用

如果不存文件元数据，你后面很多操作都会很被动。

## 11. 本地存储方案的优缺点

### 优点

- 实现简单
- 适合单体项目和学习阶段
- 调试成本低

### 缺点

- 多节点部署时文件不共享
- 容器重启后数据可能丢失
- 扩容麻烦

所以如果你是做正式项目，一般最终会把 `LocalFileServiceImpl` 抽象成统一接口，然后切换成对象存储实现。

## 12. 如果切到 MinIO 或 OSS，代码怎么演进

这一层的演进路径通常是这样的：

1. `FileService` 保持不变
2. 新增 `MinioFileServiceImpl` 或 `OssFileServiceImpl`
3. `upload()` 方法里的核心变化只有“文件写入方式”
4. 文件元数据记录逻辑仍然保留

也就是说，真正应该稳定的是：

- 上传流程
- 文件校验
- 元数据结构

而不是具体的存储介质。

## 13. 常见安全问题

文件上传是一个很容易被忽视的安全入口，至少要注意下面这些问题。

### 13.1 只校验文件后缀，不校验内容类型

有些恶意文件会伪装后缀名。  
更严格的系统里，除了校验后缀，还会校验 `contentType`，甚至做文件头检测。

### 13.2 上传目录可直接执行脚本

如果上传目录被当成可执行目录，风险很高。  
上传目录应该尽量只作为静态资源或对象存储资源，不要具备执行能力。

### 13.3 文件大小无限制

这会导致磁盘、内存、网络带宽都承压。

### 13.4 上传接口没有鉴权

很多系统里的附件上传是需要登录的，甚至需要区分业务权限。

## 14. 常见坑点

### 14.1 上传成功了，但数据库没记录

这样后续只能看到磁盘文件，却不知道业务上怎么引用它。

### 14.2 数据库记了记录，但文件没真正落盘

这会造成脏数据。  
所以文件写入和元数据保存最好作为一条完整流程处理。

### 14.3 所有文件都堆在一个目录

文件一多，目录性能和维护体验都会下降。

### 14.4 业务表直接存复杂路径字符串

更推荐业务表引用 `fileId`，这样后续替换存储策略会更灵活。

## 15. 面试里常见问法

### 15.1 文件上传你会怎么设计

回答重点：

- 接收 `MultipartFile`
- 校验文件大小和类型
- 生成安全文件名
- 写入本地或对象存储
- 记录文件元数据
- 返回文件 ID 或访问地址

### 15.2 为什么文件元数据要单独存表

回答重点：

- 便于下载、预览、删除
- 便于和业务解耦
- 便于后续统计和引用管理

### 15.3 本地存储和对象存储怎么选

回答重点：

- 本地适合单机和学习
- 对象存储适合正式项目和多节点部署

## 16. 总结

文件上传的核心，从来不是“把文件收上来”这么简单，而是围绕上传入口、校验规则、存储策略和元数据记录建立一套可扩展的基础能力。

如果只从代码层压缩成一句话，一个工程化的文件上传实现通常应该做到：

- 用 `MultipartFile` 接收文件
- 做大小和类型校验
- 用随机文件名和目录分层存储
- 保存文件元数据
- 返回文件 ID 或 URL

这套骨架一旦搭好，后续扩展图片上传、附件管理、对象存储切换，都会顺很多。
