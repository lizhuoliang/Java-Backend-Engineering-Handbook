# 文件下载实现

## 1. 功能定义

文件下载要解决的问题是：

- 已经上传到系统里的文件，如何稳定、安全地返回给用户

如果说文件上传是“把文件送进系统”，那么文件下载就是“把文件按正确方式再送出来”。

很多人第一次做下载时，会觉得这只是一个 `response.getOutputStream()` 的问题，但真正工程化落地时，还要同时处理下面这些点：

- 根据什么标识找到文件
- 如何校验当前用户有没有下载权限
- 文件名怎么在浏览器里正常显示
- 文件不存在时如何处理
- 大文件下载怎么避免内存占用过高
- 文件物理路径变更后，业务如何不受影响

所以文件下载的重点，不只是“返回字节流”，而是围绕文件元数据建立一条完整的获取链路。

## 2. 常见下载方式

文件下载常见有两种方式。

### 2.1 直接文件流输出

后端读取文件，再把内容写到响应流里。

适合：

- 本地文件存储
- 需要做权限校验的场景
- 需要统一记录下载日志的场景

### 2.2 返回临时访问地址

后端不直接传文件，而是返回对象存储的临时签名 URL。

适合：

- OSS / MinIO / COS 等对象存储
- 大文件下载
- 希望减轻应用服务器带宽压力

本文先讲最经典、最容易理解的“后端流式下载”。

## 3. 典型下载流程

一个完整的文件下载流程通常如下：

1. 前端传入 `fileId`
2. 后端根据 `fileId` 查询文件元数据
3. 校验文件是否存在
4. 校验当前用户是否有权限下载
5. 根据存储路径读取文件
6. 设置响应头
7. 把文件内容写入输出流

## 4. 典型请求与返回

### 4.1 下载请求

```http
GET /file/download/1001
```

### 4.2 元数据示例

```json
{
  "id": 1001,
  "originName": "合同.pdf",
  "storagePath": "D:/upload/20260601/8f7a2d1a.pdf",
  "contentType": "application/pdf",
  "size": 24567,
  "bizType": "contract"
}
```

## 5. 核心设计

文件下载设计时，我建议先定好这几个原则：

1. 下载接口尽量按 `fileId` 查询，不直接暴露物理路径
2. 文件元数据和物理文件分离
3. 下载前一定要做权限校验
4. 响应头要正确设置文件名和内容类型
5. 大文件尽量使用流式读取，而不是一次性读入内存

其中第一点非常重要。  
如果前端直接传完整路径，后端就很容易暴露内部存储结构，也不利于后续切换存储方案。

## 6. 核心代码

## 6.1 Controller

```java
@RestController
@RequestMapping("/file")
public class FileController {

    private final FileDownloadService fileDownloadService;

    public FileController(FileDownloadService fileDownloadService) {
        this.fileDownloadService = fileDownloadService;
    }

    @GetMapping("/download/{fileId}")
    public void download(@PathVariable Long fileId, HttpServletResponse response) {
        fileDownloadService.download(fileId, response);
    }
}
```

## 6.2 Service 接口

```java
public interface FileDownloadService {

    void download(Long fileId, HttpServletResponse response);
}
```

## 6.3 Service 核心实现

```java
@Service
public class LocalFileDownloadServiceImpl implements FileDownloadService {

    private final FileRecordMapper fileRecordMapper;
    private final FilePermissionService filePermissionService;

    public LocalFileDownloadServiceImpl(
            FileRecordMapper fileRecordMapper,
            FilePermissionService filePermissionService) {
        this.fileRecordMapper = fileRecordMapper;
        this.filePermissionService = filePermissionService;
    }

    @Override
    public void download(Long fileId, HttpServletResponse response) {
        FileRecord record = fileRecordMapper.selectById(fileId);
        if (record == null) {
            throw new BizException("文件不存在");
        }

        filePermissionService.checkDownloadPermission(UserContext.get().getUserId(), record);

        Path path = Paths.get(record.getStoragePath());
        if (!Files.exists(path)) {
            throw new BizException("文件不存在或已丢失");
        }

        response.setContentType(
                StringUtils.hasText(record.getContentType())
                        ? record.getContentType()
                        : MediaType.APPLICATION_OCTET_STREAM_VALUE
        );

        String fileName = URLEncoder.encode(record.getOriginName(), StandardCharsets.UTF_8);
        response.setHeader("Content-Disposition", "attachment; filename*=UTF-8''" + fileName);

        try (InputStream inputStream = Files.newInputStream(path);
             OutputStream outputStream = response.getOutputStream()) {
            inputStream.transferTo(outputStream);
            outputStream.flush();
        } catch (IOException ex) {
            throw new BizException("文件下载失败");
        }
    }
}
```

这段代码的关键点有 4 个：

- 先查文件元数据
- 再做权限校验
- 设置正确的响应头
- 使用流式输出而不是整块读内存

## 7. 为什么下载接口应该先查文件表

因为后续很多能力都依赖这一步：

- 权限判断
- 文件名展示
- 下载日志
- 文件状态判断
- 是否逻辑删除

如果跳过文件表，直接拿路径下载，后面的扩展空间会很差。

## 8. 文件权限一般怎么控制

文件下载权限常见有几种控制方式：

1. 上传人本人可下载
2. 业务归属人可下载
3. 某业务模块下的有权限角色可下载
4. 管理员可下载全部

例如一个合同附件，通常不会允许系统里所有登录用户都下载。

所以在工程里，最好抽一个单独的文件权限服务：

```java
public interface FilePermissionService {

    void checkDownloadPermission(Long userId, FileRecord record);
}
```

这样上传、下载、删除、预览都可以复用同一套权限判断逻辑。

## 9. 为什么文件名要做编码处理

如果文件名包含中文，例如：

- `合同.pdf`
- `张三简历.docx`

而响应头没有做编码处理，就很容易出现浏览器下载时乱码。

所以工程里通常会用：

```java
filename*=UTF-8''编码后文件名
```

这是一种兼容性比较好的写法。

## 10. 大文件下载怎么处理

对于普通附件，直接流式返回就够用了。  
但如果是大文件，例如：

- 视频
- 大型压缩包
- 数据备份文件

通常还要考虑：

1. 支持断点续传
2. 返回对象存储临时下载地址
3. 限制并发下载
4. 记录下载审计

也就是说，普通下载和大文件下载往往不是完全同一个层级的问题。

## 11. 常见坑点

### 11.1 直接让前端传物理路径

这会暴露内部目录结构，也不方便后续更换存储介质。

### 11.2 一次性把整个文件读进内存

文件稍大时就容易造成内存压力。

### 11.3 下载前不做权限校验

这会导致敏感文件被越权访问。

### 11.4 数据库有记录但磁盘文件丢了

这种情况必须明确返回错误，而不是直接空响应。

## 12. 面试里常见问法

### 12.1 文件下载你会怎么设计

回答重点：

- 前端传 `fileId`
- 后端查文件元数据
- 校验权限
- 设置响应头
- 流式输出文件内容

### 12.2 为什么要按 fileId 下载，而不是直接传路径

回答重点：

- 隐藏内部路径
- 方便权限控制
- 方便记录日志和扩展

## 13. 总结

文件下载的核心，不是“把文件吐给前端”，而是基于文件元数据建立一条可控、安全、可扩展的取回链路。

一个工程化的下载实现，至少应该做到：

- 通过 `fileId` 查文件
- 做权限校验
- 设置正确的下载响应头
- 用流式方式输出内容

这样后续无论你是本地磁盘存储，还是切换到对象存储，下载层都比较容易演进。
